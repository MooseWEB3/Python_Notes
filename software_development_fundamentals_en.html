How to use this guide

Software development is the disciplined work of turning a real need into software that people can use, change, operate, and trust. Programming is central, but production software also requires discovery, design, version control, testing, review, deployment, monitoring, security, and teamwork.

This guide is language-agnostic, with small Python examples because they are easy to read. Follow the chapters in order on a first pass. For each example, ask four questions: What problem does it solve? What assumptions does it make? How could it fail? How would we know it still works after a change?

Learning goals

By the end, you will be able to:

  • explain the software development lifecycle and why feedback loops matter;
  • turn an ambiguous request into requirements and acceptance criteria;
  • split work into small, testable increments;
  • design modules, interfaces, data models, and error behavior;
  • use Git branches, commits, pull requests, and reviews effectively;
  • manage environments, dependencies, configuration, and secrets;
  • distinguish unit, integration, end-to-end, and non-functional tests;
  • debug with evidence and add useful logs and metrics;
  • apply refactoring, review, security, CI/CD, and release practices;
  • build a small project with a maintainable structure.
AreaCore questionTypical evidence
DiscoveryAre we solving the right problem?user interviews, problem statement
RequirementsWhat must be true for success?acceptance criteria, examples
DesignHow will responsibilities be divided?diagrams, interfaces, ADRs
ImplementationIs the change understandable and correct?code, tests, review
DeliveryCan the change reach users safely?CI results, release plan
OperationsDoes it work in the real world?logs, metrics, alerts, feedback

The shortest useful definition: software development is programming plus the feedback systems that keep programming aligned with reality.

1. Software, programs, and products

1.1 A program is not automatically a software product

A program can solve one task on one machine. A software product must continue to work for users, evolve as needs change, and remain operable by a team. Production concerns include compatibility, data migration, access control, failure recovery, documentation, and support.

One-off scriptMaintained software
known input and operatormany users and unexpected inputs
manual executionrepeatable deployment and operation
author remembers assumptionsassumptions are documented and tested
failure can be inspected locallyfailures need logs, alerts, and recovery
change is occasionalchange is continuous

1.2 The cost of change

Most software cost occurs after the first version. Clear names, small modules, automated tests, reproducible environments, and useful documentation reduce the cost and risk of future changes. These are not decoration; they are economic tools.

1.3 Constraints shape engineering decisions

A two-person internal dashboard and a global payment system should not use the same process or architecture. Important constraints include users, data sensitivity, traffic, latency, budget, deadline, team skills, regulation, and the cost of failure.

Text
Decision quality = technical knowledge + product context + explicit trade-offs

2. Discover the problem before designing the solution

2.1 Write a problem statement

A good problem statement names the affected user, the current difficulty, its impact, and the desired outcome without prescribing an implementation too early.

Text
Weak:  Build a dashboard with React and five charts.

Better: Support agents spend about 20 minutes each morning combining three
exports to identify overdue tickets. They need a trustworthy view that reduces
preparation to under two minutes and shows when the data was last refreshed.

The better version permits multiple solutions and supplies measurable value.

2.2 Identify users and stakeholders

Users interact with the system. Stakeholders may fund, operate, secure, regulate, or support it. Ask who benefits, who bears risk, who approves release, who responds to failure, and whose workflow will change.

2.3 Make assumptions visible

Maintain an assumption log. Rank each assumption by impact and uncertainty; validate high-impact, high-uncertainty assumptions first.

Text
Assumption: Agents can access the source system with one shared service account.
Risk:       High—security policy may prohibit shared credentials.
Validation: Ask the identity team before implementation begins.
Owner:      Mei
Due:        2026-08-14

3. Requirements and acceptance criteria

3.1 Functional and non-functional requirements

Functional requirements describe behavior. Non-functional requirements describe qualities and constraints such as response time, availability, accessibility, privacy, recovery time, and supported platforms.

TypeExample
FunctionalA user can reset a password by email
Performance95% of searches complete within 500 ms
ReliabilityThe monthly availability target is 99.9%
SecuritySessions expire after 30 minutes of inactivity
AccessibilityKeyboard users can complete checkout
DataAudit records are retained for seven years

3.2 User stories are conversation starters

Text
As a support agent,
I want to filter overdue tickets by team,
so that I can prioritize the morning queue.

A story does not replace details, design, or conversation. Add examples, constraints, out-of-scope notes, and acceptance criteria.

3.3 Use testable acceptance criteria

The Given–When–Then form makes observable behavior explicit.

Text
Given tickets from Team North and Team South are overdue,
When the agent selects Team North,
Then only overdue Team North tickets appear,
And the result count and last-refresh time remain visible.

Avoid words such as “fast,” “easy,” or “secure” unless they are tied to a verifiable threshold or standard.

3.4 Control scope

Separate must-have outcomes from possible follow-ups. Define “not in this release.” A smaller complete slice produces more learning than several half-finished features.

Markdown
## In scope
- Filter overdue tickets by team
- Show source refresh time
- Export the filtered view as CSV

## Out of scope
- Editing tickets
- Predicting resolution time
- Mobile-native application

4. The development lifecycle and feedback loops

4.1 A practical lifecycle

Most teams repeat a loop rather than follow a one-way waterfall:

  1. Discover the problem and constraints.
  2. Define a small outcome and acceptance criteria.
  3. Design the change and identify risks.
  4. Implement and test locally.
  5. Review and integrate continuously.
  6. Deploy safely.
  7. Observe real behavior and user feedback.
  8. Learn, adjust, and repeat.

4.2 Iterative and incremental are different

Incremental work adds usable slices. Iterative work improves a solution through feedback. Good delivery usually does both: release a thin usable path, then deepen it.

4.3 Choose process according to risk

SituationUseful approach
uncertain user needprototype and interview quickly
risky data migrationrehearsal, backup, verification, rollback
safety-critical behaviorformal review, traceability, stronger validation
mature routine servicesmall changes and automated delivery

5. Planning and decomposing work

5.1 Slice vertically

A vertical slice crosses the minimum UI, logic, and data layers needed to produce value. “Create all database tables” is a technical layer; “a user can create one task and see it after refresh” is a vertical slice.

5.2 Make tasks small and verifiable

Markdown
## Task: Persist a new task

Outcome:
A valid task submitted through the service is stored and assigned an ID.

Done when:
- validation rejects an empty title;
- repository integration test passes;
- the public service method is documented;
- no secret or local database file is committed.

5.3 Estimate uncertainty, not just effort

An estimate is a forecast based on current information. State assumptions and use ranges when uncertainty is high. A short investigation, or spike, can answer a focused technical question before the team commits to a design.

5.4 Define done

A shared definition of done might require code, automated tests, review, documentation, accessibility checks, security considerations, deployment readiness, and observable behavior. It prevents “coded” from being mistaken for “complete.”

6. Architecture and design basics

6.1 Separate responsibilities

A maintainable system groups related behavior and minimizes reasons for a module to change. One possible small-service structure is:

Text
task_app/
├── domain.py       # Task rules and states
├── service.py      # Use cases and orchestration
├── repository.py   # Persistence interface and implementation
├── api.py          # HTTP or CLI boundary
└── config.py       # Validated runtime settings

The domain should not know whether the boundary is a web API or command line. The service should not contain raw SQL. Boundaries make changes and tests easier.

6.2 Prefer explicit interfaces

An interface describes what a collaborator must do without forcing callers to know how it does it.

Python
from typing import Protocol

class TaskRepository(Protocol):
    def add(self, task: "Task") -> "Task": ...
    def get(self, task_id: int) -> "Task | None": ...

The same service can use an in-memory repository in tests and a database repository in production.

6.3 Model data and invariants

Python
from dataclasses import dataclass

@dataclass(frozen=True)
class Task:
    id: int | None
    title: str
    completed: bool = False

    def __post_init__(self) -> None:
        clean = self.title.strip()
        if not clean:
            raise ValueError("title cannot be empty")
        object.__setattr__(self, "title", clean)

An invariant is a rule that must always be true. Put important rules near the data they protect, not only in a UI form.

6.4 Record important decisions

An architecture decision record (ADR) captures context and trade-offs.

Markdown
# ADR-004: Use SQLite for the first local release

Status: Accepted

Context: The application is single-user, offline, and stores fewer than
100,000 tasks. The team needs transactions and simple backup.

Decision: Use SQLite behind a repository interface.

Consequences: Setup is small and tests are fast. A future multi-user release
may require PostgreSQL, but service code will not depend on SQLite directly.

6.5 Apply simple design principles carefully

  • Keep it simple: choose the least complex design that satisfies known needs.
  • YAGNI: do not build speculative flexibility without evidence.
  • DRY: remove duplicated knowledge, not every similar-looking line.
  • High cohesion: keep related behavior together.
  • Low coupling: minimize knowledge between modules.
  • Dependency inversion: core policy depends on interfaces, not infrastructure details.

7. Implementation fundamentals

7.1 Names communicate intent

Python
# Hard to understand
def calc(x, y):
    return x * (1 - y)

# Makes units and purpose visible
def discounted_price(price_cad: float, discount_rate: float) -> float:
    return price_cad * (1 - discount_rate)

Choose names from the problem domain. Include units where confusion is costly.

7.2 Functions should have a focused contract

Python
def normalize_email(value: str) -> str:
    """Return a normalized email or raise ValueError."""
    normalized = value.strip().casefold()
    if normalized.count("@") != 1:
        raise ValueError("email must contain exactly one @")
    return normalized

A useful contract explains inputs, outputs, side effects, and failure behavior. Type hints help tools and readers but do not replace runtime validation at system boundaries.

7.3 Handle errors at the right level

Python
class TaskNotFoundError(LookupError):
    pass

def complete_task(task_id: int, repository: TaskRepository) -> Task:
    task = repository.get(task_id)
    if task is None:
        raise TaskNotFoundError(f"task {task_id} does not exist")
    return repository.save_completed(task)

Do not silently catch an error that the current layer cannot resolve. Add context, preserve the cause, and translate technical failures into stable boundary responses.

7.4 Keep side effects at boundaries

Pure logic is easier to test than code that reads files, calls a network service, reads the clock, and changes global state. Pass dependencies into core logic when practical.

Python
from collections.abc import Callable
from datetime import datetime

def build_audit_message(action: str, now: Callable[[], datetime]) -> str:
    return f"{now().isoformat()} {action}"

8. Version control with Git

8.1 The core workflow

Terminal
git status
git switch -c feature/filter-overdue-tasks
git add src/task_app/service.py tests/test_service.py
git diff --cached
git commit -m "Add overdue task filter"
git push -u origin feature/filter-overdue-tasks

Inspect the staged diff before committing. A commit should be a coherent change that can be reviewed and, ideally, reverted independently.

8.2 Write useful commit messages

Text
Add overdue task filter

- validate team identifiers at the service boundary
- preserve stable ordering by due date
- cover empty and unknown-team cases

The subject explains the outcome in imperative form. The body explains why or highlights non-obvious decisions.

8.3 Ignore generated and sensitive files

gitignore
.venv/
__pycache__/
.pytest_cache/
.env
*.sqlite3
dist/
build/

.gitignore does not remove files already committed, and it is not a security control. If a secret is committed, rotate it and remove it from history according to the repository policy.

8.4 Pull requests are reviewable change proposals

A strong pull request is small, explains the user-visible outcome, lists important decisions, includes validation evidence, and calls out risk or migration needs. Review the behavior and design, not only formatting.

Markdown
## Summary
- add team filtering to overdue tasks
- preserve due-date order

## Validation
- unit and repository tests pass
- keyboard filter interaction checked

## Risk and rollback
- read-only query change; revert this PR to roll back

9. Environments, dependencies, configuration, and secrets

9.1 Isolate the environment

Terminal
python -m venv .venv

# Windows PowerShell
.venv\Scripts\Activate.ps1

# macOS or Linux
source .venv/bin/activate

python -m pip install -e ".[dev]"

Isolation prevents project packages from interfering with system Python or other projects.

9.2 Declare dependencies

toml
[project]
name = "task-app"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = []

[project.optional-dependencies]
dev = ["pytest>=8,<9", "ruff>=0.6,<1"]

[tool.pytest.ini_options]
testpaths = ["tests"]

Applications usually pin reproducible resolved versions in a lock file. Libraries generally declare compatible ranges and test supported combinations.

9.3 Separate configuration from code

Python
import os
from dataclasses import dataclass

@dataclass(frozen=True)
class Settings:
    database_url: str
    log_level: str = "INFO"

    @classmethod
    def from_environment(cls) -> "Settings":
        url = os.environ.get("TASK_DATABASE_URL")
        if not url:
            raise RuntimeError("TASK_DATABASE_URL is required")
        return cls(database_url=url, log_level=os.getenv("LOG_LEVEL", "INFO"))

Validate configuration at startup so deployment errors fail early and clearly.

9.4 Keep secrets out of source control

Use the platform's secret manager or protected environment variables. Never place production passwords, API keys, signing keys, or personal tokens in source files, examples, logs, or screenshots.

10. Testing strategy

10.1 Test behavior at multiple levels

Test levelFocusTypical speedCommon failure found
Unitone function or objectvery fastlogic and edge cases
Integrationcomponents togethermediumdatabase, file, protocol mismatch
End-to-enduser workflowslowerwiring and deployment problems
Contractservice boundarymediumincompatible request/response changes
Non-functionalquality attributevariesperformance, security, accessibility

Prefer many focused unit tests, enough integration tests to cover real boundaries, and a small set of critical end-to-end journeys.

10.2 Use Arrange–Act–Assert

Python
def test_task_trims_title() -> None:
    task = Task(id=None, title="  write tests  ")

    actual = task.title

    assert actual == "write tests"

Test names should state behavior. Avoid tests that merely repeat the implementation.

10.3 Cover boundaries and invalid input

Python
import pytest

@pytest.mark.parametrize("title", ["", " ", "\t\n"])
def test_task_rejects_blank_title(title: str) -> None:
    with pytest.raises(ValueError, match="title cannot be empty"):
        Task(id=None, title=title)

Important cases often live at zero, one, maximum size, missing values, duplicates, time boundaries, and permission boundaries.

10.4 Test through public behavior

Python
def test_create_task_persists_valid_task() -> None:
    repository = InMemoryTaskRepository()
    service = TaskService(repository)

    created = service.create("Review pull request")

    assert created.id is not None
    assert repository.get(created.id) == created

Over-mocking internal calls makes tests fragile. Prefer simple fakes at architectural boundaries and assert observable outcomes.

10.5 A test must be trustworthy

Tests should be deterministic, isolated, readable, fast enough for their level, and able to fail for the right reason. Quarantine is not a permanent solution for flaky tests; find and fix the uncontrolled dependency.

Terminal
python -m pytest
python -m pytest tests/test_service.py -q
python -m pytest --maxfail=1

11. Debugging and observability

11.1 Debug with a hypothesis

Use a repeatable method:

  1. Reproduce the failure with the smallest known input.
  2. Write down expected and actual behavior.
  3. Identify the first point where they diverge.
  4. Form one testable hypothesis.
  5. Gather evidence with a test, debugger, log, or inspection.
  6. Fix the cause, not only the symptom.
  7. Add a regression test.

11.2 Preserve useful context

Python
import logging

logger = logging.getLogger(__name__)

def load_task(task_id: int, repository: TaskRepository) -> Task:
    try:
        task = repository.get(task_id)
    except OSError as exc:
        logger.exception("task repository read failed", extra={"task_id": task_id})
        raise RuntimeError("could not load task") from exc
    if task is None:
        raise TaskNotFoundError(str(task_id))
    return task

Log identifiers and state needed for diagnosis, but never secrets or unnecessary personal data.

11.3 Logs, metrics, and traces answer different questions

SignalBest for
Logsdetailed events and error context
Metricstrends, rates, percentiles, alerting
Tracesrequest flow across services
Python
logger.info(
    "task completed",
    extra={"task_id": task.id, "actor_type": "user", "duration_ms": 18},
)

Design observability as part of the feature. Ask what an operator will need at 2 a.m. to distinguish user error, dependency failure, and a code defect.

12. Code quality, refactoring, and review

12.1 Automate mechanical checks

Terminal
ruff check .
ruff format --check .
python -m pytest

Formatters, linters, type checkers, and tests make standards repeatable. Human review can then focus on behavior, design, security, and maintainability.

12.2 Refactor without changing behavior

Python
# Before: business rules are hidden in a dense expression.
def can_close(user, task):
    return user.active and (user.admin or task.owner_id == user.id) and not task.locked
Python
# After: names explain the policy.
def can_close_task(user: "User", task: Task) -> bool:
    owns_task = task.owner_id == user.id
    has_permission = user.is_admin or owns_task
    return user.is_active and has_permission and not task.is_locked

Refactor in small steps with tests passing. Do not combine a broad cleanup and a behavior change unless they cannot be reviewed separately.

12.3 Review the right things

A reviewer should ask:

  • Does the change satisfy the acceptance criteria?
  • Are important edge cases and failures handled?
  • Is the design simpler than plausible alternatives?
  • Are data, security, compatibility, and operational risks addressed?
  • Do tests prove behavior rather than implementation details?
  • Can another maintainer understand the change?

Review comments should explain impact and invite discussion. Distinguish blocking correctness issues from optional suggestions.

13. APIs, data, and compatibility

13.1 Treat interfaces as contracts

json
{
  "id": 42,
  "title": "Review pull request",
  "completed": false,
  "version": 1
}

An API contract includes field meaning, types, required values, errors, authorization, idempotency, ordering, pagination, and compatibility policy—not only a URL.

13.2 Validate at trust boundaries

Python
def parse_page_size(raw: str | None) -> int:
    if raw is None:
        return 25
    try:
        size = int(raw)
    except ValueError as exc:
        raise ValueError("page size must be an integer") from exc
    if not 1 <= size <= 100:
        raise ValueError("page size must be between 1 and 100")
    return size

Validate requests, file uploads, external service responses, database records crossing versions, and deserialized messages.

13.3 Evolve data safely

sql
ALTER TABLE tasks ADD COLUMN completed_at TEXT NULL;

CREATE INDEX idx_tasks_completed_at
ON tasks(completed_at);

For risky migrations, use expand–migrate–contract: add a compatible shape, deploy code that handles both forms, backfill and verify data, then remove the old shape later. Always define backup, rollback, and verification steps.

13.4 Preserve backward compatibility intentionally

Additive changes are often safer than renaming or removing fields, but even additions can break strict clients. Version public contracts when necessary and publish deprecation timelines.

14. Security and privacy fundamentals

14.1 Use a threat-oriented mindset

Ask what assets matter, who might misuse the system, which entry points exist, what trust boundaries are crossed, and how an incident would be detected and contained.

14.2 Essential practices

  • Apply least privilege to users, services, databases, and CI jobs.
  • Authenticate identity and authorize every protected action.
  • Use parameterized queries; never construct SQL from raw input.
  • Escape output for its context and protect against cross-site scripting.
  • Protect state-changing web requests against cross-site request forgery.
  • Encrypt sensitive data in transit and, where required, at rest.
  • Patch dependencies and remove unused ones.
  • Rate-limit abuse-prone operations.
  • Avoid exposing internal errors to users.
  • Collect only necessary personal data and define retention rules.
Python
# Parameterized query: values are not interpreted as SQL syntax.
cursor.execute(
    "SELECT id, title FROM tasks WHERE owner_id = ?",
    (owner_id,),
)

14.3 Never invent cryptography or password storage

Use established platform libraries and current organizational guidance for password hashing, tokens, encryption, and key rotation. Security-sensitive implementation details change; verify them against authoritative, current documentation.

14.4 Handle a leaked secret as an incident

Remove public exposure, rotate or revoke the credential, inspect access logs, assess impact, update affected deployments, then clean repository history if policy requires it. Deleting the visible line alone is insufficient.

15. Continuous integration, delivery, and releases

15.1 CI provides fast shared evidence

YAML
name: quality

on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: python -m pip install -e ".[dev]"
      - run: ruff check .
      - run: python -m pytest

Pin actions and permissions according to current repository security policy. CI should start quickly, report clear failures, and reproduce local quality checks.

15.2 Continuous delivery versus deployment

Continuous delivery keeps every accepted change releasable but may require a manual production decision. Continuous deployment automatically releases each accepted change. Neither is a substitute for tests, monitoring, or rollback.

15.3 Use semantic versions when they fit

Text
MAJOR.MINOR.PATCH

2.0.0  incompatible public change
1.4.0  backward-compatible capability
1.4.3  backward-compatible fix

Version policy must define what the team considers a public interface.

15.4 Release safely

Useful techniques include feature flags, canary releases, blue-green deployment, backward-compatible migrations, automated health checks, and one-command rollback. A release plan should name the owner, validation signal, abort threshold, and recovery action.

16. Reliability and performance

16.1 Design for failure

Networks time out, disks fill, processes restart, messages duplicate, and dependencies become slow. Decide which operations may retry, which must be idempotent, and what partial failure means.

Python
import time
from collections.abc import Callable

def retry(operation: Callable[[], str], attempts: int = 3) -> str:
    delay = 0.1
    for attempt in range(attempts):
        try:
            return operation()
        except TimeoutError:
            if attempt == attempts - 1:
                raise
            time.sleep(delay)
            delay *= 2
    raise AssertionError("unreachable")

Retry only transient failures, use bounded attempts and timeouts, and consider jitter. A retry can amplify an overloaded dependency or repeat a non-idempotent action.

16.2 Define service objectives

An indicator is a measurement, such as successful-request rate. An objective is a target, such as 99.9% successful requests over 30 days. An agreement is an external commitment. Objectives help teams balance reliability and delivery speed.

16.3 Measure performance before optimizing

Python
from time import perf_counter

started = perf_counter()
result = build_report(records)
elapsed_ms = (perf_counter() - started) * 1000
print(f"build_report took {elapsed_ms:.1f} ms")

Use representative data and measure latency distributions, throughput, memory, database queries, and external calls. Optimize the proven bottleneck, then measure again.

16.4 Capacity and graceful degradation

Plan expected load, peaks, storage growth, rate limits, and dependency limits. When a non-critical dependency fails, a cached or reduced response may be better than total failure—if the user can see that data may be stale.

17. Collaboration and documentation

17.1 Communication is part of the system

Source code captures implementation, not every decision or operational fact. Teams need lightweight, current artifacts: README, setup guide, contribution rules, ADRs, API contracts, runbooks, release notes, and incident reviews.

17.2 A useful README

Markdown
# Task App

## Purpose
Manage a personal task list locally.

## Quick start
1. Create and activate `.venv`.
2. Run `python -m pip install -e ".[dev]"`.
3. Run `python -m task_app add "Write tests"`.

## Quality checks
`ruff check .` and `python -m pytest`

Domain rules are isolated from CLI and persistence adapters.

18.2 Domain model

Python
from dataclasses import dataclass, replace

@dataclass(frozen=True)
class Task:
    id: int | None
    title: str
    completed: bool = False

    def __post_init__(self) -> None:
        clean = self.title.strip()
        if not clean:
            raise ValueError("title cannot be empty")
        object.__setattr__(self, "title", clean)

    def complete(self) -> "Task":
        return replace(self, completed=True)

18.3 Repository and in-memory adapter

Python
from typing import Protocol

class TaskRepository(Protocol):
    def add(self, task: Task) -> Task: ...
    def list_all(self) -> list[Task]: ...
    def replace(self, task: Task) -> Task: ...

class InMemoryTaskRepository:
    def __init__(self) -> None:
        self._items: dict[int, Task] = {}
        self._next_id = 1

    def add(self, task: Task) -> Task:
        saved = Task(self._next_id, task.title, task.completed)
        self._items[self._next_id] = saved
        self._next_id += 1
        return saved

    def list_all(self) -> list[Task]:
        return list(self._items.values())

    def replace(self, task: Task) -> Task:
        if task.id is None or task.id not in self._items:
            raise LookupError("task does not exist")
        self._items[task.id] = task
        return task

18.4 Service layer

Python
class TaskService:
    def __init__(self, repository: TaskRepository) -> None:
        self._repository = repository

    def create(self, title: str) -> Task:
        return self._repository.add(Task(id=None, title=title))

    def list_tasks(self, include_completed: bool = True) -> list[Task]:
        tasks = self._repository.list_all()
        if include_completed:
            return tasks
        return [task for task in tasks if not task.completed]

    def complete(self, task_id: int) -> Task:
        matches = [task for task in self._repository.list_all() if task.id == task_id]
        if not matches:
            raise LookupError(f"task {task_id} does not exist")
        return self._repository.replace(matches[0].complete())

18.5 Tests

def test_create_and_complete_task() -> None:
    repository = InMemoryTaskRepository()
    service = TaskService(repository)

    created = service.create("  Ship a small feature  ")
    completed = service.complete(created.id)

    assert created.title == "Ship a small feature"
    assert completed.completed is True
    assert service.list_tasks(include_completed=False) == []

18.7 A safe implementation sequence

  1. Write acceptance criteria for create, list, and complete.
  2. Implement the immutable domain object and its tests.
  3. Define the repository protocol and in-memory adapter.
  4. Add service behavior and tests.
  5. Add a thin CLI boundary.
  6. Add SQLite behind the same repository interface.
  7. Add integration tests with a temporary database.
  8. Add CI, documentation, packaging, and release notes.

Each step should leave the project usable and tests green.

19. Practical checklists

Before implementation

  • Is the user problem and desired outcome clear?
  • Are acceptance criteria observable and testable?
  • Are scope, constraints, dependencies, and risks explicit?
  • Is there a smaller vertical slice?
  • Do data, security, accessibility, and migration need special review?

Before opening a pull request

  • Does the change do only what the description claims?
  • Are names, interfaces, errors, and tests understandable?
  • Did you inspect the staged diff for generated files and secrets?
  • Do local quality checks pass?
  • Are operational, compatibility, and rollback notes included?

Before release

  • Did CI pass for the exact commit being released?
  • Are configuration and secrets available in the target environment?
  • Are migrations backward-compatible and backed up?
  • Are health signals, alert thresholds, owner, and rollback ready?
  • Is user-facing and operator documentation current?

After release

  • Verify critical user journeys and system health.
  • Compare key metrics with the baseline.
  • Watch errors, latency, saturation, and support feedback.
  • Record unexpected behavior and follow-up work.
  • Remove temporary flags only after the change is stable.

21. A 30-day learning plan

Week 1: fundamentals and Git

Build a command-line program with small functions. Use a virtual environment, meaningful commits, a README, formatting, and linting. Practice reading diffs and reverting a commit.

Week 2: design and testing

Separate domain logic from input/output. Add unit tests for normal and boundary cases, an integration test for persistence, and a small ADR for one design decision.

Week 3: delivery and operation

Add CI, structured logs, configuration validation, a health check, and a release checklist. Practice a failed deployment and rollback in a safe environment.

Week 4: collaboration and improvement

Open small pull requests, review someone else's change, measure one performance path, perform a basic threat review, and write a short retrospective based on evidence.

22. Exercises

  1. Rewrite a vague feature request as a problem statement, user story, three acceptance criteria, and an out-of-scope list.
  2. Draw the boundary diagram for an application you use. Identify UI, core logic, data storage, and external services.
  3. Add a due date to the task capstone. Define time-zone rules before coding.
  4. Replace the in-memory repository with SQLite and add integration tests using a temporary database.
  5. Introduce a failure, reproduce it with a test, fix it, and document the debugging hypothesis.
  6. Add a GitHub Actions workflow that runs linting and tests on pull requests.
  7. Write an ADR comparing two persistence options.
  8. Threat-model the create-task operation: assets, actors, entry points, abuse cases, controls, and detection.
  9. Define two service indicators and one objective for a web version of the task app.
  10. Review a recent project using the pre-implementation, pull request, and release checklists.
