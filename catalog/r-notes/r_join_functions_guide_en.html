How to use this guide

A join combines related records from two tables. The syntax is easy; the hard part is deciding what constitutes a match and proving that the result still represents the intended entities.

This guide starts with the seven functions in the overview image, then moves to the details that make joins safe in real analysis:

  • primary, foreign, and compound keys;
  • one-to-one, one-to-many, many-to-one, and many-to-many relationships;
  • duplicate and missing keys;
  • equality, inequality, rolling, and interval overlap conditions;
  • validation before and after the join;
  • equivalent base R and data.table patterns.

Throughout the dplyr sections, x means the left table and y means the right table.

The seven core joins

Function Meaning Rows retained Adds columns from y?
left_join() left outer join all x; every matching y row yes
inner_join() inner join only x rows with a match in y yes
full_join() full outer join all rows represented by x or y yes
right_join() right outer join all y; every matching x row yes
semi_join() existence filter x rows having at least one match in y no
anti_join() non-existence filter x rows having no match in y no
cross_join() Cartesian product every x–y combination yes

The most important distinction is between mutating joins and filtering joins:

  • left_join(), inner_join(), right_join(), and full_join() add columns and may add rows;
  • semi_join() and anti_join() only filter rows of x; they never add columns from y;
  • cross_join() deliberately generates all combinations.

Part I — Relational foundations

1. Keys identify and connect records

A key is one or more columns used to identify a record or relate two tables.

  • A primary key uniquely identifies each row in its own table.
  • A foreign key points to a key in another table.
  • A compound key uses several columns together, such as store_id plus date.
library(dplyr)

customers <- tibble(
  customer_id = c("C01", "C02", "C03", "C04"),
  customer_name = c("Ada", "Grace", "Linus", "Margaret"),
  region = c("West", "East", "West", "North")
)

orders <- tibble(
  order_id = c("O100", "O101", "O102", "O103", "O104"),
  customer_id = c("C01", "C02", "C01", "C05", NA),
  amount = c(120, 75, 180, 60, 45)
)

Here customers$customer_id is intended to be a primary key. orders$customer_id is a foreign key, but it contains both an unknown customer (C05) and a missing value.

Never assume a candidate key is unique. Test it:

customers |>
  count(customer_id, name = "n") |>
  filter(n > 1)

# Base R equivalent: 0 means no duplicate key was found.
anyDuplicated(customers$customer_id)

For a compound key:

daily_inventory <- tibble(
  store_id = c(1, 1, 2, 2),
  date = as.Date(c("2026-08-01", "2026-08-02", "2026-08-01", "2026-08-02")),
  units = c(30, 27, 18, 22)
)

daily_inventory |>
  count(store_id, date) |>
  filter(n > 1)

2. Cardinality predicts row multiplication

Cardinality describes how many records on one side can match a record on the other side.

Relationship Meaning Typical example
one-to-one each key appears at most once in both tables customer to customer profile
one-to-many one x row may match many y rows customer to orders
many-to-one many x rows may match one y row orders to customer
many-to-many repeated keys occur on both sides students to courses through enrollment

If one x key occurs twice and the same y key occurs three times, an equality join produces 2 × 3 = 6 matched rows for that key.

x_dup <- tibble(id = c(1, 1), x_value = c("x1", "x2"))
y_dup <- tibble(id = c(1, 1, 1), y_value = c("y1", "y2", "y3"))

x_dup |>
  left_join(y_dup, by = join_by(id), relationship = "many-to-many")
# Six rows are expected.

A many-to-many relationship is not automatically wrong. It is wrong when the data model did not intend it. Explicit junction tables are usually clearer:

students <- tibble(student_id = c(1, 2), name = c("A", "B"))
courses <- tibble(course_id = c("R", "SQL"), title = c("R", "Databases"))
enrollment <- tibble(
  student_id = c(1, 1, 2),
  course_id = c("R", "SQL", "R")
)

enrollment converts one conceptual many-to-many relation into two explicit one-to-many relations.

3. Start with a join contract

Before writing code, state the contract in plain language:

Each order must retain exactly one row. A non-missing customer_id should match at most one customer. Unknown customer IDs are allowed temporarily and must be reported.

That contract implies:

  1. orders is the left table because every order must remain;
  2. the expected relationship is many orders to one customer;
  3. left_join() is appropriate;
  4. relationship = "many-to-one" should be enforced;
  5. an anti_join() audit should report unknown IDs.
unknown_customer_ids <- orders |>
  filter(!is.na(customer_id)) |>
  anti_join(customers, by = join_by(customer_id))

enriched_orders <- orders |>
  left_join(
    customers,
    by = join_by(customer_id),
    relationship = "many-to-one",
    na_matches = "never"
  )

The function follows from the contract—not the other way around.

Part II — Equality joins with dplyr

4. Always specify by in maintained code

If by = NULL, dplyr performs a natural join using all column names shared by both tables. It prints a message, but a future shared column can silently change the match condition.

Prefer an explicit specification:

orders |>
  left_join(customers, by = join_by(customer_id))

Equivalent character syntax remains useful for simple equality joins:

orders |>
  left_join(customers, by = "customer_id")

When key names differ:

customer_lookup <- customers |>
  rename(id = customer_id)

orders |>
  left_join(customer_lookup, by = join_by(customer_id == id))

# Older named-character style:
orders |>
  left_join(customer_lookup, by = c("customer_id" = "id"))

For compound keys:

sales <- tibble(
  store_id = c(1, 1, 2),
  date = as.Date(c("2026-08-01", "2026-08-02", "2026-08-01")),
  revenue = c(500, 620, 410)
)

sales |>
  left_join(
    daily_inventory,
    by = join_by(store_id, date),
    relationship = "one-to-one"
  )

5. left_join(): preserve the left entity

left_join(x, y) keeps every row of x, adds non-key columns from y, and fills unmatched values with NA.

orders |>
  left_join(
    customers,
    by = join_by(customer_id),
    relationship = "many-to-one",
    na_matches = "never"
  )

Use a left join when x defines the population under study: transactions, patients, survey responses, or events.

A left join does not guarantee one output row per input row. If one row in x matches several rows in y, it is repeated. Enforce cardinality or check row counts:

before_n <- nrow(orders)

result <- orders |>
  left_join(customers, by = join_by(customer_id), relationship = "many-to-one")

stopifnot(nrow(result) == before_n)

unmatched = "error" on a left join protects unmatched keys in y that would be dropped; it does not report unmatched x rows because those rows remain. Use anti_join(x, y) to audit unmatched left-side keys.

6. inner_join(): retain only matched records

inner_join() returns only matched x rows and adds columns from y. Unmatched rows from either input disappear.

matched_orders <- orders |>
  inner_join(
    customers,
    by = join_by(customer_id),
    relationship = "many-to-one",
    na_matches = "never"
  )

An inner join is useful when matching is the definition of the analytical population. It is risky as a casual lookup because data can disappear silently.

Audit both directions before dropping:

orders_without_customer <- orders |>
  anti_join(customers, by = join_by(customer_id), na_matches = "never")

customers_without_orders <- customers |>
  anti_join(orders, by = join_by(customer_id), na_matches = "never")

For strict pipelines, unmatched = "error" can reject keys that would be discarded:

# Will error with the example data because unmatched keys exist.
try(
  inner_join(
    orders,
    customers,
    by = join_by(customer_id),
    unmatched = "error",
    na_matches = "never"
  )
)

7. full_join(): reconcile both universes

full_join() keeps all keys represented in either table. Unmatched fields on the opposite side become NA.

crm <- tibble(
  customer_id = c("C01", "C02", "C03"),
  crm_status = c("active", "active", "inactive")
)

billing <- tibble(
  customer_id = c("C01", "C02", "C04"),
  balance = c(0, 25, 90)
)

reconciliation <- crm |>
  full_join(
    billing,
    by = join_by(customer_id),
    relationship = "one-to-one"
  ) |>
  mutate(
    presence = case_when(
      !is.na(crm_status) & !is.na(balance) ~ "both",
      !is.na(crm_status) ~ "crm_only",
      TRUE ~ "billing_only"
    )
  )

Full joins are excellent for reconciliation and coverage reports. They are less convenient for routine enrichment because they change the population to the union of both tables.

8. right_join(): preserve the right table

right_join(x, y) keeps every row of y. It is the directional mirror of a left join:

customers |>
  right_join(orders, by = join_by(customer_id), na_matches = "never")

# Often easier to read:
orders |>
  left_join(customers, by = join_by(customer_id), na_matches = "never")

Right joins are valid, but many teams prefer to swap inputs and use left_join() so the preserved table appears first in the pipeline. Use whichever makes the data contract clearest.

9. semi_join(): filter by existence

semi_join(x, y) returns rows of x having at least one match in y. It adds no columns from y and never duplicates x rows because of repeated keys in y.

customers_with_orders <- customers |>
  semi_join(orders, by = join_by(customer_id), na_matches = "never")

This is the relational equivalent of an existence test. It is safer than inner_join() followed by select() when only filtering is intended.

Useful examples:

priority_ids <- tibble(customer_id = c("C01", "C04"))

priority_customers <- customers |>
  semi_join(priority_ids, by = join_by(customer_id))

10. anti_join(): find missing relationships

anti_join(x, y) returns rows of x having no match in y. It is one of the most useful data-quality functions in R.

orphan_orders <- orders |>
  anti_join(customers, by = join_by(customer_id), na_matches = "never")

Use it to detect:

  • foreign keys missing from a dimension table;
  • records not processed by a pipeline;
  • expected categories absent from a reference table;
  • differences between system extracts;
  • IDs requiring manual review.
stopifnot(
  nrow(
    orders |>
      filter(!is.na(customer_id)) |>
      anti_join(customers, by = join_by(customer_id))
  ) == 0L
)

The assertion intentionally fails for the example because C05 is unknown.

11. cross_join(): every possible combination

cross_join(x, y) returns nrow(x) * nrow(y) rows.

products <- tibble(product = c("A", "B", "C"))
scenarios <- tibble(discount = c(0, 0.10, 0.20))

scenario_grid <- products |>
  cross_join(scenarios)

stopifnot(nrow(scenario_grid) == nrow(products) * nrow(scenarios))

Cross joins are useful for parameter grids, complete panels, test cases, and all pairwise combinations. They are dangerous when accidental:

expected_rows <- as.double(nrow(products)) * nrow(scenarios)
if (expected_rows > 1e6) {
  stop("Cross join would create too many rows: ", expected_rows)
}

Do not simulate a cross join with a dummy constant key in new dplyr code; cross_join() makes the intent explicit.

Part III — Join safety and output control

12. Enforce relationship

Mutating joins accept a relationship expectation:

orders |>
  left_join(
    customers,
    by = join_by(customer_id),
    relationship = "many-to-one"
  )

The choices are:

  • "one-to-one": both sides match at most one row;
  • "one-to-many": each y row matches at most one x row;
  • "many-to-one": each x row matches at most one y row;
  • "many-to-many": explicitly accept unrestricted multiplicity.

For equality joins, dplyr warns about an unexpected many-to-many relationship by default. In production code, declaring the expected relationship turns structural assumptions into executable checks.

Do not add relationship = "many-to-many" merely to silence a warning. First inspect duplicate keys on both sides:

x_duplicates <- x_dup |> count(id) |> filter(n > 1)
y_duplicates <- y_dup |> count(id) |> filter(n > 1)

13. Control multiple matches

For each row of x, multiple controls what happens when several y rows match:

  • "all" returns every match and follows SQL semantics;
  • "any" returns one unspecified match;
  • "first" returns the first detected match;
  • "last" returns the last detected match.
customer_status <- tibble(
  customer_id = c("C01", "C01", "C02"),
  status_date = as.Date(c("2026-01-01", "2026-07-01", "2026-05-01")),
  status = c("new", "active", "active")
)

orders |>
  left_join(
    customer_status,
    by = join_by(customer_id),
    multiple = "all"
  )

If “latest status” has semantic meaning, do not rely on incidental row order and multiple = "last". Make the selection deterministic first:

latest_status <- customer_status |>
  group_by(customer_id) |>
  slice_max(status_date, n = 1, with_ties = FALSE) |>
  ungroup()

orders |>
  left_join(
    latest_status,
    by = join_by(customer_id),
    relationship = "many-to-one"
  )

14. Understand unmatched

unmatched = "error" protects rows that the join type could discard:

  • left join checks unmatched y keys;
  • right join checks unmatched x keys;
  • inner join checks both inputs;
  • full join drops neither side, so there is no equivalent loss to protect.

It does not replace an anti_join() audit. For left joins, unmatched x rows remain and therefore must be diagnosed separately if missing lookups are not allowed.

15. Decide whether missing keys match

For local data frames, dplyr’s default na_matches = "na" treats two NA values as matching. Many databases use SQL NULL semantics, where missing values do not match.

x_na <- tibble(id = c(1, NA), x_value = c("known", "missing"))
y_na <- tibble(id = c(1, NA), y_value = c("one", "unknown"))

x_na |>
  left_join(y_na, by = join_by(id), na_matches = "na")

x_na |>
  left_join(y_na, by = join_by(id), na_matches = "never")

For identifiers, na_matches = "never" is usually safer: two unknown IDs are not evidence that the records belong together. For analytical values, matching missing values may occasionally be intentional, but document that choice.

16. Resolve column-name conflicts

When non-key columns share a name, dplyr adds suffixes:

x_profile <- tibble(customer_id = "C01", status = "active")
y_profile <- tibble(customer_id = "C01", status = "verified")

x_profile |>
  left_join(
    y_profile,
    by = join_by(customer_id),
    suffix = c("_crm", "_kyc")
  )

Prefer meaningful suffixes over .x and .y in final datasets. If two columns represent the same concept, reconcile them explicitly:

joined_profile <- x_profile |>
  full_join(
    y_profile,
    by = join_by(customer_id),
    suffix = c("_crm", "_kyc")
  ) |>
  mutate(
    status_agrees = status_crm == status_kyc
  )

Keep both key columns

For differently named equality keys, dplyr normally coalesces the key into the x key column. Use keep = TRUE to retain both:

orders |>
  left_join(
    customer_lookup,
    by = join_by(customer_id == id),
    keep = TRUE
  )

Keeping both keys is useful during reconciliation because mismatches and missing values remain visible.

17. Validate key types before joining

Keys that look identical may have incompatible types or formats:

left_ids <- tibble(id = c("001", "002"))
right_ids <- tibble(id = c(1L, 2L))

Do not blindly convert character identifiers to numbers; leading zeros may carry meaning. Define a canonical representation:

right_ids_clean <- right_ids |>
  mutate(id = sprintf("%03d", id))

left_ids |>
  left_join(right_ids_clean, by = join_by(id), relationship = "one-to-one")

Also normalize whitespace, case, encodings, date classes, and time zones before joining. Avoid approximate matching until deterministic normalization has been exhausted.

Part IV — Advanced join_by() conditions

18. Equality joins with explicit table references

Inside join_by(), the left side normally refers to x and the right side to y. x$ and y$ prefixes can remove ambiguity:

orders |>
  left_join(
    customer_lookup,
    by = join_by(x$customer_id == y$id)
  )

Supported expressions are deliberately restricted to equality, inequalities, closest(), and overlap helpers. Precompute transformations before the join:

orders_clean <- orders |>
  mutate(customer_key = toupper(trimws(customer_id)))

customers_clean <- customers |>
  mutate(customer_key = toupper(trimws(customer_id)))

orders_clean |>
  left_join(customers_clean, by = join_by(customer_key))

Do not put arbitrary calculations such as join_by(toupper(id) == id) inside the specification.

19. Inequality joins

Inequality joins match using <, <=, >, or >=. A typical example assigns transactions to value tiers:

transactions <- tibble(
  transaction_id = 1:5,
  amount = c(25, 80, 150, 400, 900)
)

tiers <- tibble(
  tier = c("small", "medium", "large"),
  lower = c(0, 100, 500),
  upper = c(100, 500, Inf)
)

transactions |>
  left_join(
    tiers,
    by = join_by(amount >= lower, amount < upper),
    relationship = "many-to-one"
  )

A single row may match many rows in an inequality join, so badly defined or overlapping ranges can create a large result. Validate range ordering and overlap:

stopifnot(all(tiers$lower < tiers$upper))
stopifnot(all(head(tiers$upper, -1) <= tail(tiers$lower, -1)))

20. Rolling joins with closest()

A rolling join chooses the nearest match satisfying an inequality. It is ideal for “as-of” questions such as finding the most recent price effective at a transaction time.

price_history <- tibble(
  product_id = c("A", "A", "A", "B", "B"),
  effective_date = as.Date(c(
    "2026-01-01", "2026-03-01", "2026-07-01",
    "2026-02-01", "2026-06-01"
  )),
  price = c(10, 11, 12, 20, 22)
)

sales_events <- tibble(
  sale_id = 1:4,
  product_id = c("A", "A", "B", "B"),
  sale_date = as.Date(c("2026-02-10", "2026-08-01", "2026-05-01", "2026-07-01"))
)

sales_events |>
  left_join(
    price_history,
    by = join_by(product_id, closest(sale_date >= effective_date)),
    relationship = "many-to-one"
  )

For each sale, closest(sale_date >= effective_date) finds the latest effective date not after the sale. Check what should happen before the first known price and when effective dates are duplicated.

21. Point-in-range joins with between()

Use between() when a point from x should fall inside a range from y:

campaigns <- tibble(
  campaign = c("spring", "summer"),
  start = as.Date(c("2026-03-01", "2026-06-01")),
  end = as.Date(c("2026-05-31", "2026-08-31"))
)

events <- tibble(
  event_id = 1:4,
  event_date = as.Date(c("2026-02-20", "2026-03-15", "2026-06-01", "2026-09-01"))
)

events |>
  left_join(
    campaigns,
    by = join_by(between(event_date, start, end, bounds = "[]"))
  )

Bounds may be closed or open: "[]", "[)", "(]", or "()". For adjacent time intervals, half-open bounds such as "[)" often prevent a boundary point from matching twice.

22. Range containment and overlap

within() finds a range from x completely contained in a range from y. overlaps() finds any overlap.

observed_intervals <- tibble(
  chromosome = c("chr1", "chr1", "chr2"),
  start = c(100, 250, 50),
  end = c(180, 310, 90)
)

reference_regions <- tibble(
  chromosome = c("chr1", "chr1", "chr2"),
  ref_start = c(90, 200, 70),
  ref_end = c(160, 280, 120),
  region = c("R1", "R2", "R3")
)

observed_intervals |>
  inner_join(
    reference_regions,
    by = join_by(
      chromosome,
      overlaps(start, end, ref_start, ref_end, bounds = "[]")
    )
  )

observed_intervals |>
  inner_join(
    reference_regions,
    by = join_by(chromosome, within(start, end, ref_start, ref_end))
  )

Overlap joins are often naturally many-to-many. Estimate result size and state how boundary touching should be interpreted.

Part V — Related dplyr tools

23. nest_join(): keep matches in a list-column

nest_join() leaves x almost unchanged and adds a list-column containing all matching rows from y.

customers_nested <- customers |>
  nest_join(
    orders,
    by = join_by(customer_id),
    name = "orders",
    na_matches = "never"
  )

customers_nested |>
  mutate(order_count = lengths(orders))

This avoids immediately expanding one-to-many matches. It is useful for per-entity models, reports, or later summaries. A zero-match row receives an empty nested table, not a missing scalar.

24. rows_*() verbs modify records by key

These are not ordinary joins, but they use keys to apply database-like row operations:

  • rows_insert() adds new keys and normally errors on conflicts;
  • rows_append() appends without key matching;
  • rows_update() replaces columns in matching rows;
  • rows_patch() replaces only missing values in matching rows;
  • rows_upsert() updates existing keys and inserts new keys;
  • rows_delete() removes matching keys.
master <- tibble(
  id = c(1, 2),
  status = c("active", NA),
  score = c(10, 20)
)

updates <- tibble(
  id = c(2, 3),
  status = c("active", "new"),
  score = c(25, 30)
)

master |>
  rows_upsert(updates, by = "id")

master |>
  rows_patch(tibble(id = 2, status = "active"), by = "id")

Use these verbs when the business operation is insert/update/delete, not merely combine columns.

25. Set operations are not joins

intersect(), union(), union_all(), setdiff(), and setequal() compare whole rows with compatible columns. They do not match a chosen key and append columns.

expected_ids <- tibble(customer_id = c("C01", "C02", "C03"))
observed_ids <- tibble(customer_id = c("C01", "C02", "C04"))

setdiff(expected_ids, observed_ids)
intersect(expected_ids, observed_ids)
union(expected_ids, observed_ids)

Use set operations for row-set questions and joins for relational key questions.

Part VI — base R joins

26. merge() equivalents

Base R’s merge() covers inner and outer equality joins.

customers_df <- as.data.frame(customers)
orders_df <- as.data.frame(orders)

# Inner join
merge(orders_df, customers_df, by = "customer_id", all = FALSE)

# Left join
merge(orders_df, customers_df, by = "customer_id", all.x = TRUE)

# Right join
merge(orders_df, customers_df, by = "customer_id", all.y = TRUE)

# Full join
merge(orders_df, customers_df, by = "customer_id", all = TRUE)

Different key names use by.x and by.y:

merge(
  orders_df,
  as.data.frame(customer_lookup),
  by.x = "customer_id",
  by.y = "id",
  all.x = TRUE
)

Important differences from dplyr include:

  • merge() sorts by key by default; use sort = FALSE when appropriate, but do not rely on unspecified order;
  • suffixes = c(".x", ".y") controls conflicting non-key columns;
  • all possible duplicate-key matches are returned;
  • base R does not provide dplyr’s relationship checks;
  • incomparables = NA prevents missing keys from matching in a one-column merge.
merge(
  as.data.frame(x_na),
  as.data.frame(y_na),
  by = "id",
  all.x = TRUE,
  incomparables = NA
)

27. Cartesian, semi, and anti patterns in base R

An explicit zero-length by creates a Cartesian product:

merge(
  as.data.frame(products),
  as.data.frame(scenarios),
  by = NULL
)

For a single key, %in% can express semi and anti filters:

customers_df[customers_df$customer_id %in% orders_df$customer_id, , drop = FALSE]

orders_df[!orders_df$customer_id %in% customers_df$customer_id, , drop = FALSE]

For compound keys, missing-value policies, and classed tables, explicit dplyr joins or a carefully constructed merge() are less error-prone than pasting keys together.

28. Fast lookup with match()

When y has a unique key and only one or two columns are needed, match() can perform a direct vector lookup:

idx <- match(orders_df$customer_id, customers_df$customer_id)
orders_df$customer_name <- customers_df$customer_name[idx]

Validate uniqueness first:

stopifnot(!anyDuplicated(customers_df$customer_id))

match() returns only the first match. It is not a substitute for a general one-to-many join.

Part VII — data.table joins

29. Understand x[i, on = ...]

data.table’s native join syntax is x[i, on = ...]. It looks up rows of i in x and, by default, follows the row set of i.

library(data.table)

customers_dt <- as.data.table(customers)
orders_dt <- as.data.table(orders)

# Preserve orders (the i table) and bring in customer columns from x.
customers_dt[orders_dt, on = .(customer_id)]

# Exclude unmatched i rows: inner-join-like behavior.
customers_dt[orders_dt, on = .(customer_id), nomatch = NULL]

The direction is easy to misread. Comment which table supplies the desired row population, and select output columns explicitly for stable schemas.

merge() also has a data.table method and may be clearer for full outer joins:

merge(
  orders_dt,
  customers_dt,
  by = "customer_id",
  all.x = TRUE,
  sort = FALSE
)

30. Keys, secondary indices, and selected columns

on can match different names or several columns without setting a key:

customer_lookup_dt <- as.data.table(customer_lookup)

customer_lookup_dt[
  orders_dt,
  on = .(id = customer_id),
  .(
    order_id = i.order_id,
    customer_id = i.customer_id,
    amount = i.amount,
    customer_name,
    region
  )
]

For repeated joins, keys or secondary indices may improve performance. Measure on representative data; do not add indexing complexity without a workload that benefits.

31. Update joins

data.table can update columns by reference during a join, avoiding a separate expanded result:

orders_copy <- copy(orders_dt)

orders_copy[
  customers_dt,
  on = .(customer_id),
  `:=`(
    customer_name = i.customer_name,
    region = i.region
  )
]

In this form, orders_copy is modified in place. Confirm the join direction and uniqueness before using an update join, because repeated keys in i require a defined conflict policy.

32. Non-equi and rolling joins

data.table supports non-equi conditions in on:

transactions_dt <- as.data.table(transactions)
tiers_dt <- as.data.table(tiers)

tiers_dt[
  transactions_dt,
  on = .(lower <= amount, upper > amount),
  .(transaction_id = i.transaction_id, amount = i.amount, tier)
]

Arbitrary expressions are not placed directly inside on; precompute them as columns.

A rolling join can carry the most recent value forward:

prices_dt <- as.data.table(price_history)
sales_dt <- as.data.table(sales_events)

setkey(prices_dt, product_id, effective_date)

prices_dt[
  sales_dt,
  on = .(product_id, effective_date = sale_date),
  roll = TRUE
]

Use roll = "nearest", positive/negative limits, or mult only after defining the exact temporal rule and tie policy.

33. Overlap joins with foverlaps()

For interval overlap, data.table provides foverlaps(). The y interval table must be keyed on its start and end columns.

observed_dt <- as.data.table(observed_intervals)
reference_dt <- as.data.table(reference_regions)

setkey(reference_dt, chromosome, ref_start, ref_end)

foverlaps(
  observed_dt,
  reference_dt,
  by.x = c("chromosome", "start", "end"),
  by.y = c("chromosome", "ref_start", "ref_end"),
  type = "any",
  nomatch = 0L
)

Large interval joins can generate many rows. Check interval validity, boundary definitions, and expected multiplicity before materializing the result.

Part VIII — Databases, performance, and production design

34. Joins through dbplyr

The same dplyr verbs can target lazy database tables through dbplyr. Joins are translated to SQL and normally executed by the database.

Key considerations:

  • database NULL values generally do not match one another;
  • backend support for non-equi, rolling, and full joins varies;
  • indexes on join columns can be decisive;
  • inspect generated SQL with show_query();
  • avoid copy = TRUE unless intentionally moving a table between data sources;
  • delay collect() until filtering and selection have reduced the result.
# Illustrative only; requires a database connection.
remote_orders |>
  left_join(remote_customers, by = join_by(customer_id)) |>
  filter(order_date >= as.Date("2026-01-01")) |>
  select(order_id, customer_id, region) |>
  show_query()

Local data-frame behavior and SQL behavior are not identical. Test the actual backend used in production.

35. Performance principles

  1. Select only necessary columns from y. Wide joins consume more memory and create more conflicts.
  2. Filter early. Reduce rows before joining when the filter does not change semantics.
  3. Validate cardinality first. A Cartesian explosion is a data-model problem before it is a performance problem.
  4. Use canonical key types. Runtime coercion and dirty strings make joins slower and less reliable.
  5. Index database or data.table keys used repeatedly. Measure rather than assume.
  6. Avoid repeated chained materialization. Consider a database plan or a nested representation for very large one-to-many data.
  7. Estimate output size. Especially for cross, inequality, and overlap joins.
estimate_equality_rows <- function(x, y, key) {
  x_counts <- x |> count(across(all_of(key)), name = "nx")
  y_counts <- y |> count(across(all_of(key)), name = "ny")

  x_counts |>
    inner_join(y_counts, by = key, relationship = "one-to-one") |>
    summarise(rows = sum(as.double(nx) * ny)) |>
    pull(rows)
}

The estimate covers matched equality rows; outer joins additionally retain unmatched rows.

36. A production join wrapper

A small wrapper can encode project defaults:

safe_lookup_join <- function(
    x,
    lookup,
    by,
    relationship = "many-to-one",
    allow_unmatched_x = FALSE) {

  missing <- anti_join(x, lookup, by = by, na_matches = "never")

  if (!allow_unmatched_x && nrow(missing) > 0L) {
    stop("Lookup join has ", nrow(missing), " unmatched row(s).", call. = FALSE)
  }

  out <- left_join(
    x,
    lookup,
    by = by,
    relationship = relationship,
    na_matches = "never"
  )

  if (relationship %in% c("many-to-one", "one-to-one") && nrow(out) != nrow(x)) {
    stop("Join unexpectedly changed row count.", call. = FALSE)
  }

  out
}

safe_lookup_join(
  orders |> filter(!is.na(customer_id), customer_id != "C05"),
  customers,
  by = join_by(customer_id)
)

The wrapper is deliberately narrow: it implements one common lookup contract rather than hiding every join option.

Part IX — Applied workflows

37. Workflow: enrich a fact table safely

valid_orders <- orders |>
  filter(!is.na(customer_id))

unknown <- valid_orders |>
  anti_join(customers, by = join_by(customer_id))

if (nrow(unknown) > 0L) {
  warning(nrow(unknown), " order(s) have unknown customer IDs")
}

order_analysis <- valid_orders |>
  left_join(
    customers,
    by = join_by(customer_id),
    relationship = "many-to-one",
    na_matches = "never"
  )

This separates quality reporting from enrichment instead of letting missing lookups appear later as unexplained NA values.

38. Workflow: reconcile two systems

reconciliation <- crm |>
  full_join(
    billing,
    by = join_by(customer_id),
    relationship = "one-to-one",
    keep = TRUE,
    suffix = c("_crm", "_billing")
  ) |>
  mutate(
    in_crm = !is.na(customer_id_crm),
    in_billing = !is.na(customer_id_billing),
    issue = case_when(
      in_crm & in_billing ~ "matched",
      in_crm ~ "missing_from_billing",
      TRUE ~ "missing_from_crm"
    )
  )

Retaining both keys prevents coalescing from hiding source presence.

39. Workflow: build a complete panel

Create every store-date combination, then attach observed sales:

stores <- tibble(store_id = c(1, 2, 3))
dates <- tibble(date = seq(as.Date("2026-08-01"), as.Date("2026-08-07"), by = "day"))

panel <- stores |>
  cross_join(dates) |>
  left_join(
    sales,
    by = join_by(store_id, date),
    relationship = "one-to-one"
  ) |>
  mutate(revenue = coalesce(revenue, 0))

Only replace missing revenue with zero if “no observed row” truly means zero rather than unknown.

40. Workflow: as-of pricing

priced_sales <- sales_events |>
  left_join(
    price_history,
    by = join_by(product_id, closest(sale_date >= effective_date)),
    relationship = "many-to-one"
  )

missing_prices <- priced_sales |>
  filter(is.na(price))

stopifnot(nrow(missing_prices) == 0L)

This pattern makes the temporal rule explicit and validates that every sale received a historical price.

Part X — Review and practice

41. Common mistakes and repairs

Mistake Consequence Repair
Omit by future shared columns change the join use explicit join_by()
Assume a key is unique output rows multiply count duplicates; set relationship
Use inner_join() for routine enrichment unmatched records disappear use left_join() plus an anti_join() audit
Use inner_join() only to test existence repeated y keys duplicate x use semi_join()
Silence many-to-many warning immediately hides a data-model defect inspect both key distributions first
Let NA identifiers match unrelated unknown records combine use na_matches = "never"
Rely on multiple = "first" without ordering selected record is not semantically defined preselect deterministically
Accept .x/.y columns in final output source meaning is unclear rename or use meaningful suffix
Join dirty character keys valid records fail to match normalize case, whitespace, encoding, and format
Cross join without estimating size memory explosion calculate nrow(x) * nrow(y) first
Overwrite missing joined values with zero confuses absence with a real zero apply domain-specific missingness policy
Assume local and SQL joins are identical missing-value/backend behavior differs test generated SQL and target database

42. Join review checklist

Before approving a join, answer:

  • What entity does one row of each input represent?
  • Which columns form the complete key?
  • Are key types and formats canonical?
  • Is the expected relationship declared?
  • How many duplicate and missing keys exist on each side?
  • Which input defines the population that must remain?
  • Should missing keys match?
  • What happens to unmatched rows in each direction?
  • Can one input row produce several output rows?
  • Are overlapping column names reconciled intentionally?
  • Is row order relevant, and is it explicitly restored if necessary?
  • What row count or coverage assertion should run after the join?

43. Practice exercises

  1. Build two small tables and show the exact output of all seven core joins.
  2. Create a one-to-many relationship and enforce it with relationship.
  3. Introduce duplicate keys on both sides, estimate the result size, and explain the many-to-many output.
  4. Compare na_matches = "na" and "never" for an identifier key.
  5. Use semi_join() to select products that appear in sales, then use anti_join() to find unsold products.
  6. Create a complete product-month grid with cross_join() and attach observed values.
  7. Assign transactions to non-overlapping tiers with an inequality join_by().
  8. Match each event to the most recent prior status using closest().
  9. Reproduce inner, left, right, full, and cross joins with base merge().
  10. Rewrite a dplyr lookup join with data.table and explain which table controls the output rows.

Summary

Reliable joins are built from relationships, not memorized function names:

  • left_join(), inner_join(), right_join(), and full_join() add columns and choose different row populations;
  • semi_join() and anti_join() answer existence questions without adding columns or duplicating x;
  • cross_join() explicitly creates every combination;
  • join_by() expresses equality, inequality, rolling, and overlap conditions;
  • relationship, multiple, unmatched, and na_matches turn assumptions into visible policies;
  • nest_join() preserves one-to-many matches as a list-column;
  • merge() supplies base R inner and outer joins;
  • data.table offers concise indexed, update, non-equi, rolling, and overlap joins;
  • pre-join audits and post-join assertions are part of the join, not optional cleanup.

Start by defining the entity, key, cardinality, and missingness policy. Then select the function that implements that contract and verify the result.
