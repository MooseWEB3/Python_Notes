How to use this guide

Iteration means repeating one operation over many pieces of data. In R, that idea appears in several forms:

  • vectorized functions operate on a whole vector at once;
  • a for loop makes the iteration state explicit;
  • the base apply family packages common iteration patterns;
  • purrr provides a consistent vocabulary with explicit output types and indexed errors.

The goal is not to replace every loop. The goal is to recognize the shape of the iteration and choose a tool whose input and output contract match it.

Keep four questions in mind:

  1. What is one unit of input: a row, column, list element, group, or aligned tuple?
  2. How many inputs vary together?
  3. What output type and size should each iteration return?
  4. Is the purpose to compute a value or perform a side effect?

A one-page decision table

Need Base R purrr Return contract
Matrix/array margins apply() usually not needed simplified vector/array or list
One function over list elements lapply() map() list
Convenient automatic simplification sapply() no direct recommendation shape inferred at runtime
Type-checked scalar/vector result vapply() map_lgl/int/dbl/chr(), map_vec() declared type and size
Grouped vector summary tapply() often split() + map() array or list
Two or more aligned inputs mapply() map2(), pmap() simplified output or typed variant
Value plus name/index manual indices imap() list or typed variant
Side effects invisible(lapply(...)) or loop walk(), walk2(), pwalk() original input, invisibly
Preserve input type while changing elements assignment or loop modify() family same type as input

A useful default: use vectorized functions first; use lapply()/map() when every iteration may return an arbitrary object; use vapply() or a typed map_*() when the output contract is known.

Part I — The iteration mental model

1. Vectorization, loops, and functionals

R already knows how to add entire vectors:

x <- 1:5
x^2
# [1]  1  4  9 16 25

There is no benefit in mapping a scalar square function here. Native vectorization is clearer and usually faster. Specialized functions are even better when they express the operation directly:

mat <- matrix(1:12, nrow = 3)
rowSums(mat)
colMeans(mat)

A loop is appropriate when the algorithm has state, early exits, or several coordinated side effects:

running_total <- numeric(length(x))
for (i in seq_along(x)) {
  running_total[i] <- x[i] + if (i == 1L) 0 else running_total[i - 1L]
}
running_total
# [1]  1  3  6 10 15

An apply or map function is a functional: a function that accepts another function. It is strongest when every element undergoes the same independent transformation.

inputs <- list(1:3, 4:8, c(10, 20))
lapply(inputs, mean)

The repeated function should ideally have a stable contract. If one call returns a number, another returns NULL, and a third writes a file, the iteration will be hard to reason about regardless of syntax.

2. Three separate output decisions

Every iteration has three output dimensions:

  • length: usually one result per input element;
  • element size: one scalar, a fixed-length vector, or an arbitrary object;
  • container type: list, atomic vector, matrix, array, data frame, or the original input type.

Compare these contracts:

x <- list(a = 1:3, b = 4:8)

lapply(x, mean)                         # list of two doubles
vapply(x, mean, numeric(1))             # named double vector
vapply(x, range, numeric(2))            # 2 x 2 double matrix
purrr::map(x, mean)                     # list of two doubles
purrr::map_dbl(x, mean)                 # named double vector
purrr::map_vec(x, mean, .ptype = double())

Making this contract explicit is one of the best ways to make iteration code reliable.

Part II — base R apply family

3. apply(): iterate over matrix or array margins

apply(X, MARGIN, FUN, ...) is designed for arrays. For a matrix:

  • MARGIN = 1 means rows;
  • MARGIN = 2 means columns;
  • MARGIN = c(1, 2) retains both dimensions, so each cell becomes a margin.
scores <- matrix(
  c(81, 90, 76,
    88, 92, 85,
    79, 95, 91,
    93, 87, 89),
  nrow = 4,
  byrow = TRUE,
  dimnames = list(
    student = paste0("S", 1:4),
    subject = c("math", "science", "writing")
  )
)

apply(scores, MARGIN = 1, FUN = mean)  # one mean per student
apply(scores, MARGIN = 2, FUN = mean)  # one mean per subject
apply(scores, 2, quantile, probs = c(0.25, 0.5, 0.75))

When every call returns one value, apply() normally simplifies to a vector. When every call returns the same vector length greater than one, it commonly returns a matrix:

column_summary <- apply(
  scores,
  2,
  \(x) c(mean = mean(x), sd = sd(x), min = min(x), max = max(x))
)

column_summary

Higher-dimensional arrays

For an array, MARGIN lists the dimensions to keep. Suppose rows are stores, columns are products, and the third dimension is month:

sales <- array(
  1:24,
  dim = c(store = 2, product = 3, month = 4),
  dimnames = list(
    store = c("north", "south"),
    product = c("A", "B", "C"),
    month = paste0("M", 1:4)
  )
)

# Sum across products and months, retaining store.
apply(sales, MARGIN = "store", FUN = sum)

# Retain store and month, summing over products.
apply(sales, MARGIN = c("store", "month"), FUN = sum)

Named dimensions make array code easier to review than unexplained integers.

The data-frame coercion trap

apply() is not a general data-frame column tool. A two-dimensional data frame is coerced with as.matrix(). If any column is character, the entire matrix usually becomes character:

mixed <- data.frame(
  id = c("A", "B", "C"),
  score = c(10, 15, 12)
)

as.matrix(mixed)
# score is now represented as character too

# Better: iterate over selected columns without matrix coercion.
lapply(mixed["score"], mean)
vapply(mixed["score"], mean, numeric(1))

For data frames, prefer column selection followed by lapply()/vapply(), or purrr. For numeric matrices, prefer specialized functions such as rowSums(), colSums(), rowMeans(), and colMeans() when they match the task.

apply() checklist

  • Is the input genuinely a matrix or array?
  • Does MARGIN describe the dimensions you want to retain?
  • Will every call return the same size?
  • Would a specialized vectorized function express the operation better?
  • If the input is a data frame, have you checked as.matrix() coercion first?

4. lapply(): the stable list workhorse

lapply(X, FUN, ...) applies FUN to every element and always returns a list of the same length as X. Input names are preserved.

measurements <- list(
  control = c(4.2, 4.5, 4.1),
  low = c(5.0, 5.3, 4.9),
  high = c(6.1, 6.4, 6.0)
)

lapply(measurements, mean)
lapply(measurements, range)

The list return is not a weakness. Lists can hold heterogeneous results such as models, plots, data frames, calls, and error objects.

data_by_cyl <- split(mtcars, mtcars$cyl)

models <- lapply(
  data_by_cyl,
  \(df) lm(mpg ~ wt + hp, data = df)
)

lapply(models, coef)

Data frames are lists of columns

Because a data frame is list-like, lapply() naturally iterates over columns without flattening their classes:

column_classes <- lapply(iris, class)
numeric_summary <- lapply(
  iris[vapply(iris, is.numeric, logical(1))],
  summary
)

Constant arguments and clear wrappers

Additional arguments can be passed through ...:

lapply(measurements, mean, trim = 0.1, na.rm = TRUE)

For reusable code, an anonymous wrapper often makes argument ownership clearer:

lapply(
  measurements,
  \(x) mean(x, trim = 0.1, na.rm = TRUE)
)

This also prevents ambiguous partial matching when a mapped function has arguments such as X, FUN, or MARGIN.

Nested lists

Use nested lapply() when the data hierarchy is meaningful:

experiments <- list(
  study_a = list(control = 1:4, treated = 4:8),
  study_b = list(control = 2:6, treated = 8:10)
)

lapply(experiments, \(study) {
  lapply(study, \(group) c(n = length(group), mean = mean(group)))
})

If nesting becomes difficult to read, extract a named helper function.

5. sapply(): convenient but shape-dependent

sapply() is essentially lapply() followed by an attempt to simplify the list. Depending on what FUN returns, the result may be a vector, matrix, array, or list.

sapply(measurements, mean)   # named numeric vector
sapply(measurements, range)  # matrix when all ranges have length 2

This is convenient in interactive exploration, but the inferred output can change after the data changes:

maybe_range <- function(x) {
  if (length(x) < 3L) return(NA_real_)
  range(x)
}

unstable <- list(a = 1:3, b = 4:5)
sapply(unstable, maybe_range)
# Different result sizes prevent the expected numeric matrix.

Other surprises include:

  • one element returns NULL;
  • integer and double results are promoted;
  • classed values may be simplified in an undesirable way;
  • a zero-length input produces a result that differs from the usual case;
  • a future change to FUN silently changes downstream dimensions.

Use sapply(..., simplify = FALSE) only when compatibility requires it; lapply() communicates the list contract directly.

Practical rule: sapply() is pleasant for console work. Prefer vapply() or typed purrr maps when other code depends on the exact output.

6. vapply(): declare type and size up front

vapply(X, FUN, FUN.VALUE, ...) uses FUN.VALUE as a prototype. Every result must have a compatible type and exactly the same length.

vapply(measurements, mean, numeric(1))
vapply(measurements, length, integer(1))
vapply(measurements, \(x) anyNA(x), logical(1))
vapply(measurements, \(x) paste(x, collapse = ", "), character(1))

Useful scalar prototypes are:

Desired output Prototype
logical logical(1) or FALSE
integer integer(1) or 0L
double numeric(1) or 0
character character(1) or ""
complex complex(1)

The prototype is a contract, not a default value. If the function violates it, vapply() fails at the offending element instead of silently changing shape.

bad_mean <- function(x) {
  if (anyNA(x)) return(NULL)
  mean(x)
}

values <- list(clean = 1:3, incomplete = c(1, NA))

# Fails because NULL has length 0, not length 1.
try(vapply(values, bad_mean, numeric(1)))

Fixed-length vector outputs become matrices

vapply(
  measurements,
  \(x) c(mean = mean(x), sd = sd(x)),
  c(mean = 0, sd = 0)
)

The prototype names become row names; input names become column names. This is a compact way to build a stable summary matrix.

Type promotion is one-way

R may safely promote logical to integer and integer to double for a double prototype, but it will not demote a double containing 1 to integer merely because integer(1) was requested. Choose the type the function truly returns.

A reusable data-frame schema check

schema <- vapply(
  iris,
  \(x) paste(class(x), collapse = "/"),
  character(1)
)

schema

vapply() is one of the best base R tools for package code because it documents and enforces the expected result in the same call.

7. tapply(): summarize a vector by one or more groups

tapply(X, INDEX, FUN, ...) splits X by unique factor-level combinations, applies FUN to each non-empty group, and usually simplifies the result to an array.

score <- c(82, 91, 76, 88, 95, 84, 79, 93)
group <- c("A", "A", "B", "B", "A", "B", "A", "B")

tapply(score, INDEX = group, FUN = mean)
tapply(score, group, range)

Multiple grouping variables produce a multidimensional table:

sex <- c("F", "M", "F", "M", "F", "M", "M", "F")
tapply(score, list(group = group, sex = sex), mean)

Empty factor combinations and default

Factor levels define the possible cells. Some combinations may have no observations:

group_f <- factor(group, levels = c("A", "B", "C"))

tapply(score, group_f, length)
# C is an empty cell and is represented by NA by default.

tapply(score, group_f, length, default = 0)

default initializes empty cells when the result simplifies to an array. For a sum, default = 0 is often meaningful; for a mean, NA_real_ usually communicates absence better.

Return a list when group results are not scalar

tapply(score, group, quantile, probs = c(0.25, 0.5, 0.75), simplify = FALSE)

This produces a list-like array, avoiding fragile simplification.

Missing groups

Rows with NA in the grouping index do not form an ordinary factor level and are normally excluded. If “missing” must be reported as a group, encode it explicitly before calling tapply():

group_with_na <- c("A", "A", NA, "B")
group_explicit <- addNA(factor(group_with_na))
levels(group_explicit)[is.na(levels(group_explicit))] <- "missing"

tapply(c(10, 20, 30, 40), group_explicit, mean)

Use tapply() for concise grouped vector summaries. Use split() plus lapply()/map() when each group needs a model, plot, or complex object; use aggregate() when a data-frame result is more convenient.

8. mapply(): vectorize over multiple aligned inputs

mapply(FUN, ..., MoreArgs = NULL, SIMPLIFY = TRUE) is a multivariate form of sapply(). It calls FUN with the first elements of each varying input, then the second elements, and so on.

lower <- c(1, 10, 100)
upper <- c(5, 20, 110)

mapply(\(lo, hi) mean(c(lo, hi)), lower, upper)
# [1]   3  15 105

A common use is vectorizing a non-vectorized function:

starts <- as.Date(c("2026-01-01", "2026-02-10", "2026-03-15"))
days <- c(7L, 14L, 30L)

mapply(
  \(start, n) start + n,
  starts,
  days,
  SIMPLIFY = FALSE
)

SIMPLIFY = FALSE preserves a list. Base Map() is a convenient equivalent for that list-returning pattern:

Map(\(lo, hi) c(lower = lo, upper = hi), lower, upper)

Constant arguments with MoreArgs

mapply(
  \(mu, sigma, n) rnorm(n, mean = mu, sd = sigma),
  mu = c(0, 10, 100),
  sigma = c(1, 2, 5),
  MoreArgs = list(n = 4L),
  SIMPLIFY = FALSE
)

Recycling deserves an explicit check

mapply() recycles varying arguments to the longest length. This is convenient for a genuine scalar constant but can hide mismatched data:

mapply(paste, 1:3, letters[1:2])
# The second input is recycled; this may be unintended.

For maintained code, validate that lengths are equal or one:

compatible_lengths <- function(...) {
  sizes <- lengths(list(...))
  all(sizes == max(sizes) | sizes == 1L)
}

stopifnot(compatible_lengths(lower, upper))

mapply() also inherits sapply()-style simplification. Use SIMPLIFY = FALSE, or prefer typed map2_*()/pmap_*() when downstream shape matters.

Part III — purrr’s map vocabulary

9. map() and typed map variants

Load purrr explicitly in an interactive analysis, or use purrr:: in reusable code:

library(purrr)

map(measurements, mean)
map_dbl(measurements, mean)

The suffix defines the contract:

Function Required result per iteration Final result
map() anything list
map_lgl() one logical logical vector
map_int() one integer integer vector
map_dbl() one compatible double double vector
map_chr() one character string character vector
map_vec() one vector value of common/declared type atomic or S3 vector
walk() return ignored original input, invisibly

Typed maps fail if .f returns the wrong size or incompatible type. Their errors include the input index, which is valuable in long jobs.

map_lgl(measurements, \(x) all(is.finite(x)))
map_int(measurements, length)
map_dbl(measurements, mean)
map_chr(measurements, \(x) sprintf("%.2f", mean(x)))

map_vec() for classed vectors

map_vec() uses a common vector type and supports prototypes through .ptype. It is especially useful for classes such as Date, factors, and date-times.

date_text <- c("2026-01-01", "2026-02-14", "2026-08-12")

map_vec(
  date_text,
  as.Date,
  .ptype = as.Date(character())
)

The .ptype states the desired zero-length type, similar in spirit to FUN.VALUE in vapply().

Anonymous functions are the current clear style

Modern R’s shorthand syntax makes argument flow visible:

map_dbl(measurements, \(x) mean(x, trim = 0.1, na.rm = TRUE))

Purrr still understands formulas such as ~ mean(.x), but current documentation no longer recommends formula mappers. Anonymous functions are ordinary R and give clearer argument names and errors.

Extraction shortcuts

Mapper shortcuts can extract by name, position, or a path:

records <- list(
  list(id = "A01", meta = list(score = 9.2)),
  list(id = "B07", meta = list(score = 8.8))
)

map_chr(records, "id")
map_dbl(records, list("meta", "score"))

For complex business logic, a named or anonymous function is usually easier to understand than a deep extraction shortcut.

10. map2() and walk2(): two inputs in lockstep

map2(.x, .y, .f) passes two aligned elements to .f. Typed variants mirror the map_*() suffixes.

names <- c("control", "low dose", "high dose")
means <- c(4.27, 5.07, 6.17)

map2_chr(
  names,
  means,
  \(name, value) sprintf("%s: %.2f", name, value)
)

Inputs should have the same length. A length-one input is recycled; other incompatible lengths are errors. This is stricter than general base recycling.

map2_dbl(1:4, 10, \(x, offset) x + offset)
# [1] 11 12 13 14

Use walk2() when the aligned values control a side effect:

paths <- file.path("output", paste0(names, ".csv"))
tables <- map(measurements, \(x) data.frame(value = x))

# Not run here: writes one table to each path.
walk2(tables, paths, \(tbl, path) write.csv(tbl, path, row.names = FALSE))

The return value is the first input, invisibly, so a pipeline can continue without collecting meaningless NULL values.

11. pmap() and pwalk(): three or more varying inputs

pmap(.l, .f) maps over a list of aligned vectors. If .l is named, its names match function arguments. A data frame is an important special case: pmap() calls .f once per row.

parameters <- data.frame(
  mean = c(0, 5, 10),
  sd = c(1, 2, 3),
  n = c(4L, 3L, 5L)
)

set.seed(2026)
simulations <- pmap(
  parameters,
  \(mean, sd, n) rnorm(n = n, mean = mean, sd = sd)
)

The number of columns in .l determines the number of arguments passed to .f. Length-one components may be recycled; all other components must share a length.

Typed variants enforce scalar outputs:

pmap_dbl(parameters, \(mean, sd, n) mean + 1.96 * sd / sqrt(n))

Do not confuse “parallel inputs” with multicore execution. pmap() aligns several inputs; it is sequential unless the mapped function is explicitly wrapped for parallel execution.

pwalk() is useful for row-defined side effects:

jobs <- data.frame(
  path = c("a.txt", "b.txt"),
  text = c("first report", "second report")
)

# Not run here: creates files.
pwalk(jobs, \(path, text) writeLines(text, path))

12. imap() and iwalk(): values plus names or positions

imap() is shorthand for mapping over values and their identifiers:

  • named input: .y is names(.x);
  • unnamed input: .y is seq_along(.x).
imap_chr(
  measurements,
  \(values, name) sprintf("%s (n=%d, mean=%.2f)", name, length(values), mean(values))
)

imap_chr(
  c(10, 20, 30),
  \(value, index) paste0("item ", index, " = ", value)
)

Use iwalk() when the name becomes a log label or file name:

# Not run here: writes one RDS file per model.
iwalk(models, \(model, name) saveRDS(model, paste0("model-", name, ".rds")))

13. walk() for side effects

Mapping normally transforms values. Printing, writing files, sending requests, and producing plots are side effects. walk() states that intention and returns .x invisibly.

reports <- c("summary.html", "diagnostics.html", "appendix.html")

reports |>
  walk(\(path) message("Would build: ", path)) |>
  length()
# The pipeline can continue because walk() returns reports.

Good side-effect functions should:

  • return useful computation separately from the side effect;
  • create parent directories deliberately;
  • avoid overwriting unless that policy is explicit;
  • log enough context to identify the failing item;
  • be idempotent when practical.

For complex stateful side effects, an ordinary loop can be clearer than walk().

14. modify() and conditional mapping

map() always returns a list, while typed maps return a fixed vector type. The modify() family returns the same type as .x.

numbers <- c(a = 1, b = 2, c = 3)
modify(numbers, \(x) x * 10)
# named double vector, like the input

df <- data.frame(
  name = c("  Ada ", "Grace  "),
  score = c(9.5, 9.8)
)

modify_if(df, is.character, trimws)

Related functions include:

  • modify_at() for selected positions or names;
  • modify_if() for a predicate;
  • modify2() for two aligned inputs while preserving .x’s type;
  • imodify() for value plus name/index;
  • modify_in() for one nested location.

map_if() and map_at() also transform selected elements, but return a list. Choose modify_*() when preserving the original container is part of the contract.

15. Binding data-frame results correctly

Older code often uses map_dfr() or map_dfc(). These functions have been superseded since purrr 1.0.0. Current purrr recommends mapping first, then binding explicitly:

model_rows <- models |>
  map(\(model) {
    data.frame(
      term = names(coef(model)),
      estimate = unname(coef(model))
    )
  }) |>
  list_rbind(names_to = "cyl")

For columns, use list_cbind() when every element is a data frame with compatible row semantics.

This two-step design separates two contracts:

  1. each mapped call must return a data frame or NULL;
  2. those data frames are then combined by rows or columns.

It avoids the misleading suggestion that _dfr behaves like scalar typed suffixes such as _dbl.

Part IV — Robust and advanced mapping

16. Errors with index context

When .f fails inside a purrr map, purrr adds the location of the failing input. Preserve that context rather than wrapping every call in a generic error.

inputs <- list(ok = 10, bad = "ten", also_ok = 100)
try(map_dbl(inputs, log))
# The error identifies the failing element.

For base R, add context deliberately when it matters:

safe_vapply <- function(x, fun, prototype) {
  vapply(seq_along(x), \(i) {
    tryCatch(
      fun(x[[i]]),
      error = \(e) stop("Element ", i, " failed: ", conditionMessage(e), call. = FALSE)
    )
  }, prototype)
}

Do not suppress errors merely to finish a batch. Decide whether failure should stop the job, produce a typed fallback, or be collected for review.

17. possibly(), safely(), and quietly()

Purrr adverbs create modified functions.

Typed fallback with possibly()

log_or_na <- possibly(log, otherwise = NA_real_)
map_dbl(list(10, "bad", 100), log_or_na)

The fallback should match the typed map. NA_real_ fits map_dbl() better than untyped NA.

Keep result and error with safely()

safe_log <- safely(log, otherwise = NA_real_)

attempts <- map(list(10, "bad", 100), safe_log)
attempts[[2]]$result
attempts[[2]]$error

separated <- transpose(attempts)
separated$result
separated$error

This is appropriate when every failure must be audited. Store the input identifier alongside the captured condition.

Capture messages and warnings with quietly()

quiet_summary <- quietly(summary)
captured <- map(list(1:5, c(1, NA, 3)), quiet_summary)

Captured conditions are data. Inspect and report them rather than forgetting them.

18. Progress bars

Map functions accept .progress. Use it for genuinely noticeable work, not trivial transformations:

# Example only; intentionally slow.
results <- map(
  1:20,
  \(i) {
    Sys.sleep(0.1)
    sqrt(i)
  },
  .progress = "calculating"
)

Progress is observability, not performance. In non-interactive logs, structured messages may be more useful than an animated bar.

19. Parallel mapping with in_parallel()

Current purrr supports parallel map execution through mirai. Set daemons, wrap a freshly defined function with in_parallel(), perform the map, and tear down daemons when appropriate:

library(purrr)

mirai::daemons(4)

results <- map_dbl(
  1:12,
  in_parallel(\(x) {
    Sys.sleep(0.2)
    sqrt(x)
  })
)

mirai::daemons(0)

Important constraints:

  • without active mirai daemons, execution falls back to sequential mapping;
  • the function passed to in_parallel() must be freshly defined;
  • package functions inside it should use explicit package::function qualification;
  • required local objects must be declared so the function is self-contained;
  • ... cannot be used to pass mapped-function arguments in this context;
  • startup, serialization, and communication overhead can exceed any benefit for cheap iterations.

A self-contained example with a local constant is:

offset <- 10

map_dbl(
  1:4,
  in_parallel(\(x) x + offset, offset = offset)
)

Benchmark representative workloads before adopting parallelism. Never assume four workers make code four times faster.

Part V — Applied patterns

20. Pattern: a typed column-quality report

Suppose a data frame contains numeric measurements and identifiers:

clinical <- data.frame(
  patient = c("P01", "P02", "P03", "P04"),
  age = c(42, 55, NA, 39),
  marker = c(1.2, 1.8, 1.5, NA),
  group = factor(c("A", "B", "A", "B"))
)

Base R version:

quality_base <- data.frame(
  variable = names(clinical),
  class = vapply(clinical, \(x) class(x)[1], character(1)),
  missing = vapply(clinical, \(x) sum(is.na(x)), integer(1)),
  unique = vapply(clinical, \(x) length(unique(x)), integer(1)),
  row.names = NULL
)

quality_base

Purrr version with one data-frame result per column:

quality_purrr <- imap(clinical, \(x, name) {
  data.frame(
    variable = name,
    class = class(x)[1],
    missing = sum(is.na(x)),
    unique = length(unique(x))
  )
}) |>
  list_rbind()

quality_purrr

Both are valid. The base version makes scalar types explicit; the purrr version naturally scales to several fields per item.

21. Pattern: grouped summaries and models

Use tapply() for one grouped vector statistic:

tapply(mtcars$mpg, mtcars$cyl, mean)

Use split() plus list mapping for richer objects:

by_cyl <- split(mtcars, mtcars$cyl)

model_table <- by_cyl |>
  map(\(df) lm(mpg ~ wt, data = df)) |>
  imap(\(model, cyl) {
    data.frame(
      cyl = cyl,
      term = names(coef(model)),
      estimate = unname(coef(model)),
      row.names = NULL
    )
  }) |>
  list_rbind()

model_table

The split-map pattern keeps group names, model objects, and errors visible.

22. Pattern: parameter grids with pmap()

Create a row-oriented parameter table, then map each row to a simulation summary:

grid <- expand.grid(
  n = c(20L, 100L),
  mu = c(0, 2),
  sigma = c(1, 3),
  KEEP.OUT.ATTRS = FALSE
)

set.seed(42)

simulation_results <- grid |>
  pmap(\(n, mu, sigma) {
    draw <- rnorm(n, mu, sigma)
    data.frame(
      observed_mean = mean(draw),
      observed_sd = sd(draw)
    )
  }) |>
  list_rbind()

simulation_summary <- cbind(grid, simulation_results)

Using parameter names such as mu and sigma avoids putting columns named mean and sd beside the functions with those same names.

23. Pattern: robust batch parsing

Assume each input should become a number, but malformed values must be reviewed:

raw_values <- c(a = "12.5", b = "bad", c = "9.7")

parse_one <- \(x) {
  value <- as.numeric(x)
  if (is.na(value)) stop("not numeric: ", x)
  value
}

attempts <- raw_values |>
  map(safely(parse_one, otherwise = NA_real_))

audit <- imap(attempts, \(attempt, id) {
  data.frame(
    id = id,
    value = attempt$result,
    error = if (is.null(attempt$error)) NA_character_ else conditionMessage(attempt$error)
  )
}) |>
  list_rbind()

audit

This retains both successful values and failure reasons. It is much safer than globally suppressing warnings or silently dropping bad inputs.

Part VI — Choosing well

24. Direct translations

Intent Base R purrr
List result over one input lapply(x, f) map(x, f)
Double scalar per item vapply(x, f, numeric(1)) map_dbl(x, f)
Character scalar per item vapply(x, f, character(1)) map_chr(x, f)
Two varying inputs, list result Map(f, x, y) map2(x, y, f)
Two varying inputs, double result mapply(f, x, y) plus validation map2_dbl(x, y, f)
Many varying inputs mapply(f, ..., SIMPLIFY = FALSE) pmap(inputs, f)
Value plus index lapply(seq_along(x), \(i) f(x[[i]], i)) imap(x, f)
Grouped scalar summary tapply(x, group, f) split(x, group) |> map_*()
Side effects loop or invisible(lapply(...)) walk() family

Translation should preserve contracts, not merely shorten syntax. For example, replacing vapply(..., numeric(1)) with plain map() loses a valuable type guarantee; the closer equivalent is map_dbl().

25. Performance principles

  1. Choose the right algorithm first. Avoid unnecessary repeated work inside the mapped function.
  2. Prefer vectorized and specialized primitives. rowMeans() communicates more and commonly runs faster than apply(x, 1, mean).
  3. Do not assume apply means faster. It improves expression of a pattern; it does not magically remove iteration.
  4. Avoid repeated growth. A loop should preallocate; map functions allocate their result structure for you.
  5. Keep mapped functions focused. Move constant setup outside the iteration.
  6. Measure representative data. Microbenchmarks of toy inputs can reward the wrong design.
  7. Parallelize only sufficiently expensive, independent work. Include serialization and worker startup in the measurement.

Readable code with a stable output contract is usually a better first optimization than switching between equivalent loop syntaxes.

26. Common mistakes and repairs

Mistake Why it hurts Repair
apply() on a mixed data frame coercion may turn every column into character select compatible columns; use lapply()/vapply()/map()
apply(x, 1, sum) for a numeric matrix misses a clearer specialized primitive use rowSums(x)
sapply() in an API output type/shape depends on runtime values use vapply() or typed map_*()
vapply(..., integer(1)) around a double function safe demotion is not assumed request numeric(1) or return integer explicitly
mapply() with mismatched vector lengths recycling can hide alignment bugs validate sizes; use map2()/pmap() rules
Formula mapper ~ .x + 1 in new code current purrr docs no longer recommend it use \(x) x + 1
map_dfr() in new code superseded and binding semantics are implicit use map() then list_rbind()
map() for file writing result becomes a list of meaningless return values use walk()
possibly() with the wrong fallback type typed map fails later use NA_real_, NA_integer_, etc. deliberately
Parallel mapping for tiny tasks overhead dominates keep sequential or batch/vectorize work

27. Review checklist

Before finalizing iteration code, ask:

  • Is there a direct vectorized or specialized function?
  • Does the chosen function match rows, columns, elements, groups, or aligned inputs?
  • Is the return type explicit enough for downstream code?
  • Are empty input, missing values, and empty factor levels handled?
  • Could matrix coercion or automatic simplification change the data type?
  • Are input lengths checked before multi-input mapping?
  • Are computation and side effects separated?
  • Will an error identify the failing element or group?
  • Are superseded purrr variants avoided in new code?
  • Has any claimed performance benefit been measured?

28. Practice exercises

  1. Use apply() to compute the median of each column in a numeric matrix. Replace it with a more specialized approach if one is available.
  2. Use lapply() to fit one lm() per Species in iris; extract coefficients with vapply() or a typed purrr map.
  3. Construct an example where sapply() returns a vector for one input and a list for another. Rewrite it with an explicit contract.
  4. Use tapply() to calculate mean Sepal.Length by Species, including an unused factor level.
  5. Use mapply() and map2_chr() to format aligned labels and values. Compare their recycling behavior.
  6. Build a parameter data frame and use pmap_dbl() to evaluate a deterministic formula once per row.
  7. Use safely() to process several good and bad inputs, then create an audit data frame containing identifiers and error messages.
  8. Replace a map_dfr() example from older code with map() and list_rbind().

Summary

The apply and map families are easiest to learn as contracts:

  • apply() maps over matrix or array margins;
  • lapply() and map() guarantee a list;
  • sapply() guesses a simplified shape;
  • vapply() and typed map_*() enforce type and size;
  • tapply() summarizes a vector across factor-defined groups;
  • mapply(), map2(), and pmap() align several varying inputs;
  • imap() adds names or positions;
  • walk() makes side effects explicit;
  • modify() preserves the input container type;
  • safely() and related adverbs turn failure behavior into a deliberate design choice;
  • in_parallel() can parallelize expensive independent maps when configured and measured carefully.

Choose the smallest tool that expresses the real iteration shape and the strictest reasonable output contract. That makes R code easier to read today and safer to change later.
