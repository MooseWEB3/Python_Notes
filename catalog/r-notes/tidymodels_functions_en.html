tidymodels is not one modeling-algorithm package. It is a meta-package that loads and coordinates rsample, recipes, parsnip, workflows, tune, yardstick, dials, broom, and related packages. This guide focuses on stable, commonly used user-facing functions rather than every developer API.

Scope and the core mental model

tidymodels is a collection of modeling and machine-learning packages designed around tidyverse principles. It decomposes a traditional modeling process into composable objects: splits, recipes, model specifications, workflows, resamples, metrics, and tuning results. Its real advantage is not shorter function names but a consistent interface across models.

Raw data
  ↓ rsample: training set, test set, cross-validation
recipe: estimate preprocessing parameters from training data only
  +
parsnip: declare model type, mode, and engine
  ↓ workflows: bind preprocessing, model, and postprocessing
fit / fit_resamples / tune_grid
  ↓ yardstick: compare models and parameter configurations
finalize_workflow
  ↓ last_fit: refit on training data, assess the test set once

This guide uses two runnable threads:

  • Binary classification: modeldata::two_class_dat, logistic regression, and a decision tree.
  • Regression: Base R’s mtcars and linear regression.

The examples assume that tidymodels is installed:

# Run once if needed.
# install.packages("tidymodels")

library(tidymodels)
tidymodels_prefer()

set.seed(20260811)

Some engines require additional packages, such as ranger, xgboost, or glmnet. You can create a model specification without them, but the engine package must be installed before fit().

1. Functions in the tidymodels meta-package

1.1 What library(tidymodels) loads

library(tidymodels) loads the commonly used modeling packages and data tools. Inspect the current collection with:

tidymodels_packages()
tidymodels_packages(include_self = FALSE)

The collection includes modeling infrastructure and data packages such as dplyr, ggplot2, purrr, tibble, and tidyr. It does not automatically load every extension package. For example, stacks, finetune, probably, and butcher must be installed and attached separately.

1.2 Conflict and version tools

tidymodels_conflicts()
tidymodels_prefer()

tidymodels_prefer() uses conflicted rules to prefer tidymodels/tidyverse versions of commonly ambiguous function names. Other meta-package tools include:

Function Purpose Guidance
tidymodels_packages() List packages in the collection Inspect an environment
tidymodels_conflicts() Report function-name conflicts Check after loading other ecosystems
tidymodels_prefer() Establish common conflict preferences Call near the start of a script
tidymodels_update() Check/update related packages Changes the local library; inspect prompts first
pkg_deps() Inspect dependency state Environment diagnostics
tag_show(), tag_attach() Manage release tags Advanced reproduction/development

2. rsample: splitting and resampling data

2.1 initial_split(), training(), and testing()

The test set simulates completely unseen data. Split it before estimating a recipe, selecting variables, or tuning.

data(two_class_dat, package = "modeldata")

set.seed(1001)
class_split <- initial_split(
  two_class_dat,
  prop = 0.80,
  strata = Class
)

class_train <- training(class_split)
class_test  <- testing(class_split)

dim(class_train)
dim(class_test)
prop.table(table(class_train$Class))
  • prop is the fraction assigned to training.
  • strata approximately preserves class proportions; classification tasks normally stratify on the outcome.
  • The return value is an rsplit, not two copied data frames.
  • training() and testing() extract the rows.

2.2 vfold_cv() and repeats

set.seed(1002)
class_folds <- vfold_cv(
  class_train,
  v = 5,
  repeats = 2,
  strata = Class
)

class_folds

Each split contains analysis data for fitting and assessment data for validation. With v = 5 and repeats = 2, this design yields ten assessments.

2.3 Other useful resampling functions

Function Appropriate use
bootstraps(data, times) Bootstrap uncertainty and performance
mc_cv(data, prop, times) Repeated Monte Carlo splits
group_vfold_cv(data, group) One patient, hospital, or household must not cross folds
initial_time_split() An initial split for ordered time data
sliding_window() / sliding_period() Rolling time-window validation
nested_cv() Outer performance estimation with inner tuning

A common form of leakage in healthcare data occurs when multiple records from the same patient appear in both training and validation folds. Use group-aware splitting instead of ordinary random CV.

3. recipes: trainable preprocessing

3.1 recipe() and variable roles

recipe() describes outcomes, predictors, and preprocessing steps. It does not calculate means, factor levels, or imputation values when it is created.

class_rec <- recipe(Class ~ ., data = class_train) |>
  step_zv(all_predictors()) |>
  step_normalize(all_numeric_predictors())

class_rec
tidy(class_rec)

Common selectors:

Selector What it selects
all_predictors() All predictors
all_outcomes() All outcomes
all_numeric_predictors() Numeric predictors
all_nominal_predictors() Factor/character predictors
has_role(“id variable”) A designated role
starts_with(), all_of() tidyselect name rules

An ID should not usually be a predictor. Change its role:

patient_example <- tibble(
  patient_id = 101:106,
  age = c(50, 62, 47, 71, 59, 65),
  outcome = factor(c("no", "yes", "no", "yes", "no", "yes"))
)

id_rec <- recipe(outcome ~ ., data = patient_example) |>
  update_role(patient_id, new_role = "id variable")

3.2 Common step_*() functions

Function Purpose Important detail
step_impute_median() Median imputation for numeric data Learn the statistic from training only
step_impute_mode() Mode imputation for categories Different from a novel level
step_unknown() Convert missing categories to a level Run before dummy encoding
step_novel() Handle levels absent during training Run before dummy encoding
step_other() Pool infrequent categories Controlled by a frequency threshold
step_dummy() Convert factors to dummy variables Drops a reference level by default
step_normalize() Center and scale Common for distance/regularized models
step_log(), step_YeoJohnson() Reduce skew Yeo–Johnson supports non-positive values
step_zv(), step_nzv() Remove zero/near-zero variance Usually early in the recipe
step_corr() Remove highly correlated predictors Configure with threshold
step_interact() Create interaction terms Watch dimensional growth
step_pca() Principal components Normally normalize first

An example with missing values and a novel category:

toy_train <- tibble(
  y = c(10, 12, 9, 15, 13, 11),
  x = c(1, 2, NA, 4, 5, 6),
  z = c(100, 120, 110, 150, 140, 130),
  site = factor(c("A", "A", "B", "B", NA, "A"))
)

toy_rec <- recipe(y ~ ., data = toy_train) |>
  step_impute_median(all_numeric_predictors()) |>
  step_unknown(all_nominal_predictors()) |>
  step_novel(all_nominal_predictors()) |>
  step_dummy(all_nominal_predictors()) |>
  step_normalize(all_numeric_predictors())

3.3 prep(), bake(), and leakage

For manual recipe inspection:

toy_prep <- prep(toy_rec, training = toy_train)

processed_train <- bake(toy_prep, new_data = NULL)

toy_new <- tibble(
  x = c(3, NA),
  z = c(125, 160),
  site = factor(c("C", "A"))
)

processed_new <- bake(toy_prep, new_data = toy_new)

processed_train
processed_new
  • prep() estimates parameters from training data only.
  • bake() applies those same estimates to new data.
  • bake(prepped, new_data = NULL) returns retained processed training data.
  • For modeling, normally let workflow() handle prep/bake so each CV fold estimates the recipe from its analysis data only.

4. parsnip: unified model specifications

4.1 Model type, mode, and engine

parsnip separates three concepts:

  1. Model type, such as linear_reg() or rand_forest().
  2. Mode: “regression”, “classification”, or censored regression.
  3. Engine: the underlying implementation, such as “lm”, “glm”, “rpart”, or “ranger”.
log_spec <- logistic_reg() |>
  set_engine("glm")

tree_spec <- decision_tree(
  cost_complexity = 0.01,
  tree_depth = 6,
  min_n = 10
) |>
  set_mode("classification") |>
  set_engine("rpart")

log_spec
tree_spec
show_engines("decision_tree")
translate(log_spec)

set_engine() can receive engine-specific arguments. Put tunable model hyperparameters in the model constructor whenever possible so tune can identify them.

4.2 Common model constructors

Function Task Common tunable arguments
linear_reg() Numeric regression penalty, mixture for some engines
logistic_reg() Binary classification penalty, mixture
multinom_reg() Multiclass classification penalty, mixture
decision_tree() Classification/regression trees cost_complexity, tree_depth, min_n
rand_forest() Random forests mtry, trees, min_n
boost_tree() Boosting trees, tree_depth, learn_rate, and others
nearest_neighbor() K-nearest neighbors neighbors, weight_func, dist_power
svm_linear(), svm_rbf() Support vector machines cost, rbf_sigma
mlp() Single-hidden-layer neural network hidden_units, penalty, epochs
poisson_reg() Count outcome penalty, mixture
survival_reg() Parametric survival model dist

4.3 fit(), fit_xy(), and predict()

Fit a specification directly:

log_fit_direct <- log_spec |>
  fit(Class ~ A + B, data = class_train)

predict(log_fit_direct, new_data = class_test)
predict(log_fit_direct, new_data = class_test, type = "prob")

fit_xy() is useful when predictors and the outcome are already separated:

log_fit_xy <- log_spec |>
  fit_xy(
    x = class_train |> select(A, B),
    y = class_train$Class
  )

Common prediction types:

Mode type Output
regression “numeric” .pred
classification “class” .pred_class
classification “prob” One probability column per level
Models supporting intervals “conf_int” / “pred_int” Interval columns

5. workflows: bind all modeling components

5.1 workflow(), add_recipe(), and add_model()

log_wf <- workflow() |>
  add_recipe(class_rec) |>
  add_model(log_spec)

log_wf

The concise constructor is:

log_wf_short <- workflow(
  preprocessor = class_rec,
  spec = log_spec
)

A fitted workflow remembers recipe estimates, the model fit, and the blueprint, ensuring prediction performs exactly the same processing as training.

5.2 fit(), predict(), and augment()

log_wf_fit <- fit(log_wf, data = class_train)

class_pred <- predict(log_wf_fit, new_data = class_test)
class_prob <- predict(log_wf_fit, new_data = class_test, type = "prob")

class_aug <- augment(log_wf_fit, new_data = class_test)

class_pred
class_prob
class_aug

Do not manually bake() and then pass the result to a fitted workflow. predict.workflow() automatically runs the correct recipe.

5.3 extract_*() and component updates

extract_recipe(log_wf_fit, estimated = TRUE)
extract_spec_parsnip(log_wf_fit)
extract_fit_parsnip(log_wf_fit)
extract_fit_engine(log_wf_fit)
extract_fit_time(log_wf_fit)

Extracting the engine fit is useful for coefficients, summaries, or variable importance. Continue predicting from the workflow, however, or you may bypass preprocessing.

Common replacement functions are update_model(), update_recipe(), remove_model(), and remove_recipe().

6. yardstick: consistent performance metrics

6.1 Regression metrics

regression_predictions <- tibble(
  truth = c(10, 12, 15, 20),
  estimate = c(11, 11, 14, 18)
)

rmse(regression_predictions, truth, estimate)
mae(regression_predictions, truth, estimate)
rsq(regression_predictions, truth, estimate)

reg_metrics <- metric_set(rmse, mae, rsq)
reg_metrics(regression_predictions, truth, estimate)
  • Smaller RMSE and MAE are better.
  • R-squared is generally better when larger.
  • RMSE penalizes large errors more strongly and is in the outcome’s units.
  • Metrics estimate generalization only when computed from out-of-sample predictions.

6.2 Class and probability metrics

class_test_predictions <- bind_cols(
  class_test,
  predict(log_wf_fit, class_test),
  predict(log_wf_fit, class_test, type = "prob")
)

accuracy(class_test_predictions, Class, .pred_class)
roc_auc(class_test_predictions, Class, .pred_Class1)
sens(class_test_predictions, Class, .pred_class)
spec(class_test_predictions, Class, .pred_class)

class_metrics <- metric_set(roc_auc, accuracy, sens, spec)
class_metrics(
  class_test_predictions,
  truth = Class,
  estimate = .pred_class,
  .pred_Class1
)

For binary classification, yardstick treats the first factor level as the event by default. Always inspect it:

levels(class_train$Class)

If the business-positive class is the second level, reorder factor levels or explicitly set event_level = “second” where supported. Do not redefine the event after seeing results.

6.3 conf_mat(), curves, and thresholds

cm <- conf_mat(class_test_predictions, Class, .pred_class)
cm
summary(cm)
autoplot(cm, type = "heatmap")

roc_curve(class_test_predictions, Class, .pred_Class1) |>
  autoplot()

pr_curve(class_test_predictions, Class, .pred_Class1) |>
  autoplot()

With class imbalance, accuracy can hide poor minority-class performance. Combine it with sensitivity, specificity, precision, recall, F-measure, ROC AUC, or PR AUC.

7. fit_resamples(): assess a fixed workflow

When the model and hyperparameters are fixed, use fit_resamples() to estimate a performance distribution:

set.seed(1003)
log_resamples <- fit_resamples(
  log_wf,
  resamples = class_folds,
  metrics = class_metrics,
  control = control_resamples(save_pred = TRUE)
)

collect_metrics(log_resamples)
collect_predictions(log_resamples)
collect_notes(log_resamples)

The returned object is an rset-style tibble containing metrics/predictions list-columns for each split. collect_metrics() summarizes means, standard errors, and resample counts by default.

Inspect fold-level stability:

collect_predictions(log_resamples) |>
  group_by(id, id2) |>
  accuracy(Class, .pred_class)

8. dials and tune: parameter objects and search grids

8.1 Mark unknown parameters with tune()

tree_tune_spec <- decision_tree(
  cost_complexity = tune(),
  tree_depth = tune(),
  min_n = tune()
) |>
  set_mode("classification") |>
  set_engine("rpart")

tree_wf <- workflow(
  preprocessor = class_rec,
  spec = tree_tune_spec
)

tree_params <- extract_parameter_set_dials(tree_wf)
tree_params

tune() is only a placeholder. A dials parameter object stores type, range, transformation, and label.

8.2 update() and grid_*()

tree_params <- tree_params |>
  update(
    tree_depth = tree_depth(c(1L, 10L)),
    min_n = min_n(c(2L, 30L))
  )

set.seed(1004)
tree_grid <- grid_space_filling(
  tree_params,
  size = 15
)

tree_grid

Common grid functions:

Function Characteristic
grid_regular() Regular levels per parameter; combinations explode in high dimensions
grid_random() Random parameter combinations
grid_space_filling() Attempts to cover parameter space efficiently

Some parameters, such as random forest mtry(), have an upper bound determined by the number of predictors. Use finalize() with training data or extract the data-informed range from a workflow.

9. tune_grid(): search, compare, and select

set.seed(1005)
tree_results <- tune_grid(
  tree_wf,
  resamples = class_folds,
  grid = tree_grid,
  metrics = metric_set(roc_auc, accuracy),
  control = control_grid(
    save_pred = TRUE,
    save_workflow = TRUE
  )
)

collect_metrics(tree_results)
show_best(tree_results, metric = "roc_auc", n = 5)
autoplot(tree_results)

save_pred = TRUE makes out-of-fold predictions available later. save_workflow = TRUE lets fit_best() recover and fit the original workflow. Both options increase object size.

9.1 select_best() and robust selection rules

best_auc <- select_best(tree_results, metric = "roc_auc")
best_auc

final_tree_wf <- finalize_workflow(tree_wf, best_auc)

select_best() picks the numerical optimum. If simplicity and stability matter, consider:

simple_tree <- select_by_one_std_err(
  tree_results,
  metric = "roc_auc",
  tree_depth
)

select_by_one_std_err() uses expressions to specify the ordering toward a simpler model. Decide the primary metric and tie-breaking policy before examining final test performance.

9.2 tune_bayes() and advanced search

tune_bayes() iteratively proposes configurations based on previous results and is useful for expensive models. It requires an initial design and uses control_bayes() for iteration and saving behavior. Start with a space-filling grid for small, low-dimensional problems.

10. finalize_workflow(), last_fit(), and fit_best()

The test set must not participate in parameter selection. After choosing the final workflow:

final_tree_fit <- last_fit(
  final_tree_wf,
  split = class_split,
  metrics = metric_set(roc_auc, accuracy)
)

collect_metrics(final_tree_fit)
collect_predictions(final_tree_fit)

fitted_final_workflow <- extract_workflow(final_tree_fit)

last_fit() fits on all training data and assesses the test data once. Its result contains metrics, predictions, and the fitted workflow.

If you already have tuning results and want to fit the best configuration to a supplied data set:

# Fit to class_train without touching the test set.
best_tree_fit <- fit_best(
  tree_results,
  metric = "roc_auc"
)

fit_best() returns a fitted workflow. last_fit() also performs test-set assessment. Choose based on whether you have reached the final testing stage.

11. broom and tidy model results

broom converts engine-specific results into predictable tibbles:

tidy(log_wf_fit)
glance(log_wf_fit)

tidy(log_wf_fit, what = "recipe")

class_aug <- augment(log_wf_fit, new_data = class_test)
class_aug
  • tidy(): one coefficient, term, or component per row.
  • glance(): one-row model summary.
  • augment(): original data plus predictions/residuals.
  • Not every engine implements exactly the same tidiers; inspect the method documentation.

12. Complete binary-classification workflow

The full thread as a reusable template:

library(tidymodels)

data(two_class_dat, package = "modeldata")

set.seed(2001)
split_obj <- initial_split(two_class_dat, strata = Class)
train_dat <- training(split_obj)
folds <- vfold_cv(train_dat, v = 5, strata = Class)

rec <- recipe(Class ~ ., data = train_dat) |>
  step_zv(all_predictors()) |>
  step_normalize(all_numeric_predictors())

spec <- logistic_reg() |>
  set_engine("glm")

wf <- workflow(
  preprocessor = rec,
  spec = spec
)

cv_results <- fit_resamples(
  wf,
  resamples = folds,
  metrics = metric_set(roc_auc, accuracy)
)

collect_metrics(cv_results)

test_results <- last_fit(
  wf,
  split = split_obj,
  metrics = metric_set(roc_auc, accuracy)
)

collect_metrics(test_results)
final_model <- extract_workflow(test_results)

Use the final workflow for new predictions:

new_patients <- tibble(
  A = c(2.2, 3.0),
  B = c(1.4, 2.1)
)

predict(final_model, new_patients)
predict(final_model, new_patients, type = "prob")

13. Complete regression workflow

mtcars_tbl <- as_tibble(mtcars)

set.seed(3001)
mt_split <- initial_split(mtcars_tbl, prop = 0.75, strata = mpg)
mt_train <- training(mt_split)

mt_rec <- recipe(mpg ~ ., data = mt_train) |>
  step_zv(all_predictors()) |>
  step_normalize(all_numeric_predictors())

lm_spec <- linear_reg() |>
  set_engine("lm")

lm_wf <- workflow(
  preprocessor = mt_rec,
  spec = lm_spec
)

lm_last <- last_fit(
  lm_wf,
  split = mt_split,
  metrics = metric_set(rmse, mae, rsq)
)

collect_metrics(lm_last)
collect_predictions(lm_last)

Residual-oriented visualization:

lm_test_predictions <- collect_predictions(lm_last)

lm_test_predictions |>
  ggplot(aes(.pred, mpg)) +
  geom_abline(linetype = 2) +
  geom_point(size = 2) +
  coord_obs_pred() +
  labs(x = "Predicted mpg", y = "Observed mpg")

Test metrics from this tiny demonstration will be highly variable. Real projects need adequate data, appropriate resampling, and uncertainty intervals.

15. Common errors and production guidance

15.1 Data leakage

  • Computing means, standard deviations, PCA, or feature selection on all data before splitting.
  • Prepping once manually and passing the processed full training set into CV.
  • Allowing the same patient or future time records to cross folds.
  • Repeatedly modifying a model based on test-set results.

Put all learned preprocessing in a recipe and the recipe in a workflow.

15.2 Outcome and event level

A classification outcome should be a factor. Fix the positive/event level according to the domain definition before modeling. Character outcomes may be interpreted differently by engines.

15.3 Do not mix probability and class predictions

  • accuracy() and sens() need .pred_class.
  • roc_auc() and pr_auc() need the event probability.
  • Threshold-dependent and threshold-free metrics answer different questions.

15.4 Engine dependencies and reproducibility

show_engines("rand_forest")

# For example:
# install.packages("ranger")
# rand_forest(trees = 1000) |>
#   set_mode("classification") |>
#   set_engine("ranger")

Set random seeds, record package versions, and save the final workflow and training-data schema. Parallel tuning also needs a reproducible parallel random-number strategy.

15.5 Do not bypass the workflow for prediction

Even after extracting an engine:

# Correct: automatically runs the recipe.
predict(log_wf_fit, class_test)

# Not recommended: may bypass workflow preprocessing.
# predict(extract_fit_engine(log_wf_fit), class_test)

17. Extension packages and next steps

The wider tidymodels ecosystem includes:

Package Purpose
stacks Stacked model ensembles
finetune Racing, simulated annealing, and advanced tuning
probably Probability calibration, thresholds, and prediction intervals
tailor Workflow postprocessing steps
butcher Reduce fitted model object size
applicable Detect extrapolation in new data
textrecipes / themis Text features and class-imbalance recipe steps
censored Censored regression and survival model support

A useful learning order:

  1. Master split → recipe → specification → workflow.
  2. Learn yardstick metrics and fit_resamples().
  3. Add dials and tune.
  4. Move to workflowsets, parallel execution, ensembles, and deployment.
