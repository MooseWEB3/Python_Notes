1. What Shiny is and how to use this guide

Shiny is an R framework for building interactive web applications. You describe the interface with R functions, perform calculations in R, and let Shiny maintain the connection between browser inputs and R outputs. You can build useful applications without writing JavaScript, although HTML, CSS, and JavaScript remain available when you need deeper customization.

As of 2026-08-12, the current CRAN release is Shiny 1.14.0. The most important idea is not a particular widget. It is the reactive dependency graph:

browser input
     ↓
reactive expression
     ↓
render function
     ↓
browser output

Use this guide in layers:

  1. Run the first app and understand ui, server, input, and output.
  2. Learn reactive expressions before adding many widgets.
  3. Use validation and event control to make behavior predictable.
  4. Move repeated features into modules.
  5. Add caching, tests, and deployment controls only after the data flow is clear.

Shiny for R is different from Shiny for Python. This tutorial covers the R package.

2. Installation, app formats, and running an app

Install Shiny once, then load it in each R session:

install.packages("shiny")
library(shiny)

packageVersion("shiny")
runExample("01_hello")

2.1 The single-file app.R format

The simplest project is a directory containing one app.R file:

my_app/
└── app.R

app.R creates a UI object, a server function, and passes both to shinyApp():

library(shiny)

ui <- fluidPage(
  titlePanel("Hello Shiny"),
  sliderInput("n", "Number of observations", 10, 200, 50),
  plotOutput("histogram")
)

server <- function(input, output, session) {
  output$histogram <- renderPlot({
    hist(rnorm(input$n), col = "#1769aa", border = "white")
  })
}

shinyApp(ui, server)

Run the directory from R:

shiny::runApp("my_app")

# Useful during development
shiny::runApp("my_app", launch.browser = TRUE)

RStudio’s Run App button performs the same basic task. Stop a local app with the console’s Stop button or by interrupting the R process.

2.2 ui.R and server.R

Older and larger projects may split the app into ui.R and server.R. This format still works, but app.R plus ordinary helper files is often easier to navigate. Whichever format you choose, keep one convention per project.

3. The four objects that explain most Shiny code

Object Role Typical use
ui Describes browser structure and controls fluidPage(), sliderInput(), plotOutput()
server Runs once per browser session Create reactives, outputs, observers, and cleanup hooks
input Read-only, list-like reactive values from the browser input$bins, input$species
output List-like registry of render instructions output$plot <- renderPlot({...})
session Current client connection and namespace Update inputs, send messages, end-session cleanup

The string ID connects the browser placeholder to server logic:

# UI: reserve a location named "summary"
textOutput("summary")

# Server: define how "summary" is calculated
output$summary <- renderText({
  paste("Current value:", input$x)
})

The names must match exactly. A typo usually produces an empty output rather than a helpful compile-time error.

4. Building the user interface

4.1 Page and layout functions

Classic Shiny layouts are composed from nested tag objects:

ui <- fluidPage(
  titlePanel("Iris explorer"),
  sidebarLayout(
    sidebarPanel(
      selectInput(
        "species",
        "Species",
        choices = unique(iris$Species),
        selected = "setosa"
      )
    ),
    mainPanel(
      plotOutput("scatter"),
      tableOutput("rows")
    )
  )
)

Useful containers include:

Function Purpose
fluidPage() Responsive Bootstrap page
sidebarLayout() Sidebar plus main content
fluidRow() / column() Twelve-column responsive grid
tabsetPanel() / tabPanel() Tabbed content
navbarPage() Top-level navigation
fillPage() / fillRow() / fillCol() Fill available browser space
div(), span(), tags$... Raw HTML tag composition

For newer dashboard-like layouts and theming, Shiny imports bslib; bslib::page_sidebar(), page_navbar(), card(), and value_box() provide a modern alternative while preserving the same server model.

4.2 HTML tags and safe styling

ui <- fluidPage(
  tags$head(
    tags$style(HTML("\n      .important { color: #0e8f83; font-weight: 700; }\n    "))
  ),
  tags$h1("Sales monitor"),
  tags$p(class = "important", "Updated when filters change."),
  tags$hr(),
  tags$a(href = "https://shiny.posit.co/", "Official Shiny website")
)

Prefer www/styles.css for substantial CSS. Avoid inserting untrusted user text with HTML() because it disables HTML escaping. Ordinary character strings are escaped by htmltools.

5. Inputs: values coming from the browser

Every input has an inputId, a label, and type-specific arguments. Its current value appears at input$inputId.

ui <- fluidPage(
  textInput("name", "Name", value = "Ada"),
  numericInput("age", "Age", value = 30, min = 0),
  sliderInput("range", "Range", min = 0, max = 100, value = c(20, 80)),
  selectInput("group", "Group", choices = c("A", "B", "C")),
  checkboxInput("smooth", "Add smoother", value = TRUE),
  checkboxGroupInput("vars", "Variables", choices = names(mtcars)),
  radioButtons("format", "Format", choices = c("Table", "Plot")),
  dateInput("date", "Date"),
  actionButton("go", "Calculate")
)

Important value shapes:

Input Server value
textInput() Length-one character string
numericInput() Number, sometimes NA during editing
sliderInput() One number or a two-number range
selectInput(multiple = TRUE) Character vector, possibly empty/NULL
checkboxInput() TRUE or FALSE
actionButton() Integer click count; use it as an event, not business data
fileInput() Data frame describing the uploaded temporary file

Never assign directly to input$x. To change a control from the server, use an update*() function.

6. Outputs and matching render functions

Most visible outputs use a UI placeholder and a server renderer.

UI function Server function Expected value
textOutput() renderText() Character text
verbatimTextOutput() renderPrint() Printed R output
plotOutput() renderPlot() Base or grid plot
tableOutput() renderTable() Data frame or matrix
uiOutput() renderUI() HTML tags
imageOutput() renderImage() Image metadata list
downloadButton() downloadHandler() Download response 
server <- function(input, output, session) {
  output$message <- renderText({
    paste("Hello", input$name)
  })

  output$model <- renderPrint({
    summary(lm(mpg ~ wt + hp, data = mtcars))
  })

  output$plot <- renderPlot({
    plot(mtcars$wt, mtcars$mpg, pch = 19, col = "#1769aa")
  })

  output$table <- renderTable({
    head(mtcars, input$n)
  }, striped = TRUE, bordered = TRUE)
}

Use a widget-specific output/render pair for htmlwidgets, such as DT::DTOutput() with DT::renderDT() or plotly::plotlyOutput() with plotly::renderPlotly().

7. Reactivity: the core mental model

7.1 Dependency tracking and invalidation

When code inside a reactive consumer reads input$x or calls another reactive expression, Shiny records a dependency. When an upstream value changes, downstream nodes become invalid. They recalculate only when needed.

filtered_rows <- reactive({
  mtcars[mtcars$cyl == input$cyl, , drop = FALSE]
})

output$count <- renderText({
  paste(nrow(filtered_rows()), "rows")
})

output$table <- renderTable({
  filtered_rows()
})

Notice the parentheses: filtered_rows is a reactive expression object, while filtered_rows() reads its current value.

7.2 Reactive expressions versus observers

Use reactive() for a calculated value. Use observe() for a side effect.

# Returns a value and is lazy/cached
selected_data <- reactive({
  subset(iris, Species %in% input$species)
})

# Performs a side effect and does not return a useful value
observe({
  message("Selected rows: ", nrow(selected_data()))
})

A good rule is: data transformation belongs in a reactive expression; notifications, input updates, logging, and writes belong in an observer.

7.3 isolate()

isolate() reads a reactive value without creating a dependency:

observeEvent(input$log_now, {
  message("Current filter: ", isolate(input$species))
})

Use it deliberately. Excessive isolation hides the dependency graph and often creates stale interfaces.

8. First complete app: interactive mtcars explorer

Save the following as app.R and run shiny::runApp() from its directory.

library(shiny)

ui <- fluidPage(
  titlePanel("mtcars explorer"),
  sidebarLayout(
    sidebarPanel(
      checkboxGroupInput(
        "cyl",
        "Cylinders",
        choices = sort(unique(mtcars$cyl)),
        selected = sort(unique(mtcars$cyl))
      ),
      selectInput(
        "x",
        "X variable",
        choices = c("Weight" = "wt", "Horsepower" = "hp")
      ),
      sliderInput("point_size", "Point size", 1, 5, 2)
    ),
    mainPanel(
      textOutput("summary"),
      plotOutput("scatter", height = 420),
      tableOutput("preview")
    )
  )
)

server <- function(input, output, session) {
  cars <- reactive({
    req(input$cyl)
    mtcars[mtcars$cyl %in% as.numeric(input$cyl), , drop = FALSE]
  })

  output$summary <- renderText({
    sprintf(
      "%d cars; mean mpg = %.1f",
      nrow(cars()),
      mean(cars()$mpg)
    )
  })

  output$scatter <- renderPlot({
    x <- cars()[[input$x]]
    plot(
      x,
      cars()$mpg,
      xlab = input$x,
      ylab = "mpg",
      pch = 19,
      cex = input$point_size,
      col = "#1769aa"
    )
    grid()
  })

  output$preview <- renderTable({
    head(cars(), 10)
  }, rownames = TRUE)
}

shinyApp(ui, server)

One reactive expression supplies three downstream outputs. Filtering is therefore written once and cached until input$cyl changes.

9. Missing inputs, validation, and user-facing errors

9.1 req() for prerequisites

req() stops the current reactive chain silently when a required value is not truthy:

uploaded <- reactive({
  req(input$file)
  read.csv(input$file$datapath, check.names = FALSE)
})

Use cancelOutput = TRUE when the last valid output should remain visible while a prerequisite is temporarily missing:

output$plot <- renderPlot({
  req(input$variable, cancelOutput = TRUE)
  hist(dataset()[[input$variable]])
})

9.2 validate() and need() for explanatory messages

output$scatter <- renderPlot({
  validate(
    need(length(input$vars) == 2, "Select exactly two variables."),
    need(all(input$vars %in% names(mtcars)), "Unknown variable selected.")
  )

  plot(mtcars[[input$vars[1]]], mtcars[[input$vars[2]]])
})

Use req() when no explanation is needed; use validate(need(...)) when the user needs a corrective message. Do not expose database details, secrets, or full stack traces in production error messages.

10. Event-driven behavior with bindEvent()

Normal reactive code updates whenever any dependency changes. Sometimes you want a calculation only after a button click. Modern Shiny provides bindEvent() for reactive expressions, observers, and render functions.

result <- reactive({
  Sys.sleep(1)
  input$x ^ input$power
}) |>
  bindEvent(input$calculate)

output$result <- renderText({
  paste("Result:", result())
})

For a side effect:

observe({
  showNotification("Settings saved", type = "message")
}) |>
  bindEvent(input$save, ignoreInit = TRUE)

Older code often uses eventReactive() and observeEvent(). They remain valid. bindEvent() is more composable and can also wrap render functions and combine with bindCache().

Key arguments:

Argument Meaning
ignoreNULL = TRUE Do not run for NULL or action-button value 0
ignoreInit = TRUE Do not run when the observer/reactive is first created
once = TRUE Destroy an observer after its first execution

11. Mutable reactive state

11.1 One value with reactiveVal()

Calling without an argument reads the value; calling with an argument sets it.

server <- function(input, output, session) {
  count <- reactiveVal(0)

  observeEvent(input$add, {
    count(count() + 1)
  })

  observeEvent(input$reset, {
    count(0)
  })

  output$count <- renderText(count())
}

11.2 Several values with reactiveValues()

state <- reactiveValues(
  data = NULL,
  status = "idle",
  last_updated = NULL
)

observeEvent(input$refresh, {
  state$status <- "loading"
  state$data <- load_data()
  state$last_updated <- Sys.time()
  state$status <- "ready"
})

Only individual fields that are read become dependencies. Keep session-specific state inside server; an object created outside server is shared across sessions and can leak one user’s state to another.

12. Updating inputs and generating dynamic UI

12.1 update*() functions

The server can change an existing browser control through session:

observeEvent(input$dataset, {
  data <- get(input$dataset, "package:datasets")
  numeric_vars <- names(data)[vapply(data, is.numeric, logical(1))]

  updateSelectInput(
    session,
    "variable",
    choices = numeric_vars,
    selected = numeric_vars[1]
  )
})

There are matching functions such as updateTextInput(), updateSliderInput(), updateCheckboxInput(), and updateTabsetPanel().

12.2 conditionalPanel() versus renderUI()

conditionalPanel() hides or shows existing browser-side UI:

conditionalPanel(
  condition = "input.plot_type == 'histogram'",
  sliderInput("bins", "Bins", min = 5, max = 80, value = 30)
)

The condition is JavaScript syntax and is not a security boundary. Hidden values can still be manipulated by a client.

renderUI() creates UI on the server:

uiOutput("parameter_ui")

output$parameter_ui <- renderUI({
  if (input$model == "linear") {
    checkboxInput("intercept", "Include intercept", TRUE)
  } else {
    sliderInput("degree", "Polynomial degree", 1, 5, 2)
  }
})

Prefer updating a stable input over repeatedly destroying and recreating it. Dynamic UI can reset values and makes the reactive graph harder to inspect.

13. Uploads, downloads, and temporary files

13.1 CSV upload

input$file is a data frame with fields including name, size, type, and datapath. Read the server-managed temporary path, not the original client filename.

ui <- fluidPage(
  fileInput("file", "Upload CSV", accept = c(".csv", "text/csv")),
  checkboxInput("header", "Header row", TRUE),
  tableOutput("preview")
)

server <- function(input, output, session) {
  uploaded <- reactive({
    req(input$file)
    validate(need(input$file$size <= 5 * 1024^2, "Maximum size is 5 MB."))

    read.csv(
      input$file$datapath,
      header = input$header,
      check.names = FALSE
    )
  })

  output$preview <- renderTable(head(uploaded(), 20))
}

The accept argument helps the file chooser but is not server-side validation. Enforce size, extension, content, and schema rules after upload. Avoid deserializing untrusted R objects with readRDS().

13.2 Download handler

ui <- fluidPage(downloadButton("download", "Download filtered CSV"))

server <- function(input, output, session) {
  filtered <- reactive({
    mtcars[mtcars$cyl %in% input$cyl, , drop = FALSE]
  })

  output$download <- downloadHandler(
    filename = function() {
      paste0("mtcars-", Sys.Date(), ".csv")
    },
    content = function(file) {
      write.csv(filtered(), file, row.names = FALSE)
    },
    contentType = "text/csv"
  )
}

content receives a temporary output path. Write the file there; do not treat it as the user’s requested local path.

14. Modules: reusable, testable features

A module has a UI function and a server function. NS() namespaces browser IDs; moduleServer() creates the matching server scope.

filterUI <- function(id) {
  ns <- NS(id)

  tagList(
    selectInput(
      ns("species"),
      "Species",
      choices = levels(iris$Species),
      multiple = TRUE,
      selected = levels(iris$Species)
    ),
    textOutput(ns("count"))
  )
}

filterServer <- function(id, data) {
  moduleServer(id, function(input, output, session) {
    filtered <- reactive({
      req(input$species)
      data()[data()$Species %in% input$species, , drop = FALSE]
    })

    output$count <- renderText({
      paste(nrow(filtered()), "rows")
    })

    filtered
  })
}

Use the module twice without ID collisions:

ui <- fluidPage(
  filterUI("left"),
  tableOutput("left_table"),
  filterUI("right"),
  tableOutput("right_table")
)

server <- function(input, output, session) {
  source_data <- reactive(iris)

  left_data <- filterServer("left", source_data)
  right_data <- filterServer("right", source_data)

  output$left_table <- renderTable(left_data())
  output$right_table <- renderTable(right_data())
}

Pass ordinary values or reactive expressions explicitly. Avoid modules that reach into unrelated global variables. moduleServer() is preferred over older callModule() syntax and works naturally with testServer().

15. Performance: debounce, caching, and scope

15.1 Reduce noisy invalidations

debounce() waits until changes pause; throttle() limits the update rate.

search_text <- reactive(input$search) |>
  debounce(millis = 400)

matches <- reactive({
  grep(search_text(), rownames(mtcars), value = TRUE, ignore.case = TRUE)
})

15.2 Cache expensive calculations

A normal reactive() remembers only its most recent value. bindCache() can retain multiple keyed values and, with app-scoped caching, share results across sessions.

fit <- reactive({
  Sys.sleep(2)
  lm(reformulate(input$predictors, response = input$response), data = data())
}) |>
  bindCache(input$response, input$predictors, data_version()) |>
  bindEvent(input$fit)

The cache key must include every reactive input or external-data version that can affect the result. Keep keys cheap to serialize and hash. The required order is bindCache() first, then bindEvent().

15.3 Put work in the right scope

# Runs once when the R process starts; shared and read-only is safest
lookup_table <- read.csv("data/lookup.csv")

server <- function(input, output, session) {
  # Runs once per browser session
  session_state <- reactiveValues(selected = character())

  session$onSessionEnded(function() {
    message("Session ended")
  })
}

Loading immutable reference data outside server can save memory and time. Never place mutable user-specific data there unless deliberate cross-session sharing is required and properly synchronized.

16. Long-running work with ExtendedTask

Ordinary reactive calculations block their current session while running. ExtendedTask runs an asynchronous function in the background so that the same browser session can remain responsive. The task function should receive input values as arguments rather than reading reactive inputs internally.

This optional example uses mirai and modern bslib task buttons:

library(shiny)
library(bslib)
library(mirai)

daemons(1)
onStop(function() daemons(0))

ui <- page_fluid(
  numericInput("n", "Calculate up to n", value = 100, min = 1),
  input_task_button("go", "Run slow calculation"),
  textOutput("status"),
  textOutput("result")
)

server <- function(input, output, session) {
  slow_sum <- ExtendedTask$new(function(n) {
    mirai({
      Sys.sleep(2)
      sum(seq_len(n))
    }, n = n)
  }) |>
    bind_task_button("go")

  observeEvent(input$go, {
    req(input$n >= 1)
    slow_sum$invoke(input$n)
  })

  output$status <- renderText(slow_sum$status())
  output$result <- renderText({
    paste("Result:", slow_sum$result())
  })
}

shinyApp(ui, server)

Each ExtendedTask object queues overlapping invocations instead of running them simultaneously. Use this pattern only after measuring a real blocking problem.

17. Testing and debugging

17.1 Extract pure functions first

Pure R functions are the easiest code to test:

filter_cylinders <- function(data, cylinders) {
  stopifnot(is.data.frame(data))
  data[data$cyl %in% cylinders, , drop = FALSE]
}

stopifnot(nrow(filter_cylinders(mtcars, 4)) == 11)

17.2 Test server logic with testServer()

server <- function(input, output, session) {
  product <- reactive(input$a * input$b)
}

testServer(server, {
  session$setInputs(a = 6, b = 7)
  stopifnot(product() == 42)
})

testServer() can also test module server functions. Use shinytest2 when you need browser-level snapshots and interactions.

17.3 Inspect the reactive graph

install.packages("reactlog")

options(shiny.reactlog = TRUE)
shiny::runApp()

# After exercising the app, press Ctrl+F3 in the browser,
# or inspect the last log from R:
shiny::reactlogShow()

Useful debugging habits:

  • Give important reactives labels: reactive({...}, label = "filtered data").
  • Inspect browser developer-console errors for JavaScript or resource failures.
  • Log identifiers and timings, but never secrets or uploaded data contents.
  • Reproduce with the smallest app that still fails.
  • Profile before optimizing; use profvis for CPU work and reactlog for invalidation problems.

18. Project organization and dependency boundaries

A maintainable medium-sized app might use:

my_app/
├── app.R
├── R/
│   ├── data.R
│   ├── mod_filter.R
│   ├── mod_summary.R
│   └── utilities.R
├── data/
│   └── lookup.csv
├── www/
│   └── styles.css
├── tests/
│   └── testthat/
├── renv.lock
└── README.md

Recommended boundaries:

  1. Pure domain functions should not know about input or output.
  2. Reactive expressions adapt domain functions to changing values.
  3. Modules own a coherent feature and expose explicit return values.
  4. The top-level server wires modules together.
  5. External resources such as databases should use connection pooling and parameterized queries.

Use renv to record package versions when reproducibility matters:

install.packages("renv")
renv::init()
renv::snapshot()

19. Deployment and production checklist

Common hosting choices include shinyapps.io, Posit Connect, and Shiny Server. A deployment uploads the application and its required files; the static tutorial HTML you are reading is not itself a running Shiny server.

Before deployment:

  • Start the app in a clean R session and exercise every input path.
  • Pin dependencies and confirm the required R version.
  • Keep credentials in environment variables or a secret store, never source files.
  • Treat browser input, uploaded files, URL parameters, and database text as untrusted.
  • Use parameterized SQL; never paste user input into a query.
  • Set upload, runtime, memory, and result-size limits.
  • Escape user text and avoid HTML(untrusted_text).
  • Do not rely on hidden UI for authorization; enforce access on the server.
  • Separate global read-only data from per-session mutable state.
  • Add logging, health monitoring, and user-safe error messages.
  • Test simultaneous sessions and slow operations, not only one browser tab.

A minimal shinyapps.io deployment uses the separate rsconnect package:

install.packages("rsconnect")

# Configure the account once, then deploy the app directory.
# Never commit account tokens to the repository.
rsconnect::deployApp("my_app")

20. Complete example: upload, filter, visualize, and download

This app combines the main patterns. If no file is uploaded, it uses iris; otherwise it reads a CSV. It updates the variable selector, validates numeric plotting columns, filters rows, and provides a download.

library(shiny)

ui <- fluidPage(
  titlePanel("Data explorer"),
  sidebarLayout(
    sidebarPanel(
      fileInput("file", "Optional CSV", accept = ".csv"),
      selectInput("x", "Numeric variable", choices = NULL),
      sliderInput("rows", "Rows to show", 5, 50, 10),
      actionButton("refresh", "Apply settings"),
      downloadButton("download", "Download current data")
    ),
    mainPanel(
      textOutput("status"),
      plotOutput("histogram"),
      tableOutput("preview")
    )
  )
)

server <- function(input, output, session) {
  raw_data <- reactive({
    if (is.null(input$file)) {
      iris
    } else {
      validate(need(input$file$size <= 5 * 1024^2, "CSV must be 5 MB or smaller."))
      read.csv(input$file$datapath, check.names = FALSE)
    }
  })

  observeEvent(raw_data(), {
    numeric_vars <- names(raw_data())[vapply(raw_data(), is.numeric, logical(1))]
    updateSelectInput(session, "x", choices = numeric_vars)
  }, ignoreInit = FALSE)

  selected_data <- reactive({
    data <- raw_data()
    validate(need(input$x %in% names(data), "Choose a numeric variable."))
    validate(need(is.numeric(data[[input$x]]), "The selected variable is not numeric."))
    data
  }) |>
    bindEvent(input$refresh, raw_data())

  output$status <- renderText({
    sprintf("%d rows and %d columns", nrow(selected_data()), ncol(selected_data()))
  })

  output$histogram <- renderPlot({
    hist(
      selected_data()[[input$x]],
      main = input$x,
      xlab = input$x,
      col = "#1769aa",
      border = "white"
    )
  })

  output$preview <- renderTable({
    head(selected_data(), input$rows)
  })

  output$download <- downloadHandler(
    filename = function() paste0("data-", Sys.Date(), ".csv"),
    content = function(file) write.csv(selected_data(), file, row.names = FALSE)
  )
}

shinyApp(ui, server)

For a production app, move the upload/selection feature into a module, add explicit schema rules, and test the server logic.

22. Common mistakes

  1. Forgetting () when reading a reactive expression.
  2. Using an observer to calculate reusable data instead of reactive().
  3. Performing expensive work independently in several outputs.
  4. Reading input$... outside a reactive consumer.
  5. Expecting conditionalPanel() to enforce security.
  6. Recreating controls with renderUI() when an update*() call is enough.
  7. Omitting a dependency from a bindCache() key.
  8. Storing user-specific mutable state outside server.
  9. Trusting uploaded filenames, extensions, MIME types, or contents.
  10. Building one huge server function instead of extracting pure functions and modules.
