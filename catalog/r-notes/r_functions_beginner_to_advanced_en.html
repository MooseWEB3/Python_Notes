How to use this guide

This tutorial builds one layer at a time. The beginner section teaches function syntax and contracts. The intermediate section explains the language mechanisms that make R functions distinctive. The advanced section turns those mechanisms into reusable abstractions and production-quality APIs.

Do not try to memorize every pattern. Instead, retain three questions:

  1. What inputs does the function accept?
  2. What output and side effects does it promise?
  3. In which environment, and at what time, are names and arguments evaluated?

If those questions have clear answers, most function code becomes easier to test, compose, and maintain.

A function-quality ladder

A function often evolves through these stages:

  • Works once: the happy path produces the expected result.
  • Has a contract: accepted inputs, output type, missing-value behavior, and errors are defined.
  • Composes: it returns a stable shape, avoids hidden state, and separates computation from side effects.
  • Is observable: errors contain context, tests protect behavior, and profiling can locate cost.
  • Is extensible: higher-order functions, generics, or metaprogramming are introduced only when a real reuse problem requires them.

Part I — Beginner foundations

1. Your first function

A function packages a computation behind a name. The basic syntax has an argument list and a body:

circle_area <- function(radius) {
  pi * radius^2
}

circle_area(3)
# [1] 28.27433

R also supports a concise anonymous-function syntax, available in modern R:

square <- \(x) x^2
square(5)
# [1] 25

Use a named function when the behavior deserves a reusable name, documentation, or tests. Use an anonymous function for a short local transformation:

numbers <- 1:5
vapply(numbers, \(x) x^2, numeric(1))
# [1]  1  4  9 16 25

Every ordinary R closure has three components:

  • formals: its argument definitions;
  • body: the code that is evaluated;
  • environment: the enclosing environment used to resolve free names.
formals(circle_area)
body(circle_area)
environment(circle_area)

This is more than introspection trivia. The environment is why a function can use pi even though pi is not an argument, and it later enables closures and function factories.

Naming and shape

Prefer a verb for an action and a noun for a constructor or accessor. Names such as calculate_tax(), validate_order(), new_customer(), and customer_id() communicate intent better than process() or do_it().

The body may be one expression, but braces are usually clearer once validation or intermediate names appear:

fahrenheit_to_celsius <- function(fahrenheit) {
  celsius <- (fahrenheit - 32) * 5 / 9
  celsius
}

The final expression is returned automatically. An explicit return() is most useful for early exits, not as mandatory punctuation at the bottom of every function.

Beginner checklist

  • Can the function name be read as a clear action?
  • Does each argument have one understandable role?
  • Is the returned value obvious from the final expression?
  • Can you call it with a tiny example?

Key lesson. A function is an object containing code plus an environment, not just a textual block.

2. Arguments, defaults, and matching

Arguments define the public controls of a function. Required arguments have no default; optional arguments do:

rescale <- function(x, to = c(0, 1), na.rm = FALSE) {
  limits <- range(x, na.rm = na.rm)
  (x - limits[1]) / diff(limits) * diff(to) + to[1]
}

rescale(c(10, 20, 30))
rescale(c(10, 20, 30), to = c(-1, 1))

Choose defaults that are safe and common. Avoid a default that silently discards information or performs an expensive side effect.

R matches arguments in three stages for ordinary calls:

  1. exact name;
  2. partial name;
  3. position.

Partial matching is convenient interactively but fragile in maintained code. Prefer exact names for optional or easily confused arguments:

round(x = 3.14159, digits = 2)

Put the main data argument first, followed by the most frequently changed controls. This makes pipe-oriented calls natural:

trim_range <- function(x, lower = 0.05, upper = 0.95, na.rm = TRUE) {
  bounds <- quantile(x, probs = c(lower, upper), na.rm = na.rm)
  x[x >= bounds[1] & x <= bounds[2]]
}

values |> trim_range(lower = 0.10)

Defaults are expressions

A default can refer to an earlier argument because it is evaluated inside the function call:

label_values <- function(x, labels = names(x)) {
  if (is.null(labels)) {
    labels <- seq_along(x)
  }
  paste0(labels, ": ", x)
}

This is useful, but complex defaults can hide work. If a default needs several steps or can fail, consider using NULL as a sentinel and compute the value explicitly:

sample_rows <- function(data, size = NULL) {
  if (is.null(size)) {
    size <- min(10L, nrow(data))
  }
  data[sample.int(nrow(data), size), , drop = FALSE]
}

Detecting a missing argument

Sometimes “not supplied” differs from NULL:

show_setting <- function(value) {
  if (missing(value)) {
    return("No argument was supplied")
  }
  if (is.null(value)) {
    return("NULL was supplied explicitly")
  }
  value
}

Use this distinction sparingly. Most APIs are simpler when a documented sentinel such as NULL represents automatic behavior.

Match choice arguments explicitly

For a small fixed set of string choices, match.arg() validates and normalizes:

center_data <- function(x, method = c("mean", "median", "none")) {
  method <- match.arg(method)

  center <- switch(
    method,
    mean = mean(x),
    median = median(x),
    none = 0
  )

  x - center
}

Key lesson. Argument order, names, and defaults are API design—not merely syntax.

3. Return values and output contracts

R returns the value of the final expression:

range_width <- function(x, na.rm = FALSE) {
  limits <- range(x, na.rm = na.rm)
  diff(limits)
}

Use an early return() to handle guard clauses:

safe_ratio <- function(numerator, denominator) {
  if (length(numerator) == 0L || length(denominator) == 0L) {
    return(numeric())
  }

  if (any(denominator == 0)) {
    stop("denominator must not contain zero", call. = FALSE)
  }

  numerator / denominator
}

The output contract includes more than the value:

  • type: logical, integer, double, character, list, data frame, or classed object;
  • length and dimensions;
  • names and other attributes;
  • behavior for empty input and missing values;
  • whether the value is visible;
  • possible conditions and side effects.

Return one stable shape

A function that sometimes returns a vector, sometimes a data frame, and sometimes NULL forces every caller to branch. Prefer a consistent type:

numeric_summary <- function(x, na.rm = TRUE) {
  data.frame(
    n = length(x),
    missing = sum(is.na(x)),
    mean = mean(x, na.rm = na.rm),
    sd = sd(x, na.rm = na.rm)
  )
}

For multiple related results, use a named list:

fit_line <- function(x, y) {
  model <- lm(y ~ x)

  list(
    model = model,
    coefficients = coef(model),
    fitted = fitted(model),
    residuals = residuals(model)
  )
}

Visible and invisible returns

A function called mainly for a side effect can invisibly return a useful value:

save_report <- function(text, path) {
  writeLines(text, path)
  invisible(normalizePath(path, mustWork = FALSE))
}

The console stays quiet, but callers can still assign or pipe the path. Replacement functions and print methods also commonly use invisible returns.

Empty input is part of the contract

Decide intentionally:

first_or <- function(x, default = NULL) {
  if (length(x) == 0L) {
    return(default)
  }
  x[[1]]
}

Do not let an accidental “subscript out of bounds” error define the API for you.

Key lesson. A reliable function promises a stable output type and shape for normal, missing, and empty inputs.

4. Input validation and informative errors

Validation should occur near the function boundary and should test conditions required by the implementation—not every imaginable property.

weighted_average <- function(x, weights, na.rm = FALSE) {
  if (!is.numeric(x)) {
    stop("x must be a numeric vector", call. = FALSE)
  }
  if (!is.numeric(weights)) {
    stop("weights must be a numeric vector", call. = FALSE)
  }
  if (length(x) != length(weights)) {
    stop("x and weights must have the same length", call. = FALSE)
  }
  if (any(weights < 0, na.rm = TRUE)) {
    stop("weights must be non-negative", call. = FALSE)
  }

  weighted.mean(x, weights, na.rm = na.rm)
}

Good errors answer three questions:

  1. Which argument is wrong?
  2. What was required?
  3. What relevant property was received?
assert_scalar_number <- function(x, arg = "x") {
  ok <- is.numeric(x) && length(x) == 1L && !is.na(x) && is.finite(x)

  if (!ok) {
    stop(
      sprintf("%s must be one finite, non-missing number", arg),
      call. = FALSE
    )
  }

  invisible(x)
}

Return the checked value invisibly so the helper works both as a statement and inside a pipeline.

Errors versus warnings

Use an error when a valid result cannot be produced. Use a warning when a result is returned but may be surprising. Use a message for progress or diagnostics that a user may suppress.

log_positive <- function(x) {
  if (any(x < 0, na.rm = TRUE)) {
    stop("x must not contain negative values", call. = FALSE)
  }
  if (any(x == 0, na.rm = TRUE)) {
    warning("zero values produce -Inf", call. = FALSE)
  }
  log(x)
}

Do not use print() for warnings or progress. Printed text is difficult for callers to classify or suppress.

Avoid over-validation

Repeatedly scanning a huge vector can dominate runtime. Validate structural properties once, combine checks when possible, and trust internal helpers after a public boundary has established invariants.

Key lesson. Validation is executable documentation of the function contract.

5. Vectorization, recycling, and missing values

R functions often receive vectors even when the example uses a single number. Decide whether your function is scalar, vectorized, or summary-producing.

discount_price <- function(price, discount = 0) {
  price * (1 - discount)
}

discount_price(c(100, 80, 50), discount = 0.10)
# [1] 90 72 45

This function is naturally vectorized because its primitives are vectorized. However, recycling can hide mistakes:

discount_price(c(100, 80, 50), c(0.10, 0.20))
# A warning is expected because lengths are incompatible.

If only scalar controls are allowed, assert them:

discount_price <- function(price, discount = 0) {
  if (!is.numeric(price)) {
    stop("price must be numeric", call. = FALSE)
  }
  if (!is.numeric(discount) || length(discount) != 1L || is.na(discount)) {
    stop("discount must be one non-missing number", call. = FALSE)
  }
  if (discount < 0 || discount > 1) {
    stop("discount must be between 0 and 1", call. = FALSE)
  }

  price * (1 - discount)
}

Missing-value policy

Do not silently choose na.rm = TRUE unless dropping missing observations is unquestionably correct. Expose the choice or document it:

coefficient_of_variation <- function(x, na.rm = FALSE) {
  average <- mean(x, na.rm = na.rm)

  if (is.na(average)) {
    return(NA_real_)
  }
  if (average == 0) {
    stop("coefficient of variation is undefined when mean(x) is zero",
         call. = FALSE)
  }

  sd(x, na.rm = na.rm) / average
}

Use typed missing values when output type matters: NA_integer_, NA_real_, NA_character_, or NA_complex_.

Simplification and attributes

Some vectorized helpers simplify or coerce results. Confirm that dates, factors, names, and dimensions are preserved when your contract requires them. Use seq_along(x) instead of 1:length(x), because the former correctly produces an empty integer vector for empty input.

Key lesson. Vectorized code is still an API: define recycling, missingness, and output attributes rather than inheriting accidental behavior.

Part II — Intermediate R function design

6. Lexical scoping and environments

When R encounters a name inside a function, it first looks in the current execution environment, then follows the chain of enclosing environments. This is lexical scoping: where a function was created matters more than where it is called.

tax_rate <- 0.05

calculate_total <- function(subtotal) {
  subtotal * (1 + tax_rate)
}

calculate_total(100)
# [1] 105

Here tax_rate is a free variable. The function finds it in its enclosing environment. Changing that global binding changes later results, which may be convenient interactively but creates a hidden dependency.

Prefer passing essential configuration explicitly:

calculate_total <- function(subtotal, tax_rate) {
  subtotal * (1 + tax_rate)
}

Local names do not leak

Every call creates a new execution environment:

standardize <- function(x) {
  center <- mean(x)
  spread <- sd(x)
  (x - center) / spread
}

# center and spread do not appear in the caller.

Assignment with <- creates or changes a local binding by default. Superassignment with <<- searches enclosing environments and mutates the first existing binding. Because that side effect is non-local, it should be confined to carefully designed closures.

Inspecting a closure

environment(calculate_total)
parent.env(environment(calculate_total))
environmentName(globalenv())

Do not confuse the enclosing environment with the caller environment. The enclosing environment controls lexical lookup. The caller is a runtime relationship visible in the call stack and can be accessed with tools such as parent.frame() when an API genuinely needs it.

Dependency injection

Passing dependencies as functions makes behavior testable:

fetch_and_parse <- function(url, fetch = download.file, parse = readLines) {
  path <- tempfile()
  on.exit(unlink(path), add = TRUE)

  fetch(url, path, quiet = TRUE)
  parse(path, warn = FALSE)
}

Tests can provide fake fetch and parse functions without network access.

Key lesson. A function’s environment is part of its behavior. Make important dependencies explicit and use captured state deliberately.

7. Lazy evaluation and promises

R arguments are promises. Each promise stores the supplied expression and the caller’s environment. It is evaluated only when the argument is first used, and the value is then cached.

first_only <- function(x, y) {
  x
}

first_only(10, stop("y is never evaluated"))
# [1] 10

Lazy evaluation enables useful defaults:

plot_centered <- function(x, center = mean(x, na.rm = TRUE)) {
  plot(x - center)
  invisible(center)
}

It also delays errors. A bad argument may fail far from the call site when it is first forced. If an argument must be checked or captured immediately, force it near the boundary:

make_adder <- function(amount) {
  force(amount)
  function(x) x + amount
}

Side effects in arguments are confusing

repeat_value <- function(x) {
  c(x, x)
}

counter <- 0
repeat_value({
  counter <- counter + 1
  counter
})

# The promise is evaluated once, so the result is c(1, 1).

Avoid relying on this subtlety in ordinary APIs. Compute side-effecting expressions before the call.

Defaults and supplied arguments use different environments

Default expressions are evaluated inside the function’s execution environment. Supplied expressions are evaluated in the caller’s environment:

x <- 100

where_is_x <- function(value = x) {
  x <- 10
  value
}

where_is_x()
# [1] 10

where_is_x(x)
# [1] 100

Understanding this rule removes many apparent scoping paradoxes.

Key lesson. An argument is initially a delayed computation, not merely a value. Know when forcing occurs.

8. The dots argument and forwarding

The … argument collects inputs that did not match named formals. Its most common use is forwarding options to another function:

plot_series <- function(x, y, main = NULL, ...) {
  if (is.null(main)) {
    main <- "Series"
  }
  plot(x, y, main = main, ...)
}

plot_series(1:10, (1:10)^2, col = "steelblue", pch = 19)

This makes wrappers flexible, but it also hides the accepted interface. A misspelled forwarded argument may be ignored or fail far downstream. Keep important controls as explicit arguments.

Capture and inspect dots

collect_options <- function(...) {
  options <- list(...)

  if (is.null(names(options))) {
    names(options) <- rep("", length(options))
  }

  options
}

Modern base R also exposes …length(), …names(), and …elt() for low-level access without necessarily building a list.

Reject unused arguments

A strict public function can reserve dots for future extension while rejecting current inputs:

calculate_score <- function(x, ..., na.rm = FALSE) {
  extra <- list(...)
  if (length(extra) > 0L) {
    stop(
      "Unused arguments: ",
      paste(names(extra), collapse = ", "),
      call. = FALSE
    )
  }
  mean(x, na.rm = na.rm)
}

Programmatic calls

When arguments are already stored in a list, do.call() constructs a call:

options <- list(x = c(1, 3, 8), na.rm = TRUE)
do.call(mean, options)

Do not parse strings to create ordinary calls. A function plus a named argument list is safer and clearer.

A forwarding guideline

If a constant argument belongs to the inner function, an explicit anonymous wrapper often produces clearer errors:

lapply(files, \(path) read.csv(path, stringsAsFactors = FALSE))

This is clearer than placing many unnamed constants after the mapped function.

Key lesson. Dots are an interface escape hatch. Forward narrowly, document the destination, and validate when ambiguity would be costly.

9. Functions as values and higher-order functions

Functions can be stored in variables, lists, and data frames; supplied as arguments; or returned as results.

operations <- list(
  add = \(x, y) x + y,
  multiply = \(x, y) x * y,
  maximum = max
)

operations$multiply(6, 7)
# [1] 42

A higher-order function consumes or produces functions:

apply_twice <- function(f, x) {
  f(f(x))
}

apply_twice(sqrt, 16)
# [1] 2

Validate function arguments with is.function() when misuse would otherwise generate a cryptic call error:

apply_safely <- function(f, x) {
  if (!is.function(f)) {
    stop("f must be a function", call. = FALSE)
  }
  f(x)
}

Composition

Composition connects the output of one function to the input of another:

compose2 <- function(f, g) {
  force(f)
  force(g)
  function(...) f(g(...))
}

log1p_abs <- compose2(log1p, abs)
log1p_abs(c(-2, 0, 3))

Composition works best when intermediate functions have simple, stable contracts and limited side effects.

Separate configuration from execution

Instead of branching inside a loop, choose the strategy once:

choose_center <- function(method = c("mean", "median")) {
  method <- match.arg(method)
  switch(method, mean = mean, median = median)
}

center <- choose_center("median")
center(c(1, 2, 100))
# [1] 2

This pattern becomes a function factory when the returned function also captures configuration.

Key lesson. Treating functions as data makes behavior configurable without duplicating control flow.

10. Iteration with functionals

A functional makes an iteration contract explicit. Base R provides several useful families:

  • lapply() returns a list;
  • vapply() requires a declared output shape and type;
  • Map() iterates over multiple inputs;
  • Filter() keeps elements satisfying a predicate;
  • Reduce() combines elements into one result;
  • walk-like behavior can be written with a loop when only side effects matter.
columns <- list(a = 1:5, b = c(2, 4, 8), c = c(10, 20))

vapply(columns, mean, numeric(1))
#    a    b    c
#  3.0  4.7 15.0

Prefer vapply() over sapply() in programmatic code because the output contract is explicit:

lengths <- vapply(columns, length, integer(1))

Write the loop first

If the pattern is unclear, a preallocated loop is an excellent starting point:

out <- numeric(length(columns))
names(out) <- names(columns)

for (i in seq_along(columns)) {
  out[[i]] <- mean(columns[[i]])
}

Once the input, operation, and output shape are stable, a functional may express the same contract more directly.

Reduction

Reduce(
  f = \(left, right) paste(left, right, sep = " -> "),
  x = c("extract", "transform", "load")
)
# [1] "extract -> transform -> load"

Optional purrr vocabulary

The purrr package provides a regular map family:

# install.packages("purrr")
library(purrr)

map(columns, mean)       # list
map_dbl(columns, mean)   # double vector
map_int(columns, length) # integer vector
walk(files, process_file) # side effects; returns input invisibly

Typed variants fail if each result is not length one and compatible with the requested type. That failure is valuable: it catches contract drift near the source.

Key lesson. Choose iteration by input arity, output type, and side-effect policy—not by a belief that loops are inherently slow.

11. Side effects, resources, and cleanup

Pure functions depend only on arguments and return a value without changing outside state. They are easiest to test and compose. Real programs also write files, draw plots, emit logs, update databases, and use connections. Keep the pure core separate from the side-effect shell.

format_report <- function(data) {
  summary <- numeric_summary(data)
  sprintf(
    "n=%d, missing=%d, mean=%.2f, sd=%.2f",
    summary$n, summary$missing, summary$mean, summary$sd
  )
}

write_report <- function(data, path) {
  text <- format_report(data)
  writeLines(text, path)
  invisible(path)
}

Always clean up acquired resources

Register cleanup immediately after acquisition:

read_first_line <- function(path) {
  connection <- file(path, open = "rt")
  on.exit(close(connection), add = TRUE)

  readLines(connection, n = 1L, warn = FALSE)
}

Using add = TRUE avoids replacing earlier exit handlers. Cleanup runs on normal return and on errors.

Restore temporary state

with_digits <- function(digits, code) {
  old <- options(digits = digits)
  on.exit(options(old), add = TRUE)
  force(code)
}

Avoid changing global options, working directory, random seed, or graphical parameters without restoring them.

Randomness as a dependency

For deterministic tests, either accept a seed explicitly and restore state carefully, or pass a generator function:

bootstrap_mean <- function(x, draw = sample) {
  resampled <- draw(x, size = length(x), replace = TRUE)
  mean(resampled)
}

Tests can provide a fixed draw implementation.

Key lesson. Side effects should be narrow, explicit, and paired with immediate cleanup registration.

12. Conditions, debugging, documentation, and tests

Errors, warnings, and messages are structured conditions. A function signals; a caller decides how to handle.

parse_percentage <- function(x) {
  if (!is.character(x)) {
    stop("x must be character", call. = FALSE)
  }

  clean <- sub("%$", "", x)
  value <- suppressWarnings(as.numeric(clean))

  bad <- is.na(value) & !is.na(x)
  if (any(bad)) {
    warning(
      sprintf("%d value(s) could not be parsed", sum(bad)),
      call. = FALSE
    )
  }

  value / 100
}

Catch only conditions you can recover from:

read_config <- function(path, default = list()) {
  tryCatch(
    readRDS(path),
    error = function(condition) {
      warning(
        "Could not read configuration: ",
        conditionMessage(condition),
        call. = FALSE
      )
      default
    }
  )
}

A catch-all that silently returns NULL usually hides defects.

Debug from evidence

  1. Make the failure reproducible.
  2. Reduce it to the smallest input.
  3. Inspect traceback() or the IDE call stack.
  4. Add browser(), debugonce(), or temporary assertions at the narrowest suspected point.
  5. Convert the confirmed bug into a regression test.

Document the contract

A useful function description covers:

  • purpose in one sentence;
  • each argument, including type and missing-value meaning;
  • returned type and shape;
  • side effects and conditions;
  • one minimal example and one edge case.

Base assertions and testthat

Small internal checks can use stopifnot(), but public-facing errors often need custom messages. A testthat test might look like:

# testthat::test_that("safe_ratio rejects zero denominators", {
#   testthat::expect_error(
#     safe_ratio(1, 0),
#     "denominator must not contain zero"
#   )
# })
#
# testthat::test_that("safe_ratio preserves empty output", {
#   testthat::expect_identical(
#     safe_ratio(numeric(), numeric()),
#     numeric()
#   )
# })

Test normal behavior, empty input, missing values, invalid types, boundaries, class and attributes, warnings/errors, and side effects.

Key lesson. Production functions are defined as much by their conditions, documentation, and tests as by their happy-path result.

Part III — Advanced patterns

13. Closures and function factories

A function factory returns a function. The returned closure retains the factory call’s execution environment.

make_power <- function(exponent) {
  force(exponent)
  function(x) x^exponent
}

square <- make_power(2)
cube <- make_power(3)

square(4)
cube(4)

The manufactured functions share code structure but capture different values. Inspect their environments:

environment(square)
ls(environment(square))
get("exponent", envir = environment(square))

Parameterized validators

make_range_validator <- function(lower = -Inf, upper = Inf, inclusive = TRUE) {
  force(lower)
  force(upper)
  force(inclusive)

  function(x, arg = "x") {
    if (!is.numeric(x)) {
      stop(arg, " must be numeric", call. = FALSE)
    }

    ok <- if (inclusive) {
      x >= lower & x <= upper
    } else {
      x > lower & x < upper
    }

    if (any(!ok | is.na(ok))) {
      stop(
        sprintf("%s must be inside the configured range", arg),
        call. = FALSE
      )
    }

    invisible(x)
  }
}

assert_probability <- make_range_validator(0, 1)

Stateful closures

Closures can intentionally modify captured state:

make_counter <- function(start = 0L) {
  value <- as.integer(start)

  function(step = 1L) {
    value <<- value + as.integer(step)
    value
  }
}

counter <- make_counter()
counter()
counter(5L)

This is controlled reference-like state. It is useful for counters, caches, or mock objects, but it reduces transparency. Provide methods to inspect or reset state if callers need them, and avoid sharing one stateful closure accidentally across tests.

Memory retention

A closure keeps its enclosing environment reachable. If that environment contains a huge temporary object, it may remain in memory. Factories should create a small environment containing only necessary configuration.

Key lesson. A closure packages code with private data. Force captured promises and keep the captured environment intentionally small.

14. Function operators and decorators

A function operator takes a function and returns a modified function. This separates a reusable policy from the underlying calculation.

Timing

with_timing <- function(f) {
  force(f)

  function(...) {
    started <- proc.time()[["elapsed"]]
    on.exit({
      elapsed <- proc.time()[["elapsed"]] - started
      message(sprintf("Elapsed: %.3f seconds", elapsed))
    }, add = TRUE)

    f(...)
  }
}

timed_mean <- with_timing(mean)

Retry with a bounded policy

with_retry <- function(f, attempts = 3L, wait = 0) {
  force(f)
  attempts <- as.integer(attempts)

  if (length(attempts) != 1L || is.na(attempts) || attempts < 1L) {
    stop("attempts must be a positive integer", call. = FALSE)
  }

  function(...) {
    last_error <- NULL

    for (attempt in seq_len(attempts)) {
      result <- tryCatch(
        list(ok = TRUE, value = f(...)),
        error = function(condition) {
          last_error <<- condition
          list(ok = FALSE)
        }
      )

      if (result$ok) {
        return(result$value)
      }
      if (attempt < attempts && wait > 0) {
        Sys.sleep(wait)
      }
    }

    stop(last_error)
  }
}

Retries are appropriate only for transient failures and idempotent operations. Repeating a non-idempotent write may duplicate side effects.

Memoization

A small cache can use an environment:

memoize_one_arg <- function(f) {
  force(f)
  cache <- new.env(parent = emptyenv())

  function(x) {
    key <- serialize(x, NULL, version = 3)
    key <- paste(as.integer(key), collapse = "-")

    if (!exists(key, envir = cache, inherits = FALSE)) {
      assign(key, f(x), envir = cache)
    }

    get(key, envir = cache, inherits = FALSE)
  }
}

Production caching needs size limits, invalidation, collision-resistant keys, and a policy for hidden dependencies. Never memoize a function whose result depends on time, randomness, files, options, or network state unless those dependencies are represented in the cache key.

Key lesson. Operators are powerful for reusable cross-cutting behavior, but wrappers must preserve argument forwarding, errors, and side-effect semantics.

15. Recursion and recursive data

Recursion solves a problem by applying the same function to smaller instances. Every recursive function needs:

  • a base case that terminates;
  • a step that makes measurable progress;
  • a rule for combining results.
sum_nested <- function(x) {
  if (!is.list(x)) {
    if (!is.numeric(x)) {
      stop("leaves must be numeric", call. = FALSE)
    }
    return(sum(x))
  }

  sum(vapply(x, sum_nested, numeric(1)))
}

sum_nested(list(1:3, list(4, c(5, 6))))
# [1] 21

Walking an expression tree

count_symbols <- function(expr) {
  if (is.symbol(expr)) {
    return(1L)
  }
  if (!is.call(expr)) {
    return(0L)
  }

  children <- as.list(expr)
  sum(vapply(children, count_symbols, integer(1)))
}

count_symbols(quote(mean(x + y)))

R does not optimize tail calls, and deep recursion can exhaust the evaluation stack. Prefer an explicit stack or loop for very deep or linear recursion.

Accumulator pattern

For tree traversal, pass accumulated context explicitly rather than using globals:

collect_names <- function(x, path = character()) {
  if (!is.list(x)) {
    return(list(path))
  }

  labels <- names(x)
  if (is.null(labels)) {
    labels <- as.character(seq_along(x))
  }

  unlist(
    Map(
      \(item, label) collect_names(item, c(path, label)),
      x,
      labels
    ),
    recursive = FALSE
  )
}

Key lesson. Recursion is natural for trees and language objects; prove termination and keep context explicit.

16. Extensible behavior with S3 generics

An S3 generic selects a method based primarily on the class of its first argument.

describe <- function(x, ...) {
  UseMethod("describe")
}

describe.default <- function(x, ...) {
  sprintf("<%s> length %d", typeof(x), length(x))
}

describe.data.frame <- function(x, ...) {
  sprintf("<data.frame> %d rows x %d columns", nrow(x), ncol(x))
}

describe.factor <- function(x, ...) {
  sprintf("<factor> %d values, %d levels", length(x), nlevels(x))
}
describe(1:5)
describe(iris)
describe(factor(c("low", "high", "low")))

Keep the generic thin. Its job is dispatch, not substantial computation. Methods should share a compatible argument interface and output contract.

Creating a small S3 class

new_percentage <- function(x = double()) {
  stopifnot(is.double(x))
  structure(x, class = "percentage")
}

percentage <- function(x) {
  if (!is.numeric(x)) {
    stop("x must be numeric", call. = FALSE)
  }
  x <- as.double(x)
  if (any(x < 0 | x > 1, na.rm = TRUE)) {
    stop("x must be between 0 and 1", call. = FALSE)
  }
  new_percentage(x)
}

format.percentage <- function(x, digits = 1, ...) {
  paste0(formatC(unclass(x) * 100, digits = digits, format = "f"), "%")
}

print.percentage <- function(x, ...) {
  print(format(x, ...), quote = FALSE)
  invisible(x)
}

The constructor establishes representation, the helper performs user-friendly validation/coercion, and methods define behavior. A class is worthwhile when several functions should share invariants and dispatch, not merely to rename a vector.

Key lesson. Use S3 when external packages or users need to add behavior without modifying the original function.

17. Metaprogramming and tidy evaluation

R can capture code without evaluating it. Base tools include quote(), substitute(), bquote(), call(), and eval():

expr <- quote(x + y)
eval(expr, envir = list(x = 10, y = 5))
# [1] 15

This power should solve a real interface problem. Ordinary value-based functions are easier to understand and compose.

A base R data-mask wrapper

subset_rows <- function(data, condition) {
  condition <- substitute(condition)
  keep <- eval(condition, envir = data, enclos = parent.frame())

  if (!is.logical(keep) || length(keep) != nrow(data)) {
    stop("condition must produce one logical value per row", call. = FALSE)
  }

  data[keep & !is.na(keep), , drop = FALSE]
}

subset_rows(iris, Sepal.Length > 7 & Species == "virginica")

The expression is evaluated with columns visible as names, then falls back to the caller environment. This convenience creates ambiguity when a column and caller variable share a name.

Optional rlang pattern

rlang pairs captured expressions with their environment in quosures:

# library(rlang)
# library(dplyr)
#
# summarise_mean <- function(data, column) {
#   column <- enquo(column)
#   summarise(data, mean = mean(!!column, na.rm = TRUE))
# }
#
# # Modern embracing syntax for a single data-masked argument:
# summarise_mean <- function(data, column) {
#   dplyr::summarise(data, mean = mean({{ column }}, na.rm = TRUE))
# }

Use .data and .env pronouns when data-mask ambiguity matters. Capture only arguments that the interface explicitly defines as expressions; ordinary arguments should remain ordinary values.

Metaprogramming risks

  • evaluating an expression twice;
  • losing the caller’s environment;
  • injecting untrusted text as code;
  • accepting duplicate or unnamed dynamic arguments;
  • creating an interface that is concise interactively but difficult to wrap.

Key lesson. Track expression, evaluation environment, and data context separately. Prefer standard evaluation unless syntax capture materially improves the user interface.

18. Performance and production API design

Do not optimize by intuition. First establish correctness, then profile realistic work, then benchmark alternatives.

slow_growth <- function(n) {
  out <- numeric()
  for (i in seq_len(n)) {
    out <- c(out, sqrt(i))
  }
  out
}

preallocated <- function(n) {
  out <- numeric(n)
  for (i in seq_len(n)) {
    out[[i]] <- sqrt(i)
  }
  out
}

vectorized <- function(n) {
  sqrt(seq_len(n))
}

The progression illustrates three common improvements: avoid repeated growth, preallocate, then use an existing vectorized primitive when it precisely matches the task.

Optional benchmarking

# library(bench)
# bench::mark(
#   preallocated = preallocated(10000),
#   vectorized = vectorized(10000),
#   check = TRUE
# )

Benchmark representative inputs and compare distributions, allocations, and garbage collection—not one timing.

Production function checklist

Contract

  • Are argument types, lengths, classes, and missing-value behavior clear?
  • Is the output type and shape stable?
  • Are empty input and boundaries intentional?

Evaluation

  • Are important dependencies explicit?
  • Could lazy evaluation delay an error or retain a large environment?
  • Does captured code keep the correct caller environment?

Side effects

  • Are files, options, connections, randomness, and global state controlled?
  • Is cleanup registered immediately with on.exit()?
  • Is retry or caching behavior safe?

Extensibility

  • Is a plain function enough?
  • Would a function argument solve the variation more simply than a class?
  • Is S3 or metaprogramming justified by external extension needs?

Evidence

  • Do tests cover normal, empty, missing, invalid, and boundary cases?
  • Was the real bottleneck found with a profiler?
  • Do benchmarks check equivalent results?

Optimization order

  1. Remove unnecessary work.
  2. Choose a better algorithm.
  3. Reuse a mature implementation.
  4. Vectorize with an appropriate primitive.
  5. Reduce copying and allocation.
  6. Parallelize only independent, sufficiently large tasks.
  7. Move a proven hot kernel to C++ only when the complexity is justified.

Key lesson. The most advanced function is not the cleverest one; it is the smallest interface that remains correct, observable, composable, and fast enough.

Pattern cookbook

Guard clause

normalize <- function(x) {
  if (length(x) == 0L) {
    return(numeric())
  }
  if (!is.numeric(x)) {
    stop("x must be numeric", call. = FALSE)
  }

  total <- sum(x)
  if (total == 0) {
    stop("sum(x) must not be zero", call. = FALSE)
  }

  x / total
}

Strategy argument

aggregate_values <- function(x, strategy = c("mean", "median", "sum")) {
  strategy <- match.arg(strategy)
  f <- switch(strategy, mean = mean, median = median, sum = sum)
  f(x)
}

Safe result object

capture_result <- function(expr) {
  tryCatch(
    list(ok = TRUE, value = force(expr), error = NULL),
    error = function(condition) {
      list(ok = FALSE, value = NULL, error = condition)
    }
  )
}

Common anti-patterns

Anti-pattern Why it hurts Better approach
Reading required values from globals Hidden dependency and fragile tests Pass values or functions explicitly
Returning different types for similar cases Every caller must branch Define one stable output contract
Silently dropping missing values Can change analytical meaning Expose and document na.rm
Growing vectors in a loop Repeated allocation and copying Preallocate or use a suitable functional
Broad tryCatch() returning NULL Hides programming defects Catch specific recoverable failures
Parsing strings into code Injection risk and lost structure Use values, calls, or captured expressions
Using <<- for ordinary output Non-local mutation Return a value; restrict state to closures
Adding S3 or tidy evaluation immediately Complexity before a reuse need exists Start with a plain function
Optimizing before profiling Work may target the wrong code Profile realistic inputs first
