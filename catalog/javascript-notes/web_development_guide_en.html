Web Development Fundamentals

Start with what happens after entering a URL, then learn page structure, presentation, behavior, network communication, quality, and deployment by building a small web application.

Beginner friendlyFront-end foundationsFull-stack thinkingInteractive labs

This tutorial is a set of personal learning and practice notes.

Learning outcome: By the end, you will be able to explain how a site travels from a server to a browser, create semantic responsive pages, add JavaScript behavior, read API data, and understand the basics of security, performance, version control, and deployment.

1. The web development landscape

Web development is the practice of building software delivered through a browser. A modern website is rarely “a few pages.” It is a system made of a user interface, application logic, data, network protocols, servers, and deployment infrastructure.

Front end

Runs in the browser and controls what users see and operate. Its foundational technologies are HTML, CSS, and JavaScript.

Back end

Runs on servers and handles permissions, business rules, databases, email, payments, and APIs. Common languages include JavaScript, Python, Java, and Go.

Full stack

Connects the front end, server, and data layers while understanding testing, deployment, monitoring, and security boundaries.

Layer Main question Common technology
Content structure What does the page mean? HTML
Presentation How is it laid out and adapted? CSS
Browser behavior What happens after an action? JavaScript and the DOM
Network interface How is data exchanged? HTTP, JSON, REST/GraphQL
Server Who may do what, and where are rules enforced? Node.js, Python, databases
Delivery How does a change reach users reliably? Git, CI/CD, CDN, logging
Learn the platform before the frameworkReact, Vue, Next.js, and similar tools are valuable, but they ultimately produce HTML, CSS, and JavaScript and must follow browser rules. Strong platform knowledge makes frameworks easier to reason about.

2. What happens when you enter a URL?

The URL https://example.com/products?id=42#reviews contains:

Part Example Purpose
Scheme https Communication and encryption rules
Host example.com Name of the server
Path /products Resource location on the server
Query string ?id=42 Parameters sent to the server
Fragment #reviews Browser-side location; not sent in the HTTP request

2.1 A page request, step by step

  1. The browser parses the URL and checks caches and security policies.
  2. DNS converts the domain name into a server IP address.
  3. The browser creates a TCP connection; HTTPS adds a TLS handshake and certificate validation.
  4. The browser sends an HTTP request such as GET /products?id=42.
  5. The server returns a status code, response headers, and an HTML body.
  6. The browser parses HTML and requests CSS, JavaScript, fonts, and images.
  7. It creates the DOM and CSSOM, computes layout, and paints pixels.
  8. JavaScript registers events, requests more data, and updates the page.

2.2 Client, server, and database

The browser is the client. A server receives requests, validates identity, applies business rules, and may read or write a database. A database should not normally be exposed directly to ordinary browsers; the server API is the controlled boundary.

Browser ──HTTPS──> Web server / API ──query──> Database
   ↑                    │                         │
   └──── HTML/JSON ─────┴──── validated data ────┘

2.3 HTTP essentials

A request has a method, URL, headers, and an optional body. A response has a status code, headers, and a body.

Method Typical meaning Safe to repeat?
GET Read a resource Yes; should not change server state
POST Create or trigger an operation Usually not
PUT Replace a whole resource Usually idempotent
PATCH Update part of a resource Depends on design
DELETE Delete a resource Commonly designed to be idempotent

Common status codes include 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests, and 500 Internal Server Error.

4. HTML: meaningful structure

HTML is a markup language, not a programming language. Elements describe the meaning and hierarchy of content. Browsers build the DOM from that structure; assistive technology and search engines also depend on its semantics.

4.1 Elements, attributes, and nesting

<a href="/courses" class="primary-link">View courses</a>
  • <a> and </a> are opening and closing tags.
  • href and class are attributes.
  • “View courses” is content.
  • Some elements such as <img> and <input> do not have a closing tag.

Nest elements correctly. Browsers attempt to repair invalid HTML, but their repaired DOM may not match your intent. Inspect the final DOM in the Elements panel or use an HTML validator.

4.2 A semantic page skeleton

<body>
  <header>
    <nav aria-label="Primary">...</nav>
  </header>

  <main>
    <article>
      <header><h1>Article title</h1></header>
      <section aria-labelledby="overview-heading">
        <h2 id="overview-heading">Overview</h2>
      </section>
    </article>
    <aside aria-label="Related content">...</aside>
  </main>

  <footer>...</footer>
</body>

Prefer semantic elements such as header, nav, main, article, section, aside, footer, and button over using a div for everything. Semantics provide document structure, accessibility information, and—in the case of controls—correct keyboard behavior.

4.3 Headings, links, buttons, and images

  • Give the page one clear main h1; do not skip heading levels merely for visual size.
  • Use <a href> to navigate and <button> to perform an action on the current page.
  • Give meaningful images descriptive alt; use alt="" for purely decorative images.
  • Give every form control a visible <label> rather than relying on a placeholder.
<label for="email">Email address</label>
<input id="email" name="email" type="email" autocomplete="email" required>

<img src="team.jpg" alt="The product team discusses a prototype at a whiteboard">

4.4 Form basics

<form action="/api/contact" method="post">
  <label for="name">Name</label>
  <input id="name" name="name" required maxlength="80">

  <label for="message">Message</label>
  <textarea id="message" name="message" required></textarea>

  <button type="submit">Send</button>
</form>

Browser validation improves usability, but the server must validate, normalize, and authorize every input again. The front end is never the only security boundary.

5. CSS: cascade, box model, and layout

CSS rules contain a selector and declarations:

.card {
  padding: 1rem;
  color: #172033;
  background: white;
  border: 1px solid #dce5f0;
  border-radius: 12px;
}

5.1 Cascade and specificity

When multiple rules set the same property, the browser considers origin, importance, cascade layer, selector specificity, and source order. Good defaults are:

  • use simple class selectors;
  • avoid deep nesting and routine use of !important;
  • organize styles by component or responsibility;
  • inspect the final value and override source in the Computed panel.
/* Low specificity and reusable */
.button { color: white; }
.button-danger { background: #bd3652; }

/* Avoid depending on a deeply nested structure */
main .panel ul li a.button { /* ... */ }

5.2 The box model

Every visible element can be understood as content + padding + border + margin.

*, *::before, *::after {
  box-sizing: border-box;
}

With border-box, a declared width includes padding and border, which usually makes sizing easier to predict.

5.3 Flexbox and Grid

Flexbox is suited to one-dimensional alignment. Grid is suited to two-dimensional rows and columns:

.toolbar {
  display: flex;
  align-items: center;
  justify-content: space-between;
  gap: 1rem;
  flex-wrap: wrap;
}

.cards {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(220px, 1fr));
  gap: 1rem;
}

Start with normal document flow. Introduce Flexbox, Grid, or positioning when the design actually requires them. Avoid building the main page structure with many absolutely positioned elements.

5.4 Responsive design

Mobile-first CSS starts with narrow-screen defaults and enhances the layout at wider breakpoints:

.layout { display: block; }

@media (min-width: 768px) {
  .layout {
    display: grid;
    grid-template-columns: 2fr 1fr;
    gap: 2rem;
  }
}

Use flexible widths, max-width, relative units, and content-driven breakpoints. Test more than one phone width: include text zoom, landscape orientation, and unusually long content.

6. JavaScript: page behavior

JavaScript is the browser’s programming language for state, events, data transformation, network requests, and dynamic interfaces.

const button = document.querySelector("#toggle-button");
const panel = document.querySelector("#details-panel");

button.addEventListener("click", () => {
  const isOpen = panel.classList.toggle("is-open");
  button.setAttribute("aria-expanded", String(isOpen));
});

6.1 State, rendering, and events

A small application can be modeled as:

  1. State: what the data is now.
  2. Render: how data becomes DOM.
  3. Events: how user actions change the data.
let count = 0;

function render() {
  document.querySelector("#count").textContent = String(count);
}

document.querySelector("#increase").addEventListener("click", () => {
  count += 1;
  render();
});

Centralizing state changes in a few functions is easier to debug than unrelated DOM mutations spread across many handlers.

6.2 Safe DOM updates

const item = document.createElement("li");
item.textContent = userProvidedText;
list.append(item);

Use textContent for untrusted content. Concatenating user input into innerHTML can create a cross-site scripting (XSS) vulnerability. Do not run external strings with eval().

import { loadProducts } from "./api.js";

7. Browser rendering and developer tools

The browser converts HTML into the DOM and CSS into the CSSOM, combines them into a render tree, performs layout for size and position, paints pixels, and may composite separate layers.

Panel Main use
Elements Inspect DOM, CSS, box model, and accessibility properties
Console Read errors and logs; run temporary JavaScript
Network Inspect requests, status, cache, responses, and waterfalls
Sources Set breakpoints, step through code, and inspect scope
Performance Analyze long tasks, layout, painting, and input delay
Application Inspect storage, service workers, and caches
Lighthouse Get diagnostics for performance, accessibility, and SEO

Debug by observing facts first: the actual error, variable value, request, and response. Avoid changing many lines based only on a guess.

8. APIs, JSON, and asynchronous work

An API is an agreed interface between software components. Browsers commonly request JSON over HTTP:

{
  "id": 42,
  "name": "Keyboard",
  "price": 89.99,
  "inStock": true
}
async function loadProduct(id) {
  const response = await fetch(`/api/products/${id}`, {
    headers: { "Accept": "application/json" }
  });

  if (!response.ok) {
    throw new Error(`Could not load product: ${response.status}`);
  }

  return response.json();
}

fetch does not reject automatically for a 404 or 500; check response.ok. Design at least four interface states: loading, success, empty, and failure.

async function showProducts() {
  setStatus("loading");
  try {
    const products = await loadProducts();
    if (products.length === 0) setStatus("empty");
    else renderProducts(products);
  } catch (error) {
    setStatus("error", error.message);
  }
}

8.1 Same-origin policy and CORS

Browsers restrict scripts from one origin reading responses from another origin. An origin is the combination of scheme, host, and port. A server can use CORS response headers to allow selected origins. Front-end code cannot bypass this browser protection on its own.

8.2 API design basics

  • Let URLs identify resources, such as /api/products/42.
  • Let methods describe actions: GET reads and POST creates.
  • Use accurate status codes and stable JSON shapes.
  • Validate, authorize, rate-limit, and log important operations.
  • Paginate large collections rather than sending every record.
  • Never place passwords or sensitive tokens in URLs.

9. State, cookies, and browser storage

HTTP is stateless: by default, a server does not know whether two requests belong to the same signed-in session. Cookies, tokens, or server-side sessions establish continuity.

Option Good for Important limitation
In-memory variable Temporary state on the current page Lost on refresh
localStorage Small, non-sensitive preferences and drafts Synchronous and readable by page JavaScript
sessionStorage Temporary state for the current tab Removed when the tab session ends
IndexedDB Larger structured offline data Asynchronous, more complex API
Cookie Server sessions Configure Secure, HttpOnly, and SameSite 
const settings = { theme: "dark", density: "comfortable" };
localStorage.setItem("settings", JSON.stringify(settings));

const saved = localStorage.getItem("settings");
const restored = saved ? JSON.parse(saved) : {};

Do not put passwords, private keys, or long-lived access tokens in localStorage. Any malicious script running on the page may be able to read it.

10. Accessibility and inclusive design

The web should let people complete tasks across devices, physical abilities, and environments.

10.1 A practical baseline

  • Every action works with a keyboard and has a visible focus indicator.
  • Heading order is clear and there is one main region.
  • Form controls have labels; errors are specific and associated with fields.
  • Text contrast is sufficient; color is not the only status signal.
  • Images have appropriate alt text; video has captions or a transcript.
  • Motion respects prefers-reduced-motion.
  • The page remains usable at 200% zoom.
  • Dynamic status uses an appropriate aria-live region without excessive announcements.
:focus-visible {
  outline: 3px solid #13b8c5;
  outline-offset: 3px;
}

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    scroll-behavior: auto !important;
    animation-duration: 0.01ms !important;
  }
}
The first rule of ARIAIf a native HTML element already provides the needed semantics and behavior, use it. For example, use a real <button>, not a clickable <div>.

11. Web security and privacy basics

Users can inspect or change browser code and requests, so every genuine security decision must be enforced on a trusted server.

Risk Cause Baseline protection
XSS Untrusted content executes as script Output encoding, textContent, CSP
CSRF A browser sends a forged request with login cookies SameSite cookies, CSRF token, origin checks
SQL injection Input is concatenated into a database query Parameterized queries, least privilege
Broken authorization A button is hidden but the server does not check access Authorize every sensitive operation
Dependency risk A third-party package is vulnerable or compromised Lock versions, audit, minimize dependencies
Secret leakage A key is placed in front-end code or source control Server-side secret management and key rotation 
// Wrong: anyone can see this after the browser downloads it
const PRIVATE_API_KEY = "secret-value";

The front end may hold identifiers explicitly designed to be public. True secrets belong in server environment variables or a secret-management service.

11.1 HTTPS and security headers

HTTPS encrypts transport and validates the server’s identity. Common security headers include Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options, and a suitable Referrer-Policy. Test each policy against the site’s actual resources.

11.2 Privacy minimization

Collect only data necessary for a clear feature, explain its purpose and retention, limit internal access, and offer deletion routes. Analytics and third-party embeds may also collect personal information.

12. Performance, SEO, and progressive enhancement

12.1 Performance is user experience

Performance is not only total download size. It includes when content appears, when the page becomes interactive, how quickly it responds, and whether the layout jumps.

  • Compress and correctly size images; use modern formats.
  • Give images dimensions to reduce layout shift.
  • Lazy-load off-screen media.
  • Reduce render-blocking CSS and JavaScript.
  • Split non-critical code and cache hashed static assets.
  • Use a CDN to shorten the network path for static files.
  • Measure on real devices and slow networks, not only a development machine.
<img
  src="hero-960.webp"
  srcset="hero-480.webp 480w, hero-960.webp 960w"
  sizes="(max-width: 600px) 100vw, 50vw"
  width="960"
  height="640"
  alt="A team reviews a website performance chart"
  loading="lazy">

12.2 SEO basics

  • Give every page an accurate, unique <title> and description.
  • Use semantic HTML, a clear heading structure, and crawlable links.
  • Provide a canonical URL, sitemap, and appropriate robots rules.
  • Set Open Graph metadata for shared pages.
  • Keep important content visible when JavaScript fails or is slow where practical.

The durable basis of SEO is useful content, clear structure, good performance, and a trustworthy site—not keyword stuffing.

12.3 Progressive enhancement

Start with a working HTML core, improve presentation with CSS, and enhance interaction with JavaScript. When the product permits it, users should still be able to read essential content or submit a basic form if scripts fail.

13. Git, dependencies, builds, and deployment

13.1 A basic Git workflow

git init
git status
git add index.html styles.css app.js
git commit -m "Build initial web page"

Commits should be small, meaningful, and explain why a change exists. Do not commit passwords, API keys, .env, build caches, or operating-system artifacts. Teams commonly merge changes through branches, code review, and automated checks.

13.2 npm and dependencies

npm init -y
npm install package-name
npm install --save-dev eslint prettier

package.json describes scripts and dependencies; a lockfile records the exact resolved versions. Before adding a package, consider maintenance, bundle size, licensing, and security history. Prefer platform capabilities when they solve the problem cleanly.

13.3 What build tools do

Tools such as Vite can provide a development server, module transforms, code splitting, minification, and content hashing. Production output commonly goes to dist/; deploy that output rather than the development server.

{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  }
}

13.4 Deployment checklist

  1. Run tests and a production build in a clean environment.
  2. Configure environment variables and confirm secrets are absent from the front-end bundle.
  3. Use HTTPS, a custom domain, and appropriate cache headers.
  4. Configure SPA fallback or server routes as required.
  5. Run a smoke test after deployment.
  6. Monitor errors, performance, availability, and critical business flows.
  7. Keep a previous release available for a quick rollback.

14. Complete exercise: product filter

This project combines semantic HTML, responsive CSS, the DOM, array filtering, state rendering, and an empty state.

14.1 HTML

<main class="catalog">
  <header>
    <h1>Product catalog</h1>
    <label for="search">Search by name</label>
    <input id="search" type="search" autocomplete="off">
  </header>
  <p id="result-status" role="status"></p>
  <ul id="product-list" class="product-grid"></ul>
</main>

14.2 CSS

.catalog {
  width: min(100% - 2rem, 70rem);
  margin-inline: auto;
}

.product-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(14rem, 1fr));
  gap: 1rem;
  padding: 0;
  list-style: none;
}

.product-card {
  padding: 1rem;
  border: 1px solid #dce5f0;
  border-radius: 0.75rem;
}

14.3 JavaScript

const products = [
  { id: 1, name: "Keyboard", price: 89 },
  { id: 2, name: "Mouse", price: 39 },
  { id: 3, name: "Monitor", price: 429 }
];

const search = document.querySelector("#search");
const list = document.querySelector("#product-list");
const status = document.querySelector("#result-status");

function renderProducts(items) {
  list.replaceChildren();

  for (const product of items) {
    const item = document.createElement("li");
    item.className = "product-card";

    const heading = document.createElement("h2");
    heading.textContent = product.name;

    const price = document.createElement("p");
    price.textContent = `$${product.price.toFixed(2)}`;

    item.append(heading, price);
    list.append(item);
  }

  status.textContent = items.length
    ? `${items.length} product(s) found`
    : "No matching products";
}

search.addEventListener("input", () => {
  const query = search.value.trim().toLowerCase();
  const filtered = products.filter(product =>
    product.name.toLowerCase().includes(query)
  );
  renderProducts(filtered);
});

renderProducts(products);

Extensions: load products from an API, add loading and failure states, sort by price, synchronize the query with URL parameters, and unit-test the filter function.

15. Testing, debugging, and code quality

15.1 A practical test pyramid

  • Unit tests quickly test pure functions such as filtering and price calculation.
  • Integration tests test how modules, the DOM, and an API client work together.
  • End-to-end tests verify critical flows such as registration or checkout in a real browser.
  • Exploratory testing finds issues automation did not anticipate, especially visual and usability problems.
function calculateTotal(items) {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

console.assert(
  calculateTotal([{ price: 10, quantity: 2 }]) === 20,
  "total should include quantity"
);

15.2 Pre-release checklist

  • HTML has no duplicate IDs; headings and form labels are complete.
  • Every interaction is keyboard-accessible and focus order is sensible.
  • Layout works on phones, tablets, desktops, and at 200% zoom.
  • Loading, empty, failure, and insufficient-permission states are designed.
  • Network inspection shows no unexpected 404s, oversized resources, or sensitive data.
  • The console has no unhandled errors.
  • The server validates input and enforces authorization.
  • Critical flows have tests, monitoring, and a rollback plan.

17. Learning path and quick reference

Completed 0 / 9

A useful sequence is: build a static personal page, then a responsive multi-page site, then a small API-powered application, and finally add a server, database, authentication, tests, and automated deployment. Finish one accessible, working artifact at each stage.

Goal Learn first
Create structure HTML semantics, forms, media
Lay out pages CSS cascade, box model, Flexbox, Grid
Add behavior JavaScript, DOM, events, modules
Connect data HTTP, fetch, JSON, API states
Improve quality Accessibility, security, performance, testing
Deliver reliably Git, builds, deployment, monitoring
The most effective way to learnChoose a small site you would genuinely use. Define the user task, then implement it layer by layer: HTML → CSS → JavaScript → API → tests → deployment. Add one verifiable capability at a time.

Web development is not about memorizing every API. It is about building clear models: how the browser interprets code, which layer can be trusted with data and decisions, whether users can complete tasks across devices and failure states, and how changes reach production safely.
