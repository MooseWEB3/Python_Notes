How to use this tutorial

Object-oriented programming (OOP) is a way to organize a program around objects that own data and behavior. It is especially useful when a program has concepts with identity and a lifecycle: users, bank accounts, orders, sensors, reports, or game characters.

This tutorial targets readers who already know variables, functions, conditions, loops, lists, and dictionaries. Read it in order the first time. Type the examples yourself, change one thing, predict the result, and only then run the code.

Learning goals

By the end, you will be able to:

  • explain the difference between a class and an object;
  • create classes with instance attributes and methods;
  • protect invariants with properties and domain methods;
  • use class attributes, class methods, static methods, and special methods;
  • choose between inheritance and composition;
  • model records with dataclass and categories with Enum;
  • define interfaces with abstract base classes and protocols;
  • design domain-specific exceptions and context managers;
  • test object behavior and refactor common OOP mistakes;
  • build a small, complete library-loan system.

Recommended Python version The examples use Python 3.10 or newer. Most work on older versions after small type-hint changes.

1. The mental model: objects, classes, state, and behavior

1.1 Everything is an object

In Python, integers, strings, functions, modules, and classes are all objects. An object has:

Idea Meaning Example
Identity Which particular object is this? one specific bank account
Type What operations are supported? BankAccount
State What data does it hold now? owner and balance
Behavior What can it do? deposit and withdraw 
message = "hello"

print(type(message))       # <class 'str'>
print(message.upper())     # HELLO
print(message.__class__)   # <class 'str'>

message is an object of class str. The string stores character data and exposes behavior such as .upper().

1.2 A class is a blueprint, not an object collection

A class describes how its objects are constructed and what operations they support. An instance is one object created from that class.

class Dog:
    pass

first = Dog()
second = Dog()

print(type(first))       # <class '__main__.Dog'>
print(first is second)   # False

first and second have the same type but different identities.

1.3 Procedural code versus an object

Procedural code can represent an account with a dictionary and free functions:

account = {"owner": "Amina", "balance": 100.0}

def deposit(account, amount):
    account["balance"] += amount

This is fine for small tasks. As rules accumulate, however, any part of the program can assign an invalid balance or forget validation. A class places the data and its rules together.

class BankAccount:
    def __init__(self, owner, opening_balance=0.0):
        self.owner = owner
        self.balance = opening_balance

    def deposit(self, amount):
        self.balance += amount

OOP is an option, not a requirement Use ordinary functions and simple containers when the data has no meaningful identity or lifecycle. A short data-cleaning pipeline usually does not need a large class hierarchy.

2. Your first useful class

2.1 __init__ initializes a new instance

class BankAccount:
    """A simple account that tracks an owner and a balance."""

    def __init__(self, owner: str, opening_balance: float = 0.0):
        self.owner = owner
        self.balance = float(opening_balance)


account = BankAccount("Amina", 100)
print(account.owner)    # Amina
print(account.balance)  # 100.0

Calling BankAccount(...) creates an object. Python then calls __init__ with that new object as the first argument.

2.2 What self means

self refers to the instance receiving the method call. It is not a keyword, but using any other name would make Python code unnecessarily confusing.

class BankAccount:
    def __init__(self, owner, opening_balance=0.0):
        self.owner = owner
        self.balance = float(opening_balance)

    def deposit(self, amount):
        self.balance += amount
        return self.balance


account = BankAccount("Amina", 100)
account.deposit(25)

# Conceptually equivalent; normally use the first form.
BankAccount.deposit(account, 10)

print(account.balance)  # 135.0

The dot-call account.deposit(25) automatically passes account as self.

2.3 Methods should protect rules

An account should reject non-positive deposits and withdrawals that exceed the balance.

class BankAccount:
    def __init__(self, owner: str, opening_balance: float = 0.0):
        if not owner.strip():
            raise ValueError("owner cannot be empty")
        if opening_balance < 0:
            raise ValueError("opening balance cannot be negative")
        self.owner = owner.strip()
        self.balance = float(opening_balance)

    def deposit(self, amount: float) -> float:
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self.balance += amount
        return self.balance

    def withdraw(self, amount: float) -> float:
        if amount <= 0:
            raise ValueError("withdrawal must be positive")
        if amount > self.balance:
            raise ValueError("insufficient funds")
        self.balance -= amount
        return self.balance

The conditions that must always remain true are called invariants. Here, the owner is non-empty and the balance never becomes negative.

3. Attributes and namespaces

3.1 Instance attributes

Attributes assigned through self belong to each instance.

amina = BankAccount("Amina", 100)
leo = BankAccount("Leo", 40)

amina.deposit(20)
print(amina.balance)  # 120.0
print(leo.balance)    # 40.0

For ordinary user-defined objects, vars(object) reveals the instance namespace.

print(vars(amina))
# {'owner': 'Amina', 'balance': 120.0}

Use this for learning and debugging, not as the normal interface to an object.

3.2 Class attributes

A class attribute is stored on the class and shared as a default across instances.

class BankAccount:
    bank_name = "North Star Bank"
    annual_interest_rate = 0.02

    def __init__(self, owner, opening_balance=0.0):
        self.owner = owner
        self.balance = float(opening_balance)


first = BankAccount("Amina", 100)
second = BankAccount("Leo", 40)

print(first.bank_name)                # North Star Bank
print(second.annual_interest_rate)    # 0.02

Assigning through an instance creates an instance attribute that shadows the class attribute.

first.annual_interest_rate = 0.03

print(first.annual_interest_rate)         # 0.03
print(second.annual_interest_rate)        # 0.02
print(BankAccount.annual_interest_rate)   # 0.02

3.3 The mutable class attribute trap

class BadCart:
    items = []  # shared by every instance


one = BadCart()
two = BadCart()
one.items.append("book")
print(two.items)  # ['book'] -- surprising!

Create per-instance mutable values inside __init__.

class Cart:
    def __init__(self):
        self.items = []

4. Encapsulation and properties

Python does not enforce private fields in the same way as some languages. It relies on clear interfaces and naming conventions.

Name Convention
balance Public API; callers may use it
_balance Internal implementation detail; callers should avoid direct use
__balance Name-mangled to reduce accidental clashes; not true security

4.1 A read-only property

class BankAccount:
    def __init__(self, owner: str, opening_balance: float = 0.0):
        self.owner = owner
        self._balance = float(opening_balance)

    @property
    def balance(self) -> float:
        """Current balance; change it through deposit or withdraw."""
        return self._balance

    def deposit(self, amount: float) -> None:
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self._balance += amount


account = BankAccount("Amina", 100)
print(account.balance)  # looks like an attribute
# account.balance = -5  # AttributeError: no setter

A property lets callers use attribute syntax while the class retains control.

4.2 A validated setter

Use setters when direct assignment is a meaningful operation. Do not add them automatically for every field.

class Temperature:
    def __init__(self, celsius: float):
        self.celsius = celsius

    @property
    def celsius(self) -> float:
        return self._celsius

    @celsius.setter
    def celsius(self, value: float) -> None:
        value = float(value)
        if value < -273.15:
            raise ValueError("temperature cannot be below absolute zero")
        self._celsius = value

    @property
    def fahrenheit(self) -> float:
        return self._celsius * 9 / 5 + 32

Prefer domain methods for important changes order.cancel() communicates intent and can enforce rules better than order.status = "cancelled".

5. The Python data model and special methods

Names such as __init__, __repr__, and __len__ are often called dunder methods. They connect your class to Python syntax and built-in functions.

5.1 __repr__ and __str__

class BankAccount:
    def __init__(self, owner, opening_balance=0.0):
        self.owner = owner
        self._balance = float(opening_balance)

    @property
    def balance(self):
        return self._balance

    def __repr__(self):
        return (
            f"BankAccount(owner={self.owner!r}, "
            f"opening_balance={self.balance!r})"
        )

    def __str__(self):
        return f"{self.owner}'s account: ${self.balance:,.2f}"


account = BankAccount("Amina", 125.5)
print(repr(account))
print(account)
BankAccount(owner='Amina', opening_balance=125.5)
Amina's account: $125.50

Aim for an unambiguous, developer-facing repr. Use str for a friendly display.

5.2 Length, containment, iteration, and equality

class Playlist:
    def __init__(self, name: str):
        self.name = name
        self._songs: list[str] = []

    def add(self, song: str) -> None:
        if song not in self._songs:
            self._songs.append(song)

    def __len__(self) -> int:
        return len(self._songs)

    def __contains__(self, song: str) -> bool:
        return song in self._songs

    def __iter__(self):
        return iter(self._songs)


playlist = Playlist("Focus")
playlist.add("Blue Sky")
playlist.add("Night Train")

print(len(playlist))
print("Blue Sky" in playlist)
for song in playlist:
    print(song)

Only implement a special method when its meaning is natural. A customer does not need __len__ merely because the class has several fields.

6. Class methods, static methods, and alternate constructors

6.1 Instance method

An instance method receives self and works with one object’s state.

6.2 Class method

A class method receives cls. It is commonly used for alternate constructors.

from datetime import date


class Person:
    def __init__(self, name: str, birth_year: int):
        self.name = name
        self.birth_year = birth_year

    @classmethod
    def from_age(cls, name: str, age: int) -> "Person":
        return cls(name, date.today().year - age)


person = Person.from_age("Noah", 30)

Using cls(...) rather than Person(...) allows subclasses to reuse the constructor correctly.

6.3 Static method

A static method receives neither self nor cls. It is a function placed in the class namespace because it closely supports the class.

class ProductCode:
    def __init__(self, value: str):
        if not self.is_valid(value):
            raise ValueError("invalid product code")
        self.value = value.upper()

    @staticmethod
    def is_valid(value: str) -> bool:
        return len(value) == 8 and value[:3].isalpha() and value[3:].isdigit()

If a helper does not strongly belong to the class, keep it as a module-level function.

7. Inheritance and polymorphism

Inheritance describes an is-a relationship. A subclass receives behavior from a base class and may extend or replace it.

7.1 A base class and subclasses

class Notification:
    def __init__(self, recipient: str):
        self.recipient = recipient

    def send(self, message: str) -> None:
        raise NotImplementedError


class EmailNotification(Notification):
    def __init__(self, recipient: str, subject: str):
        super().__init__(recipient)
        self.subject = subject

    def send(self, message: str) -> None:
        print(f"Email to {self.recipient}: {self.subject} — {message}")


class SmsNotification(Notification):
    def send(self, message: str) -> None:
        print(f"SMS to {self.recipient}: {message}")

super() delegates part of initialization to the base class.

7.2 Polymorphism

Polymorphism means different objects can respond to the same operation.

def announce(channels: list[Notification], message: str) -> None:
    for channel in channels:
        channel.send(message)


channels = [
    EmailNotification("a@example.com", "System update"),
    SmsNotification("+1-555-0100"),
]
announce(channels, "Maintenance starts at 18:00")

The function does not need separate if statements for every notification type.

7.3 The substitution rule

A subclass should be usable wherever its base class is expected without surprising the caller. If an alleged subtype has to disable most inherited methods, the relationship is probably wrong.

Avoid deep inheritance trees They make behavior hard to locate and changes risky. Prefer small interfaces and composition unless the is-a relationship is stable and meaningful.

8. Composition and dependency injection

Composition describes a has-a relationship. One object contains or collaborates with another.

8.1 Prefer collaborators over hard-coded dependencies

class PaymentGateway:
    def charge(self, amount: float) -> str:
        return f"payment-{amount:.2f}"


class OrderService:
    def __init__(self, gateway: PaymentGateway):
        self.gateway = gateway

    def checkout(self, total: float) -> str:
        if total <= 0:
            raise ValueError("total must be positive")
        return self.gateway.charge(total)


service = OrderService(PaymentGateway())
receipt = service.checkout(49.95)

Passing the gateway into OrderService is dependency injection. It makes the dependency visible and replaceable.

8.2 Composition is easier to test

class FakeGateway:
    def __init__(self):
        self.charged = []

    def charge(self, amount: float) -> str:
        self.charged.append(amount)
        return "test-receipt"


fake = FakeGateway()
service = OrderService(fake)

assert service.checkout(25) == "test-receipt"
assert fake.charged == [25]

No real payment system is called. The test observes behavior through a simple collaborator.

9. Data classes and enums

9.1 @dataclass removes record-like boilerplate

from dataclasses import dataclass, field


@dataclass
class Course:
    code: str
    title: str
    students: list[str] = field(default_factory=list)

    def enroll(self, student: str) -> None:
        if student not in self.students:
            self.students.append(student)


course = Course("PY101", "Python Foundations")
course.enroll("Maya")
print(course)

The decorator generates __init__, __repr__, and equality based on annotated fields. default_factory=list gives every instance a new list.

9.2 Validation with __post_init__

@dataclass(frozen=True, slots=True)
class Money:
    amount: float
    currency: str = "CAD"

    def __post_init__(self):
        if self.amount < 0:
            raise ValueError("amount cannot be negative")
        if len(self.currency) != 3:
            raise ValueError("currency must be a three-letter code")
        object.__setattr__(self, "currency", self.currency.upper())
  • frozen=True blocks ordinary reassignment after construction.
  • slots=True prevents arbitrary new attributes and can reduce memory use.
  • __post_init__ runs after the generated initializer.

9.3 Enum models a closed set of choices

from enum import Enum, auto


class OrderStatus(Enum):
    PENDING = auto()
    PAID = auto()
    SHIPPED = auto()
    CANCELLED = auto()


status = OrderStatus.PENDING
if status is OrderStatus.PENDING:
    print("Payment is still required")

An enum prevents spelling variants such as "shipped", "Shipped", and "shiped" from silently becoming different states.

10. Abstract base classes and protocols

10.1 An abstract base class defines a required interface

from abc import ABC, abstractmethod


class Exporter(ABC):
    @abstractmethod
    def export(self, rows: list[dict]) -> str:
        """Return serialized rows."""


class CsvExporter(Exporter):
    def export(self, rows: list[dict]) -> str:
        if not rows:
            return ""
        columns = rows[0].keys()
        lines = [",".join(columns)]
        lines.extend(",".join(str(row[col]) for col in columns) for row in rows)
        return "\n".join(lines)

Python prevents direct construction of an incomplete subclass that omits export.

10.2 A protocol describes structural compatibility

from typing import Protocol


class SupportsExport(Protocol):
    def export(self, rows: list[dict]) -> str: ...


def save_report(exporter: SupportsExport, rows: list[dict]) -> str:
    return exporter.export(rows)

A class does not have to inherit from SupportsExport; it only has to provide a compatible method. This formalizes Python’s duck typing: if an object behaves like the required collaborator, it can be used.

Tool Best fit
Inheritance Shared implementation and a stable is-a relationship
Abstract base class Runtime-enforced family of implementations
Protocol Type-checked behavior without forced inheritance
Composition Flexible collaboration and replaceable components

11. Exceptions and resource management

11.1 Domain-specific exceptions

class AccountError(Exception):
    """Base error for account operations."""


class InsufficientFundsError(AccountError):
    def __init__(self, requested: float, available: float):
        self.requested = requested
        self.available = available
        super().__init__(
            f"requested {requested:.2f}, but only {available:.2f} is available"
        )

Callers can catch the specific condition without matching an error message.

try:
    account.withdraw(500)
except InsufficientFundsError as error:
    print(f"Could not withdraw: {error}")

Do not use exceptions for ordinary branching. They represent exceptional failure to complete an operation.

11.2 Context managers

A context manager guarantees setup and cleanup around a block.

class ManagedFile:
    def __init__(self, path: str, mode: str = "r"):
        self.path = path
        self.mode = mode
        self._file = None

    def __enter__(self):
        self._file = open(self.path, self.mode, encoding="utf-8")
        return self._file

    def __exit__(self, exc_type, exc_value, traceback):
        if self._file is not None:
            self._file.close()
        return False  # do not suppress an exception


with ManagedFile("notes.txt") as file:
    text = file.read()

For real file work, use Python’s built-in open, which is already a context manager. This example explains the protocol.

12. Type hints for object-oriented code

Type hints document expectations and help tools find mistakes before runtime. Python still remains dynamically typed.

from __future__ import annotations


class Node:
    def __init__(self, value: str, parent: Node | None = None):
        self.value = value
        self.parent = parent
        self.children: list[Node] = []

    def add_child(self, child: Node) -> None:
        child.parent = self
        self.children.append(child)

Useful forms include:

Form Meaning
Customer one Customer object
Customer | None a customer or no value
list[Customer] a mutable list of customers
Sequence[Customer] any read-only sequence-like input
Callable[[float], str] function receiving a float and returning text
ClassVar[int] class-level value, not an instance field

Prefer abstract input types such as Iterable or Sequence when the method does not require a concrete list.

13. Complete example: a small library-loan system

The following design combines data classes, composition, domain methods, invariants, exceptions, and type hints.

13.1 Model the entities

from __future__ import annotations

from dataclasses import dataclass, field
from datetime import date, timedelta


class LibraryError(Exception):
    pass


class BookUnavailableError(LibraryError):
    pass


class LoanLimitError(LibraryError):
    pass


@dataclass(frozen=True, slots=True)
class Book:
    isbn: str
    title: str
    author: str

    def __post_init__(self):
        if not self.isbn.strip() or not self.title.strip():
            raise ValueError("isbn and title are required")


@dataclass(slots=True)
class Member:
    member_id: str
    name: str
    max_loans: int = 3
    checked_out: set[str] = field(default_factory=set)

    @property
    def can_borrow(self) -> bool:
        return len(self.checked_out) < self.max_loans


@dataclass(frozen=True, slots=True)
class Loan:
    isbn: str
    member_id: str
    borrowed_on: date
    due_on: date

    @property
    def is_overdue(self) -> bool:
        return date.today() > self.due_on

13.2 Coordinate the workflow

class Library:
    def __init__(self, loan_days: int = 14):
        if loan_days <= 0:
            raise ValueError("loan_days must be positive")
        self.loan_days = loan_days
        self._books: dict[str, Book] = {}
        self._members: dict[str, Member] = {}
        self._available: set[str] = set()
        self._loans: dict[str, Loan] = {}

    def add_book(self, book: Book) -> None:
        if book.isbn in self._books:
            raise ValueError(f"duplicate ISBN: {book.isbn}")
        self._books[book.isbn] = book
        self._available.add(book.isbn)

    def register(self, member: Member) -> None:
        if member.member_id in self._members:
            raise ValueError(f"duplicate member: {member.member_id}")
        self._members[member.member_id] = member

    def borrow(self, isbn: str, member_id: str, today: date | None = None) -> Loan:
        if isbn not in self._available:
            raise BookUnavailableError(isbn)

        member = self._members[member_id]
        if not member.can_borrow:
            raise LoanLimitError(member_id)

        borrowed_on = today or date.today()
        loan = Loan(
            isbn=isbn,
            member_id=member_id,
            borrowed_on=borrowed_on,
            due_on=borrowed_on + timedelta(days=self.loan_days),
        )
        self._available.remove(isbn)
        self._loans[isbn] = loan
        member.checked_out.add(isbn)
        return loan

    def return_book(self, isbn: str) -> None:
        loan = self._loans.pop(isbn)
        member = self._members[loan.member_id]
        member.checked_out.remove(isbn)
        self._available.add(isbn)

    def available_books(self) -> list[Book]:
        return sorted(
            (self._books[isbn] for isbn in self._available),
            key=lambda book: book.title.casefold(),
        )

13.3 Use the model

library = Library(loan_days=21)
library.add_book(Book("978-1", "Clean Python", "A. Author"))
library.add_book(Book("978-2", "Practical Statistics", "B. Analyst"))
library.register(Member("M001", "Maya"))

loan = library.borrow("978-1", "M001", date(2026, 8, 11))
print(loan.due_on)  # 2026-09-01

library.return_book("978-1")
print([book.title for book in library.available_books()])

Why this design is useful:

  • Book and Loan are immutable value-like records.
  • Member owns the member-specific loan limit and current ISBNs.
  • Library coordinates operations involving multiple entities.
  • sets make availability and membership checks efficient.
  • domain exceptions distinguish expected failure conditions.
  • state changes happen through methods rather than scattered assignments.

14. Testing classes by behavior

Good tests focus on public behavior and invariants, not private implementation details.

14.1 A simple pytest test

from datetime import date
import pytest


def test_borrow_moves_book_to_member():
    library = Library(loan_days=14)
    library.add_book(Book("1", "Python", "Author"))
    member = Member("M1", "Maya")
    library.register(member)

    loan = library.borrow("1", "M1", date(2026, 1, 1))

    assert loan.due_on == date(2026, 1, 15)
    assert member.checked_out == {"1"}
    assert library.available_books() == []


def test_same_book_cannot_be_borrowed_twice():
    library = Library()
    library.add_book(Book("1", "Python", "Author"))
    library.register(Member("M1", "Maya"))
    library.register(Member("M2", "Noah"))
    library.borrow("1", "M1")

    with pytest.raises(BookUnavailableError):
        library.borrow("1", "M2")

Run tests with:

python -m pip install pytest
python -m pytest -q

14.2 What to test

Use a balanced set of cases:

  • normal construction and operations;
  • invalid input at boundaries;
  • state before and after each command;
  • interactions between collaborating objects;
  • domain exceptions and unchanged state after failure;
  • equality and special methods when they are part of the public API.

15. Common mistakes and better alternatives

15.1 A class that only stores data

If a class has no behavior or invariants, a dictionary, named tuple, or data class may be clearer than a hand-written class.

15.2 One giant “manager” object

A class that loads files, validates users, sends email, calculates prices, and writes reports has too many reasons to change. Split responsibilities into collaborating components.

15.3 Getters and setters for every attribute

Python permits public attributes. Add a property only when you need validation, computation, compatibility, or read-only access.

15.4 Inheriting only to reuse a few lines

Inheritance creates a semantic promise, not just code reuse. Extract a function or compose a helper object when the subclass is not truly a subtype.

15.5 Mutable default arguments

class Team:
    def __init__(self, members=[]):  # wrong: one shared list
        self.members = members

Use None and create a new list.

class Team:
    def __init__(self, members=None):
        self.members = list(members) if members is not None else []

15.6 Returning internal mutable collections

If callers must not mutate an internal list, return an immutable view or copy.

class Team:
    def __init__(self):
        self._members = []

    @property
    def members(self) -> tuple[str, ...]:
        return tuple(self._members)

16. Design checklist

Before creating a class, ask:

  • Does the concept have meaningful state, behavior, identity, or a lifecycle?
  • Can I state the class responsibility in one short sentence?
  • Which invariants must always remain true?
  • What is the smallest useful public interface?
  • Should this be a regular class, data class, enum, function, or plain container?
  • Is the relationship really is-a, or is composition more accurate?
  • Can collaborators be passed in so the class is easy to test?
  • Do special methods have an obvious, unsurprising meaning?
  • Are failure conditions represented clearly?
  • Can a test verify behavior without reaching into private attributes?

Final perspective

Good OOP is not about maximizing the number of classes. It is about assigning responsibility clearly, protecting important rules, and making change safer. Begin with simple functions and data. Introduce an object when state and behavior genuinely belong together. Prefer small public interfaces, shallow inheritance, explicit composition, and tests that describe observable behavior.
